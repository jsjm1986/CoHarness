# 电脑间加密备份

[English](README.md) | 中文

## 概述

在 **Admin → 部署** 中选择一个保护范围、源电脑与另一台受管接收电脑。源 Gateway 在后台导出、加密并提交。接收仓库通过检查后才会记录恢复点。个人和项目 Runtime 可以继续服务用户并执行后台任务。

## 配置电脑

先开启[多电脑部署](../deployment-topology/README.zh.md)，并接入目标电脑。在源电脑和恢复演练电脑上安装运维认可的 restic 可执行文件。已验证的原生版本为 0.18.1。它通过现有 HTTPS Gateway 或已接入的转发通道使用 [restic REST 仓库协议](https://restic.readthedocs.io/en/stable/100_references.html#rest-backend)。

每条策略生成三个独立随机值。源电脑保管追加凭据与仓库密码，恢复凭据和仓库密码副本另外保管在两台工作电脑之外。接收电脑需要自己的私有密文目录。POSIX 下可用以下命令创建仅所有者可读的文件并输出 Admin 所需的两个指纹。Windows 上为同样三个文件设置仅所有者可读的 ACL。

```sh
umask 077
openssl rand -hex 32 > append.token
openssl rand -hex 32 > recovery.token
openssl rand -hex 32 > repository.key
node -e "for (const f of process.argv.slice(1)) console.log(f, require('node:crypto').createHash('sha256').update(require('node:fs').readFileSync(f,'utf8').trim()).digest('hex'))" append.token recovery.token
```

创建策略、指定仓库配额，然后从**部署标识**复制策略 ID。在每个参与的 Gateway 上保存以下私有 JSON 文件，把其绝对路径配置为 `HGW_PEER_BACKUP_CONFIG_FILE`。密文目录与暂存目录需互相独立，放在 Runtime 家目录、项目、Gateway 状态目录、部署备份及密钥目录之外。替换示例中的路径、地址和策略 ID。

```json
{
  "version": 1,
  "directory": "/srv/peer/encrypted",
  "stagingDirectory": "/srv/peer/staging",
  "resticExecutable": "/opt/restic/restic",
  "capacityBytes": 10737418240,
  "reserveBytes": 536870912,
  "maxExportBytes": 2147483648,
  "uploadKiBps": 2048,
  "downloadKiBps": 4096,
  "routes": [{
    "policyId": "11111111-1111-4111-8111-111111111111",
    "origin": "https://gateway.example",
    "appendTokenFile": "/secure/peer/append.token",
    "passwordFile": "/secure/peer/repository.key"
  }]
}
```

仅作接收端时，`routes` 填 `[]`。独立演练电脑使用同一仓库地址和策略 ID，并设置 `recoveryTokenFile` 与 `recoveryPasswordFile`。通过现有 Gateway 部署流程应用配置。Admin 会报告本机备份服务的配置状态。本地测试可使用数值回环地址的 HTTP。

## 查看保护状态

**已保护至**取最近一个持久确认恢复点的源端快照时间。重要数据的恢复点目标是 15 分钟，普通数据是一小时。断网、达到配额、缺少程序或上传未完成时，确认时间不会前移。下一次采集可复用传完的加密数据包。接收端同时检查单策略配额、仓库总容量、对象数和磁盘预留量。请预留上传、数据库日志和解压演练的临时空间。

`reserveBytes` 同时保护源端暂存目录和正在使用的原生快照卷。内置导出器在每批 SQL、每块文件和清单写入前检查可用空间；并发作业共用写入准入。在线和离线恢复演练的个人数据再次校验及重建副本继续使用同一准入。空间不足或无法读取时，仅停止备份、释放快照并删除其私有暂存文件，不停止 Runtime。个人 SQLite 投影需按最多三倍 `maxExportBytes` 准备临时容量；外部快照提供程序执行前需要具备其声明的完整 `maxExportBytes` 空间。这些检查不能替代文件系统配额：其他进程和原生快照的写时复制存储仍可独立消耗空间。请配置操作系统存储限制，未知插件覆盖继续标为不完整。

| 内置导出器 | 已包含 | 覆盖缺口 |
|---|---|---|
| 协作项目 | 在已发布的节点卷上，以一个可重复读事务导出工作区、对话、执行和项目记录 | 工作区、附件和插件文件需要同一修订的快照提供方。 |
| 个人 Runtime（默认导出器） | 已发布的目录、标签页草稿、限定范围的 PostgreSQL Session 和插件记录，以及已发布的账号文档记录 | 可选的原生文件快照补充文件覆盖。独立数据域水位与后台投递仍是缺口；未知插件状态和缺失来源另列缺口。 |
| 组织治理 | 已审核的管理身份、配额及用量、归属、名称 HMAC 材料和恢复证据 | 重建时凭据和权限全部停用。节点业务数据、模型连接、插件配置和外部凭据需要独立恢复或重新配置。版本 1–7 清单仍为部分覆盖。 |

部分恢复点可以还原表中列出的数据域。Admin 显示覆盖缺口、最近恢复点是否超过目标时限以及最近演练。部分恢复点也可能超期。接收 Gateway 独立测量策略配额、仓库的合计用量、可继续写入的对象数和磁盘保留量，即使策略未完成过备份也会报告。Admin 显示测量时间，接收端不再报告时会标明过期。过期测量不能作为剩余容量依据。有覆盖缺口或演练失败时，正式恢复预检会被阻止。维护备份沿用自己的保护范围与还原检查。

个人文件通过 `HGW_PEER_PERSONAL_SNAPSHOTS_FILE` 指向仅所有者可读的 JSON，保存 `version: 1`、`organizationId`、`nodeId`、`provider: "btrfs"|"vss"` 及 `runtimes` 数组。每项声明 `runtimeId`、`source`、`snapshotDirectory`、以 `{id,path}` 记录的获准工作区 `workspaces`；VSS 另需卷 GUID `volume`。声明的 Runtime 存储与账号的三个 UserDoc 根目录需在所选原生快照内。恢复只写入新的隔离目录。文件覆盖不能证明定时投递或跨数据库检查点已一致。默认个人导出器仍为部分覆盖。获准的 `snapshotExecutable` 可改为提供个人 Runtime 的一致快照，但必须由独立验证操作证明全部必检数据域；仅安装该程序不能证明恢复点完整。

## 轮换仓库

1. 在 **Admin → 部署** 中选择当前策略的**轮换仓库**，复制显示的新策略 ID。在源电脑配置该策略的追加凭据及加密密钥，在恢复端配置独立的恢复凭据及离线保管副本。保留原仓库期间需要具备完整的新仓库及 SQLite 日志所需的空间；原接收电脑余量不足时，另选一台已接入的接收电脑。
2. 提交轮换。组织数据库在同一事务中将采集切换到新策略，并将原仓库封存为只读。原恢复凭据仍可读原恢复点，已经批准的恢复操作沿用原策略版本。原追加凭据被撤销。重新配置或重试传输期间，原仓库中如有已经独立演练的点，仍可使用。
3. 按当前的新策略制作并独立演练一个完整恢复点。恢复点须覆盖相同范围、处于恢复点目标时限内，保护时间不得早于原仓库任一恢复点。此时 Admin 提供**审核仓库退役**。批准时要确认原仓库和明确保留的恢复点。仓库仍用于演练、未完成的恢复或其他待完成的退役时，暂不能退役。
4. 确认不再需要原仓库历史后，再批准永久退役。接收端根据服务中的部署授权撤销访问，再分批回收该仓库，重启后可继续。每批回收都要求保留点对应的策略维持启用，且版本与演练时一致。后续写入可复用 SQLite 释放的页。物理文件可能维持原来的大小，接收端仍要具备配置中的磁盘保留空间。异地副本遵循各自的保留规则。

Admin 标明退役是在等待回收、已经完成还是等待重新审核。接收端恢复连接后可以继续，维护期间暂停回收。保留点的策略被停用、版本变化或组织治理被重建后，要审核新的演练结果才能继续回收。历史授权和恢复点元数据继续保留用于审计。追加凭据和恢复凭据均无权退役仓库。

## 核验恢复

选择恢复点和另一台受管电脑，再点**开始隔离演练**。工作器核对磁盘余量，解密到新建私有目录，核验哈希、归属和逻辑顺序，保存结果并清理本次演练的明文。完整演练需要无缺口的恢复点。停用策略或轮换凭据可撤销后续网络访问；已离线保管的仓库密码仍能解密已取得的密文副本。

主入口和源电脑不可用时，在隔离恢复机使用接收仓库及离线保管的密码。在独立卷中准备一个空白私有恢复目录，把离线保管的组织、源电脑、接收电脑、策略和恢复点 UUID 填入仅所有者可读的 JSON 文件。从 `gateway/` 下执行构建后的 Gateway 入口。

```json
{
  "version": 1, "kind": "project",
  "organizationId": "<organization UUID>", "sourceNodeId": "<source UUID>",
  "targetNodeId": "<receiver UUID>", "policyId": "<policy UUID>", "pointId": "<point UUID>",
  "repositoryDirectory": "/recover/encrypted", "recoveryDirectory": "/isolated/new-drill",
  "passwordFile": "/escrow/repository.key", "resticExecutable": "/opt/restic/restic",
  "maxBytes": 2147483648, "maxRows": 2000000, "reserveBytes": 536870912, "timeoutMs": 3600000
}
```

```sh
node lib/peer-backup-rehearse-main.js /escrow/selected-point.json
```

命令在隔离目录重建并校验密文仓库，验证恢复内容，移除临时仓库，并输出所保留的明文路径、覆盖情况和耗时。检查期间限制访问，结束后清理本次私有演练。计划迁移的激活另需核验原写入端确已停止、分配独占的新写入代次，并重新取得桌面授权。租约到期或旧电脑失联不构成停止证明；故障恢复需要执行下述明确的物理隔离流程。

## 更换项目所在电脑

备份接收电脑与替代电脑可以是不同的受管电脑。原恢复点及其接收电脑保持不变。两台电脑都必须发布已安装的恢复协议能力并保持当前连接。替代电脑还需要已装配的相应项目或个人范围恢复工作器；接收电脑可以只提供密文存储。为演练和接管选择同一替代电脑，再选择其已登记数据卷。管理员创建且没有个人所有者的标准项目仍可恢复；恢复不会授予成员电脑使用权。此流程不包含 Steward 项目。

选择其他替代电脑时，在其私有策略路由中配置独立的 `recoveryTokenFile` 和离线保管的 `recoveryPasswordFile`，`origin` 指向原接收电脑。在**替代电脑的备份读取授权**中仅批准凭据指纹，并选择不超过备份 `timeoutMs` 的本地到期时间。授权绑定策略修订、恢复点、替代电脑身份及连接代次。重新连接、撤销、到期或策略变化后，需要新的审批及凭据，并在该替代电脑独立演练。仓库密码能够解密共享数据块的其他历史点：此授权限制平台操作，不构成单点密码学隔离。私有密钥与恢复暂存目录必须由获准管理员保管。

在 Admin 打开已发布项目的备份策略。选择无覆盖缺口的恢复点，在所选替代电脑上完成独立演练。该电脑登记了多个数据卷时，需明确选择目标卷。点击**准备替换电脑**，在新分配的工作区和 Runtime 目录解密数据。替换机重建本机 UserDoc 存储身份，核验保存的 Session 事件和定时投递回执。准备期间原电脑可以继续工作。

原 Runtime 已经停止后，选择**审核原机退出**。原电脑的 Gateway 必须确认同一进程代次已停止、文件操作和项目记录投递均已结束，并核对受保护文件和数据库水位仍与恢复点一致。文件发生变化时需要新的备份和演练。原机忙碌或失联、缺少定时回执、插件存储未覆盖、目标路径已被占用时，系统会阻止切换。原机封存前可以取消接管并继续使用。

定时历史沿用插件的保留策略。回执裁剪或明确删除任务不会删除已持久保存的 Session 消息，本身也不阻止恢复。保留的每条回执仍须对应已提交的消息；活动任务的待投递时间不晚于已有投递记录时，执行状态存在歧义，系统会阻止正式接管。恢复核验不会执行定时任务。

曾经封存本项目文件写入权的 Gateway 无法将自身确认为替换端。请选择其他满足条件的目标电脑，并保留原 Gateway 的退役记录。

原机封存后选择**审核切换**。主入口在一个事务中将现有 Runtime 和项目的归属更新至已核验的目标卷。替换机再次校验重建的文件，然后启用更高的写入代次。桌面控制需要重新授权。点击**刷新接管状态**查看结果，恢复的 Runtime 沿用正常授权和调度策略启动。

暂停策略或轮换凭据后，需按当前策略修订重新演练同一恢复点。**审核继续接管**确认该修订、原恢复点和既定目标，不会重新开放已封存的源端。常规配额及恢复点目标调整需等接管完成或取消。取消的候选需清理完成后，才能在该目标重新准备。

接管继续执行电脑使用权和项目权限。Admin 显示尚无目标电脑权限的成员数量。激活后，选择**为新电脑配置保护**，为该项目的新电脑建立策略。选择另一接收端、配置新凭据，并核对首个恢复点。原策略不会自动保护新源。

### 原电脑损坏后的数据恢复

在替换电脑演练完整恢复点后，才选择**故障恢复**。即使目标同时是备份接收机，也必须发布新版准备协议能力；旧版 worker 不能接收新的灾难准备。初始准备先在不连接源机的情况下验证恢复文件、支持的平台和已登记的目标卷。仅通过校验后才能确认隔离：先在云控制台或现场将原电脑断电或隔离，再记录证据引用，并确认恢复点后的数据缺口。确认绑定已审核的恢复点、策略修订、电脑、进程代次及写入代次，撤销整台原电脑的凭据和租约；同机其他项目需要分别审批恢复。当前主入口不能隔离自身，已隔离身份不能重新接入。

替换电脑不读取原机，从加密备份还原，在恢复后的私有副本中暂停定时任务，再核验实际文件及投递证据。原机停止和内容证明保持为空。**审核切换**发布更高写入代次，同时保留旧任务的执行隔离。目标激活后，**检查恢复后的运行配置**检查已停止的 Runtime，不启动或停止进程。核对已暂停组件后，批准**仅允许新对话**。恢复的历史对话可以读取，但不能恢复运行、接收消息或重放旧收件箱队列。新对话使用已审核的基础配置，继续执行电脑、项目、模型和插件权限。

对可审核的插件和外部连接逐项填写证据引用并批准。审批绑定安装文件与配置的摘要，要求 Runtime 停止后重新检查，不会重启正在运行的任务。无法检查的动态配置保持禁用。配置变更后，启动或重新加载前必须重新审核。将私有 `recovery-execution` 文件与节点数据一起保护：项目备份随所属内容加密这些文件，维护备份核验其不可变摘要。文件缺失或变化会阻止执行。

原电脑再次损坏时，可在更高写入代次上创建新的故障恢复并重新审核。计划迁移通过加密恢复点传递最初冻结的 Session 集合，并要求在目标电脑重新审核执行权限。之后正常创建的对话不会加入冻结集合。缺少源审核数据会在原写入端封存前阻止准备；插件和连接审批不会随迁移转移。日常升级保留既有策略，不使用故障恢复。返回单电脑模式后，部署页仍提供该电脑已发布项目的本机执行审核入口，不提供远程目标或新接管。此激活流程适用于协作项目。治理重建使用下方独立的离线流程。

### 更换个人空间所在电脑

完整原生个人恢复点使用 `native-personal-v3` 格式。其文件视图必须包含 Runtime 主目录、获准工作区、标签页草稿、目录 SQLite 数据及账号的全部文档根目录。已安装的 Session 读取器核验每个根对话和子对话的 JSONL 目录。个人 Session 仍存于 PostgreSQL、文件与 SQLite 快照相互独立、存在未知插件数据或 Session 路径平台不兼容时，会阻止正式激活。较早的部分恢复点仍可用于隔离检查。

在个人备份策略中先准备所选替代电脑及数据卷，再确认物理隔离。目标准备在私有副本中还原和检查，不影响源端任务。账号必须已具备目标电脑使用权限及可用 Runtime 配额。目标 Runtime 主目录或账号文档目录已被占用时拒绝替换，不覆盖或合并数据。目标电脑上同一账号的其他活动个人 Runtime，必须先通过正常管理流程安全停止。

源电脑隔离后，审批切换并等待目标发布。工作器只安装已经记录归属的目录，恢复文档身份，并在保留每个标签页身份的同时重新绑定目录和草稿坐标。原账号与 Runtime ID 不变。账号文档只迁移一次，同一账号和源电脑的另一个 Runtime 只能复用该目标上完全相同的文档检查点。恢复后的定时任务保持停用，所有旧 Session 保持只读。通过相同的逐项审核流程检查已停止的 Runtime，再批准新对话；检查不会停止现有任务。单电脑模式保留本机个人执行审核入口。发布时停用原电脑备份策略，需要为替换电脑另建保护策略。已核验但未发布的个人候选会阻止普通维护备份，因为尚未完成的物理安装不能作为可恢复文件快照。应先完成恢复，或在源隔离前取消，再重试该备份。

<a id="governance-rebuild"></a>

## 重建组织治理

`governance-rebuild-v1` 恢复点包含逐列审核的管理数据包。未知的表或列会阻止完整捕获。导出器排除业务正文和本地路径，保留账号、Runtime、项目身份及配额用量，并包含原有项目名称查重密钥。旧版本 1–7 治理清单只支持隔离检查，不能授权重建。

当前导出需要应用至迁移 146。替换电脑可以导入审核过的 Schema 135 至 146 所生成的 `governance-rebuild-v1` 恢复点，迁移校验值须与已安装序列的对应部分一致。重建后设备需要重新注册，投递结果从新通知开始记录。即使源库从未进入维护，导入也会将目标库保持在 `restoring` 模式。

物理隔离损坏的主入口并保留确认凭据。在替换电脑上先使用离线演练命令解密并验证恢复点。针对全新的 PostgreSQL 数据库运行 `node gateway/lib/governance-rebuild-main.js /private/governance-rebuild.json`。仅所有者可读的配置包含 `version: 1`、`action: "import"`、`databaseUrlFile`、演练返回的 `packageDirectory`、`bootstrapPasswordFile`、`operationId`、新的 `targetNodeId`、`targetNodeName`、原管理员的 `bootstrapUserId`、`isolationMethod`、`evidenceReference`、`acknowledgeDataLoss: true`、`maxBytes`、`maxRows` 和 `timeoutMs`。恢复点包含已登记查重密钥时还需提供 `projectNameKeyFile`。路径使用绝对路径，秘密值不进入命令参数。命令应用已安装的迁移，拒绝非空数据库，不启动任何服务。

导入先提交保持关闭准入的审核记录，再安装密钥文件。文件安装失败时，该记录继续保持关闭。修正仅所有者可读的目标位置，再以 `action: "install-name-keyring"` 和同一恢复点、操作及替换身份重试；该操作不重复导入数据，也不更改密码。在恢复和密钥安装完成前，保持已验证明文目录私有。不得生成替换的查重密钥材料。

在 `/admin/governance-recovery` 打开替换电脑的受限 Admin 入口。引导管理员使用新密码登录。审核账号和电脑，并确认明确列出的未恢复数据域后再放开。恢复的账号使用新密码和普通成员角色；放开只允许登录，原有电脑、项目、模型及插件授权继续停用。页面保留原授权记录，供现有 Admin 逐项重新配置。旧浏览器会话、节点凭据和接入码始终无效；电脑需要重新接入。

每个保留的 Runtime 还需单独绑定本地数据并审核执行。已有目录、本地索引身份、Session 代次与实际监督进程停止证据必须一致。监督状态未知或忙碌时阻止检查，不停止它们。组织审核放开后，在所属电脑打开 `/admin/governance-recovery/local`，选择非标准路径并审核该电脑的执行。此页要求当前管理员资格和本机使用权，不提供组织账号、远程电脑或放开入口操作。绑定前从旧 Runtime 的 `.env` 中移除继承的 `HGW_`、`DSH_`、libpq 和 `DATABASE_URL` 键；所需设置改由当前节点部署或经审核的插件配置提供。仅替换旧文件中的值仍不满足要求。诊断仅显示键名。绑定不创建空的替代目录，也不更改既有 Session 字节。Runtime 准备、模型和目录权限、个人文档、个人快照和维护文件采集核验同一组私有位置；绑定证据不可用时拒绝访问或认证，不改选默认目录。手动检查失败后需重新提交所选目录；后台工作进程不能将它替换成标准路径。获准的新对话使用精确绑定的目录；所有旧根会话、子会话、待执行工作和定时工作仍暂停。插件和外部连接需重新审核代码及配置。节点私有绑定和执行记录应进入该节点的加密备份，不进入组织清单。

之后计划迁移项目时，传递当前治理恢复冻结的 Session 集合，并在目标重新审核组件。目标必须证明已读取移交的私有策略，才允许批准源端退休；缺少该证明的旧版工作进程不能推进迁移。项目写入代次和 Runtime 进程代次分别核验。

经验证的 schema 135 重建包在核验原迁移校验和及精确字段清单后，可以导入 schema 136。既有恢复操作保留原接收电脑；尚无目标证明的未完成灾难准备需要重新验证目标。临时读取审批与协议心跳不会恢复，也不会重新开放原准入。

<a id="providers"></a>

## 快照提供方

在 Linux 上，`HGW_PEER_PROJECT_SNAPSHOTS_FILE` 指向仅所有者可读的 JSON 文件，保存 `version: 1`、组织和电脑 UUID、`provider: "btrfs"` 及 `projects` 数组。每条记录包含项目 UUID、源子卷 `subvolume` 和位于同一 Btrfs 文件系统的独立 `snapshotDirectory`。Gateway 需要在这些明确位置创建和释放只读快照的能力。工作区、Runtime 声明的存储、Gateway 的 UserDoc 元数据与保留对象目录都应位于源子卷中。出现未分类的数据或嵌套子卷时，将不能生成完整恢复点。Windows 和 macOS 接收机可以独立于源端快照提供方核验加密恢复点。Windows 源机使用专用 NTFS 数据卷和 VSS 提供方。Mac 源机需要检查专用 APFS 卷，并配置面向该项目的快照服务。详见[节点存储配置](../../deploy/node-content/README.zh.md)。

每条私有路由可设置 `snapshotExecutable` 来提供一致的文件和数据库版本，并对相应数据域做独立语义验证。在恢复机的还原数据目录之外安装同一受信任的提供方。三个独立参数依次是 `capture|validate`、私有请求文件路径和数据暂存路径。请求含范围标识、字节和行数限制、必检数据域，验证时另含已封存的采集说明。两种操作均无浏览器凭据。

个人 Runtime 的必检数据域为 `directory`、`drafts`、`sessions`、`files`、`document-references`、`plugins` 和 `background-delivery`。提供方必须保留准确的账号、电脑、Runtime、草稿标签页身份及不可变 Session 代次，核对定时投递回执与持久化 Session 消息、验证引用的文件字节，并将未知插件数据列为缺口。共享文件系统快照必须包含其声称覆盖的全部文件和 SQLite 数据域；独立 PostgreSQL 快照需要稳定的限定范围水位，或其他经过证明的协调机制。时间戳一致或复制了 `storages` 文件均不能构成该证明。采集和验证不得停止在跑任务或执行恢复的定时任务。

采集返回版本、组织、源电脑、范围、写入代次、水位、UTC 快照时间、已覆盖数量及明确缺口。验证返回 `{"version":1,"checked":[…]}`。每个必检数据域都要通过验证，或记录对应的 `domain:reason` 缺口。需保留不可变 Session 代次、将附件引用核验到实际字节，并在不执行定时任务的情况下核对投递回执。受保护文件清单应排除快照程序与托管密钥。字段定义见[提供方实现](../../src/peer-backup-snapshot-owner.ts)。

个人和项目故障恢复会在目标副本中暂停旧 `HGW_*`、`DSH_*`、libpq 连接设置及 `DATABASE_URL`。Admin 只显示受影响的设置名称，供管理员按目标电脑明确重新配置；源加密恢复点保留原值。业务环境设置保持不变。普通升级和计划迁移保留其当前环境。

## 开发说明

组织库迁移 109、115、119、120、130–136 保存策略指纹、恢复点、审批、原写入端封存、清理确认、灾难隔离及执行审核。节点迁移 012 和 016 保存封存、替换及暂存归属凭证。治理清单版本 7 包含审核摘要、审批、计划迁移凭证、电脑权限、配额、归属、名称 HMAC 标识及不含正文的审计字段；版本 1–6 仍可作为部分清单读取。Session 标识与配置正文保存在节点私有策略文件中，不进入治理清单。所有清单均不恢复凭据。详见[恢复决策](../../../.agents/notes/implemented/architecture/2026-11-05-project-recovery-reauthorization.zh.md)。[接收端](../../src/peer-backup-repository.ts)拥有只可追加的密文仓库。[演练命令](../../src/peer-backup-rehearse-main.ts)在不连接源电脑或组织治理库的情况下核验指定恢复点。

[双机离线演练](../../tests/run-peer-backup-os-pair.py)会先删除合成源、关闭两条转发通道，再从接收仓库恢复。[在线更换写入电脑用例](../../tests/run-peer-backup-online.py)使用独立测试数据库和 Windows 专用测试磁盘。原电脑保持在线，以便出具已停止写入的凭证。端到端计时涵盖准入、传输、演练、审批、启用及一次定时投递。离线 restic 计时只覆盖解密和还原到私有检查目录。

`node gateway/tests/run-node-content-postgres.mjs --disaster-ui` 通过回环 HTTP 和独立测试 PostgreSQL 数据库验证真实 Admin 恢复组件。运行需要 Web 测试工作区的 Playwright 和 Chromium；可用 `HGW_TEST_PG_BINDIR` 指定私有 PostgreSQL 程序目录。用例登记的恢复点为合成数据，因此只证明审批、过期输入拒绝和执行隔离，不证明物理停机或数据还原。用例回放桌面和手机的 ARIA 快照；使用 `DSH_SNAPSHOT=refresh` 更新预期输出。
