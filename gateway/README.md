# harness-gateway

English | [中文](README.zh.md)

The public-facing portal gateway for DeepSeek Harness: PostgreSQL-backed login/session handling, user/project/directory grants, HTTP+WS reverse proxy (rewriting Host/Origin to the instance loopback address), personal and shared-project dsh runtime lifecycle, the `/admin` SPA plus `/admin/api` JSON, collaborative conversations, model governance, usage accounting, and auditing. Design and staged plan: [design doc](../.agents/superpowers/specs/2026-08-14-user-directory-permission-gateway-design.md), [Phase 1 plan](../.agents/superpowers/plans/2026-08-14-gateway-phase1.md), [project-centric admin](../.agents/superpowers/specs/2026-08-14-project-centric-admin-design.md).

## Toolchain

- **Node 25** (`.nvmrc`; the dsh repository's engines `^22.19 || >=24` accept it). `better-sqlite3` and `argon2` are native modules whose ABI binds to the Node major that installed them — after switching Node, run `npm rebuild better-sqlite3 argon2`, otherwise they fail with a `NODE_MODULE_VERSION` mismatch.
- Commands: `npm run dev` (tsx source entry), `npm run build` (compiled `lib/index.js` production entry), `npm test` (unit tests), `npm run typecheck`. `HGW_TEST_DATABASE_URL` selects a disposable database for `npm run test:postgres`; its PostgreSQL suites run serially and replace the `harness` schema. CI runs both test commands.
- Managed execution: from the repository root, set `HGW_TEST_DATABASE_URL` to a disposable PostgreSQL database and run `pnpm run test:gateway:execution`. It requires workspace and Gateway runtime dependencies, runs the real Loader and HTTP authorization without a model API key, and joins the existing CI consumer job for Gateway-related changes.

`npm run build` emits the Gateway source graph under `lib/` with relative imports rewritten to `.js`; production supervisors must execute `node lib/index.js` from the same release directory. The source `tsx` entry is for development and tests only.

## Admin console and project grants

`/admin` serves the Vite SPA built from `gateway/admin-ui` into `gateway/public/admin`; `/admin/api/*` is the gateway JSON API (non-`admin` role 403). Administrator-origin projects have two creation modes: **Managed directory** submits only a name and creates or reuses `<HGW_PROJECTS_ROOT>/<name>` with mode `0770`; **Existing directory** submits a name plus a directory selected from the Gateway host. User-origin projects remain name-only and allocate one directory below `HGW_USER_PROJECTS_ROOT`. Both origins use the same workspace, shared runtime, membership, and conversation model. User-created projects make their creator the `rw` owner and expose invitation lifecycle operations; administrators can inspect both origins through one list and filter by origin.

`GET /admin/api/project-directories` backs the existing-directory browser. Local launcher mode starts at `/`, so macOS external disks appear below `/Volumes`; systemd mode shows a virtual root containing only `HGW_PROJECT_PATH_ROOTS`, and configured roots themselves are navigation-only. Each response contains one sorted level and at most 1,000 directories; hidden directories carry a marker and stay hidden in the UI until enabled. Canonical symlinks that leave a systemd root are omitted. The browser never reads the administrator's client filesystem. Final project creation resolves and validates the selected path again, rejecting non-absolute, missing, non-directory, inaccessible, outside-root, Gateway-owned/reserved, user-home, and existing-project-overlap paths with stable diagnostics. Managed names are trimmed and must form exactly one directory segment, so `.`/`..`, separators, control characters, and symlink-resolved escapes are rejected. Project rename changes only the catalog name, and project deletion retains host files.

Members have `ro` or `rw`, and each regular user's effective list (private home plus memberships, each with a `label`) is written to `$DSH_HOME/directory-grants.json`. Administrators receive one `rw` grant for the filesystem root and the Full access preset in personal and project scopes. The preset changes dsh's in-app sandbox and approval knobs only; a project runtime remains kernel-confined to its project path. A role change rewrites this projection and restarts a running personal instance. User deletion is logical: it stops the personal instance, releases its operational port assignment, revokes sessions, removes project and model access, hides the account from login and admin lists, and retains audit, usage, conversation, and home history; the username stays reserved.

The admin console uses one visual system across Users, Projects, Models, Usage, and Audit: a restrained surface palette, shared page and section headers, status badges, shared metric cards, explicit loading/empty/error states, keyboard focus rings, and modal forms for mutating operations. Project detail includes membership, instance state, effective per-route model authorization with assign-all and clear-all, the project default-following mode and model-specific exceptions, natural-month token/cost/missing-usage totals, a quota dialog that defaults to project-independent Token and company-cost limits with an option to inherit the ordinary-member quota, and a configuration summary of quota source, path, origin, owner, members, and effective models. Personal Provider and model registration uses visible labels, an explicit `YYYY-MM-DD` date format, and apply/reset actions, so draft edits do not issue a request for every keystroke and invalid dates fail before a request. At viewports wider than `840px`, navigation is a fixed sidebar and data tables remain comparison-oriented; at `840px` and below, the sidebar becomes a sticky brand header plus a seven-item fixed bottom navigation, table rows switch to readable cards, and the Models view control stays on one row. At `560px` and below, form grids stack, actions fill the available width, and dialogs use nearly the full viewport with an independently scrollable body. Coarse-pointer controls reserve a `44px` target, while dark color-scheme and reduced-motion preferences are honored. After changing the UI, rebuild the static assets with `npm run build --prefix gateway/admin-ui`; the running gateway serves the generated `gateway/public/admin` files without a database migration.

Project logic settings use a separate ownership path from server resources. `/account/api/preferences` stores language, theme, and busy-Enter choices per account, including while a project is active. `/account/api/projects/:id/configuration` exposes the project theme policy and capability flags; project owners and organization administrators may update it. `/account/api/projects/:id/model-settings` and its credential/discovery subroutes manage project-owned Provider profiles through encrypted PostgreSQL rows and a revision fence. The user-facing project settings panel is read-only for other members but still explains each owner boundary. `/admin` only summarizes these settings and links into the selected project scope; directory paths, mounts, lifecycle, quotas, and organization model authorization remain administrator operations.

The Admin **Archives** channel lists organization-wide root conversations from the Gateway archive index. It filters by state, title/body/Session ID, user, and project; opens a paged chat-oriented reader that keeps full events in collapsible technical details; exports JSON; and supports confirmed batch restore, trash, and purge actions. Personal transcripts remain in their owning runtime and are loaded on demand; project transcripts use PostgreSQL. Every read, export, and mutation is audited without copying message text into the audit row. Runtime archive snapshots carry a revision and are reconciled after offline Admin actions.

## Plugin management

`/admin/plugins` selects an existing runtime on the current node and adapts the upstream manager workflow for package inspection, installation, script approval, cancellation, enablement and removal. Node and generation mismatches require reloading the selection. The page does not start stopped instances. Installation output stays in the administrator request; transport loss is an unconfirmed outcome, never an automatic retry. Registered non-account settings appear as configuration cards backed by the existing settings owner. Forms show resolved and inherited values, ownership and restart requirements; they send only edited paths with the held revision. Secrets require an explicit retain, replace or unset choice and are never read back. A conflict preserves the draft until the administrator discards it and reads the current value. Account preferences stay in account settings. Explicit authority loss clears the private workflow and logs; an old target’s late response cannot invalidate its successor.

A clean Admin checkout needs the locked root and Admin dependencies. Run `npm run prepare:remotes --prefix gateway/admin-ui` before its standalone tests or build; a complete root build already emits those two codecs. Browser gates build Admin assets after the shared runtime build and compare the [regional installation golden](../apps/web/tests/plugin-administration.e2e.ts) through real Gateway routes.

## User terminals

The **Terminals** page in `/admin` controls revisioned user and project qualification. Personal terminals require user qualification; project terminals also require project authorization and writable membership. Session access remains independently checked. Qualification revocation stops retained processes and waits for cleanup; Agent permission selection and Auto eligibility do not grant terminal access.

Select a user or project to list terminal identities, Sessions, creators and process states on the current node. Reading inventory does not start an idle runtime. Administrators can explicitly close a reviewed entry but cannot read terminal output or send input. Closing binds the node and runtime generation; a restart requires fresh inventory. Cleanup failure remains visible for refresh and retry. The [terminal controller](../packages/api/terminal-controller/README.md) owns process lifetime and browser recovery.

## Android shell and completion notifications

`apps/android-shell` is a Capacitor shell that loads the deployed Web UI through `DSH_ANDROID_WEB_URL`. Publish ordinary Web UI changes to the Gateway without rebuilding the APK. Re-run `pnpm --dir apps/android-shell run cap:sync` and rebuild only when the native project, permissions, package id, icons, or notification handling changes. The package id is `com.coharness`.

The shell can register FCM and JPush independently. FCM requires the Firebase client file at `apps/android-shell/android/app/google-services.json`; the Gateway needs `HGW_FCM_PROJECT_ID` and an owner-private `HGW_FCM_SERVICE_ACCOUNT_FILE`. JPush uses the Android JPush AppKey supplied through `JPUSH_APPKEY` (a Gradle property or environment variable) and the Gateway pair `HGW_JPUSH_APP_KEY` / `HGW_JPUSH_MASTER_SECRET`. The JPush RegistrationID is stored with provider `jpush`, while existing clients without a provider remain `fcm`. Huawei and other domestic vendor channels are optional Gradle integrations; Huawei additionally requires `agconnect-services.json` and `JPUSH_ENABLE_HUAWEI=true`. Do not commit any AppKey, secret, Firebase service-account JSON, or vendor configuration file.

The Gateway stores Android tokens per authenticated user and sends a small creator-scoped notification only after a durable completed turn; the notification contains a session id and opens the existing Web UI rather than exposing reply text. PostgreSQL migration 010 adds provider-aware token uniqueness; normal Gateway startup applies it.

Push-provider error bodies are read through a 64 KiB budget before token-error classification, so an unhealthy provider cannot retain an unbounded diagnostic response.

## Project collaborative conversations

Local `stopAll()` workers continue draining tracked runtimes after per-target failures; each rejects with its own first error after draining. `Promise.allSettled` waits for all workers, then reports the first rejected worker in array order, not the globally earliest error. systemd shutdown remains a no-op; local exit force cleanup and the external shutdown deadline are unchanged, so deadline expiry can interrupt draining ([decision](../.agents/notes/implemented/bug-fix/2026-09-17-stop-all-worker-failures.md)).

An account runs in either personal scope or one accessible project scope. Personal scope retains its per-user runtime and persistence; every project uses one shared runtime over the project path. The scope-selection endpoint starts and awaits the target runtime before it stores the new scope cookie, so a failed start preserves the current scope and a successful reload reaches a ready process. Proxy retry responses are non-cacheable and advertise a two-second retry; the HTML waiting page places its automatic refresh metadata in the document head. The Gateway signs a short-lived request principal for the selected runtime and forwards it on every proxied HTTP/WebSocket operation. Long HTTP/WebSocket work holds a serialized runtime lease; idle reaping rechecks lease admission, and a stop that wins the race causes a fresh-generation retry instead of forwarding a stale port. The runtime verifies organization, user, scope, runtime id, and generation before Host code can observe the request. Private runtime credentials and collaboration endpoints remain loopback-only. The complete decision is recorded in [project collaborative conversations](../.agents/notes/implemented/feature/2026-08-15-project-collaborative-conversations.md).
The account workbench additionally exposes `/account/api/workbench/catalog`, which returns personal and membership-allowed project conversation metadata without transcript content. If the personal runtime is temporarily unavailable, the Gateway still returns the ACL-filtered account rows it has, so a personal startup failure does not hide project conversations. Browser API and WebSocket requests may carry a `dshTarget` selector; the Gateway validates that selector against the authenticated membership before resolving the target runtime and signing its principal. This keeps concurrent panes on separate runtime connections while preserving the same ACL, sandbox, and approval checks.

Project members are `ro` or `rw`. Organization administrators have implicit `rw` authority over every active project and every project conversation, including private roots, without a project-membership row. The administrator-only `danger-full-access` preset is available in every personal or project scope after request identity is verified; ordinary users cannot select it through either `/permission` or a new-session default. In a shared project session, permission events are session-global, so an administrator changing the preset changes the in-app preset seen by all participants until another authorized selection; the systemd project unit still limits host access to the project path. For ordinary members, root conversations choose project-visible or creator-private access, and descendants inherit the root ACL. Host operations authorize reads, writes, management, forks, streams, approvals, and questions; PostgreSQL admits only one response to each shared approval/question. Project runtimes store Session headers and complete events through the Gateway PostgreSQL provider, whose write and read decoders require exact event-envelope fields and surface metadata before data enters a live Session. Durable participant metadata lets the model and transcript distinguish contributors. The Web plugin exposes scope, visibility, creator, participants, and contribution counts, and replaces the complete composer for `ro` members; the browser is not the authorization boundary.

Auto review eligibility is a separate administrator grant on each user (`autoReviewEligible`), initially false for both users and administrators. The user list and edit dialog expose this grant in desktop and mobile layouts. Only administrators can change it through `/admin/api/users/:id` PATCH, with a strict boolean, audit record, and access invalidation across Gateways. Granting eligibility does not activate Auto, change a current Session, or change future-session permission defaults; project access continues to use the existing membership and conversation ACLs. See [administrator-owned eligibility](../.agents/notes/implemented/bug-fix/2026-09-22-admin-auto-review-eligibility.md).

Desktop qualification is separate from Auto and model permissions. The Desktop coordination page edits user and project grants through `/admin/api/desktops/permissions`; unconfigured grants are false. Saves carry a revision and reject concurrent overwrites. The execution `desktop` capability requires every verified actor to be qualified and, in a project, requires the project grant and writable membership even for administrators. Changes publish through the access outbox. A runtime carries a desktop driver only when the node declares an interactive desktop through `HGW_DESKTOP_ID`: the launch composition then mounts the computer-use service and the provisioned Cua Driver MCP provider, and the configured [execution provider](../packages/context/gateway-execution/README.md) publishes the managed policy that owns driver admission. Qualification alone supplies neither root-Session confirmation nor a desktop lease.

Live-root desktop confirmation is recorded separately for the authenticated user, current node, runtime generation and exact desktop. Migration 033 binds it to the current user and project qualification revisions. Withdrawing confirmation publishes access invalidation; revoking and regranting qualification requires a new confirmation. Private execution APIs reject caller-supplied actors and nodes. Desktop grant ownership binds the authenticated runtime generation and actual live root. Verified children share that root; another root cannot renew, release or confirm its lease stopped. Coordination derives its node and actors on the server without reusing a browser assertion. After revocation, exact-owner cleanup remains available, while acquisition, status and renewal require current qualification and confirmation.

Execution authorization uses PostgreSQL records of exact authenticated message inputs and question answers. Receipt IDs prove origin, not permission; participant metadata and caller-supplied roles cannot grant authority. Edits retain earlier actors, and Session actor sets only grow across steps and adjacent parent/child exchanges. Each authorization checks every actor's current account and Session write access; plugin management additionally requires every actor to be an administrator, and Auto requires every actor's eligibility grant. Unknown historical input permanently denies those privileged capabilities while ordinary execution still requires a verified writable actor. Explicit mode selection checks the selector and existing actors without adding an actor. Personal transcripts remain in JSONL; registering their runtime-scoped lineage grants no authority.

The private execution API returns a monotonic decimal `revision` with its compact witness set and primary actor. Its `capture` operation reads those facts after revocation without granting execution. Empty legacy inheritance requires explicit unknown history and an actually empty sender set; it cannot omit recorded actors. Replaying a consumed input, initial inheritance, or receiver message does not reset later attribution. Parent/child transfers retain the captured primary actor after verifying membership in the selected origin records; later sender inputs cannot change that attribution.

Runtime watch connections receive `ready`, invalidation hints, and configured heartbeat frames; close or backpressure releases the subscription and timer. Losing the database listener closes these streams. New watches receive `503` until the monitor reconnects, catches up, and settles pending local cancellation. A watch notification is not proof that remote tasks have stopped; the runtime owns cancellation and fresh authorization.

Session ACL checks query current membership on every operation. Scope-only Host operations use the signed mode for at most `HGW_PRINCIPAL_ASSERTION_TTL_MS` (30 seconds by default), and long-lived streams disconnect at principal expiry. Deleting a project stops its shared runtime inside the runtime's serialized operation slot before PostgreSQL cascades project-owned runtime and collaboration records; the project directory remains on disk.

After a committed logout, password or account-authority change, project membership change, visibility change, or project deletion, the serving Gateway closes matching in-flight generic proxy responses and WebSockets. Other targets stay connected. This registry belongs to one Gateway process; changes made through another Gateway process or directly in the database are rechecked on operations and principal renewal, not broadcast by this registry.

The document broker uses the same runtime identity and membership authority for cross-scope copies. It streams a source document between personal and project runtime HTTP endpoints, never through the browser, applies target collision naming, returns safe per-file results, and writes source identity to the durable audit log. Project-to-project copies and live synchronization are not part of the version-1 protocol. Runtime JSON responses and streamed bodies are bounded by `HGW_UPSTREAM_RESPONSE_LIMIT_BYTES`; proxy operations and document metadata/lifecycle requests are bounded by `HGW_UPSTREAM_TIMEOUT_MS`. A stalled document request returns `DOCUMENT_SCOPE_TIMEOUT` with HTTP 504 and releases its runtime lease; a successful content stream keeps the lease until EOF or cancellation and is not cut off by the metadata deadline. Metadata-only transfer plans expire after five minutes and are bounded by process (10,000 plans/128 MiB), organization (2,000 plans/32 MiB), and actor (100 plans/8 MiB) count and serialized-byte budgets; consuming or expiring a plan releases all three counters.

The browser-facing `POST /api/documents/transfer/list` route is owned by the Gateway rather than the generic runtime proxy. The Gateway performs the scope check and asks the selected target runtime for metadata, so a runtime start failure is an authenticated JSON error and cannot redirect a browser to a loopback runtime port. Readiness is proved with a one-time nonce and an HMAC derived from the runtime bearer token and identity, rather than by accepting any HTTP response on the port. As a final proxy safeguard, loopback `Location` headers from other upstream responses are converted to same-origin paths before they reach the public response.

The Gateway also owns the target-scope resumable upload route under `/api/documents/transfer/uploads`. The browser supplies a compact personal or project scope key on every session, chunk, status, completion, and cancellation request. Gateway authorization is repeated for every request, and chunk bodies are streamed to the selected runtime without exposing its port or filesystem path.

## Model governance and usage accounting

The admin SPA has **Models** and **Usage** pages. Models are identified by exact `(provider, model)` routes. The governance catalog is the sole authorization source for every role — the former `defaultAllowed` bypass for administrators has been removed. A per-route role default (`admin` / `member`), per-user `allow` / `deny` / `inherit` exceptions, and a global enabled flag determine the effective policy for catalog routes. New projects start with a project-level default that authorizes every currently available organization-managed model; newly added catalog models follow that default until an administrator clears the project or records a model-specific denial. Existing projects retain their stored mode. Routes absent from the catalog are denied for all roles; in a personal runtime, a route the user declared in their own settings layer (BYOK, bring your own key) is additionally authorized with personal-cost attribution and no catalog price, while project runtimes remain catalog-only. A policy projection also writes the first authorized, enabled organization route as the composition default in the runtime home patch; a user-layer `agent-default-model` selection remains higher precedence. A policy change atomically rewrites `$DSH_HOME/model-governance.json` (mode `0600`); a running instance watches that file and applies the validated policy without a restart, while an invalid live document fails closed for new model requests. The instance plugin provides `ctx.modelAccess`; `apiproxy` filters catalogs and rejects selection/prompt RPCs, while the `llm/stream` middleware is the final adapter-dispatch enforcement point for chat, title, compaction, and direct calls.

Bulk policy projections use bounded workers over the user and project rows already returned by the catalog queries. A transient file or credential failure schedules a retry, while a runtime's lazy revision check keeps its next request aligned with the durable policy.

Document-catalog reconciliation validates the complete metadata request before writing and applies a removal list in one scoped transaction when the PostgreSQL batch method is available; compatibility providers retain the per-document fallback.

The policy projection version cache retains at most 10,000 recent subject/path entries; eviction only causes a later safe rewrite.

## PostgreSQL control plane

Administrators register webhook endpoints through the Admin UI or `/admin/api/webhook-endpoints` (`POST`, `POST …/update`, `POST …/mutate` with `enable`/`disable`/`remove`). New endpoints are disabled and answer intake with 404 until an administrator enables one explicitly. Each endpoint binds a provider (`github`), a write-only signing secret encrypted under `HGW_WEBHOOK_SECRET_KEY_FILE`, an execution account, a user or project runtime target, event/action filters, a structured repository filter of `owner/repo` full names matched case-insensitively against the payload's `repository.full_name`, `{{path}}` title and prompt templates, and intake limits. Providers POST to the public `POST /webhook/<endpointId>` route; the signature is verified against the stored secret, the body is deduplicated durably, and accepted deliveries are dispatched to the bound runtime's managed `webhook-dispatch` route, which admits one Session per delivery. Administrators can query `/admin/api/webhook-deliveries?endpointId=<uuid>` with optional `cursor` and `limit` (1–100, default 50). The response contains bounded delivery receipts without event payloads or secrets. `submitted` means prompt admission, not Agent success; `ignored` means a configured event, action, or repository filter excluded the delivery, and the receipt's error code names the unmatched rule; `unknown` prevents automatic redispatch. A settled receipt can be replayed by an administrator through `POST /admin/api/webhook-deliveries/redispatch`, which records a new audited receipt under the endpoint's current configuration. The reservation service takes separate intake and body-replay windows. Equal bodies inside the replay window share a receipt across nodes, and all observed delivery ids remain bound to that receipt after expiry. Dispatching or unknown results continue to block automatic repeats outside the window.

A pinned PostgreSQL 17 deployment lives in [`deploy/postgres/`](deploy/postgres/README.md). The Gateway entry point applies its immutable migrations and refuses to listen unless the configured active organization and compute node resolve. Authentication, users, account preferences, projects, personal/project instances, shared project conversations, collaboration claims, audit, model governance, project Provider profiles and encrypted credentials, quotas, and usage are PostgreSQL-backed. Internal UUIDs preserve organization foreign keys while numeric public IDs keep the existing HTTP API stable. SQLite remains only as the accepted source of a stopped-writes final import and rollback backup; the running Gateway never opens it.

Every call produces one UUID-keyed usage record in a crash-safe per-runtime outbox. The loopback intake deduplicates UUIDs in PostgreSQL, applies the price version effective at the call timestamp, and attributes company cost from a non-secret credential source label (`file`/`project-env`/`request` are personal; launch environment sources are company; unknown remains company-conservative). No API key, prompt, or response content enters the ledger. Natural months use `HGW_USAGE_TIME_ZONE`; token and company-cost quotas support role defaults, per-user inherit/unlimited/custom overrides, and project inherit-or-explicit limits. Quotas warn at 80% and 100% but do not block calls. Billing ownership remains exactly one user or project; shared-project records additionally retain a verified participant id when available for non-billing activity reports. Historical project records without that fact remain unattributed. Users see durable crossings in the Web shell; admins see separate personal, project, and contributor summaries, missing-usage counts, and explicit price-coverage status.
The Admin usage API keeps the legacy subject summary and adds `/admin/api/usage/overview`, `/admin/api/usage/contributors`, and `/admin/api/usage/health`; contributor rows are activity projections and are never added to project billing totals. Archived identities remain in the overview so historical personal usage and confirmed project activity continue to reconcile with their subject totals.
Personal settings changes use the same authenticated outbox with a `model-registration` record type. The Gateway stores Provider/model creation, modification, and deletion separately from usage and exposes them through the administrator Models page; records contain route identities and timestamps only.

## Deployment maintenance and coordinated restore

Upgrades and restores run as controlled operations instead of relying on startup migration or the `deploy/postgres` shell scripts alone. `harness.cluster_control` holds one organization row: the mode (`serving`/`maintenance`/`restoring`), the maintenance epoch nodes must acknowledge, the write epoch that fences stale writers, and the operator reason. `harness.deployment_operations` is the operation ledger; `harness.backup_records` registers each dump with its managed-file manifest, verification state, and the write epoch it was taken under. Each compute node reports its applied maintenance epoch on `maintenance_applied_epoch`; a node with a fresh heartbeat that has not acknowledged the current epoch counts as an active writer, while a node declared `offline` is excluded — and returns to `active` if it keeps heartbeating.

While maintenance is open the Gateway rejects mutating HTTP and runtime calls with 503 (`maintenance`), and after a restore the bumped write epoch rejects every process started before it (`stale-epoch`). Administrators drive the window from the Admin Deployment page or `/admin/api/deployment*` (cluster state, maintenance enter/exit, node drain, restore requests, backup create/list/verify); state-changing requests are audited. The standalone applier `pnpm pg:deploy <status|maintenance enter|maintenance exit|apply|backup|restore|restart-plan>` (`scripts/deploy-apply.ts`) runs the sanctioned sequence outside the serving process: it claims pending admin restore requests, waits for writer quiescence, applies migrations under the window, dumps the database plus a managed-file snapshot (principal keys, runtime credentials, governance and webhook keys, bootstrap password file), verifies the dump and every manifest digest before restoring files atomically, and prints the rolling restart order. `HGW_PGDUMP_COMMAND`/`HGW_PGRESTORE_COMMAND` configure the pg client command lines — including `docker exec` forms — and `HGW_BACKUP_DIR` selects the artifact directory. A dump restore rewinds the cluster control row, so the applier re-asserts the restoring window before completing; `completeRestore` then advances the write epoch monotonically so writers baselined before the restore fence themselves out.

## Access revocation across Gateways

Committed changes to existing account, project, conversation, archive, and document access invalidate affected proxied HTTP responses and WebSockets on every Gateway in the organization. New requests catch up with the durable access records and recheck login and project authority after runtime admission. Directory-grant changes also stop affected local runtimes so their next start receives current grants. New Session/document registration, message appends, statistics, and sliding login expiry do not invalidate traffic.

A lost PostgreSQL listener closes admitted proxy traffic. Reconnection waits for cancellation and reads missed records before admitting more traffic; signed-principal expiry is an additional limit. A cold Gateway resumes its compute node's successfully applied runtime revision; an existing process keeps its own cursor across reconnects. Keep the `access.invalidate` records in `harness.outbox`, including records with `completed_at` set: they are a replay history, not a deletable work queue. Missing revisions fail readiness and proxy admission. The [decision record](../.agents/notes/implemented/architecture/2026-09-22-cross-gateway-access-invalidation.md) explains transaction ordering, retention, and cost.

Runtime event streams recheck Session visibility for each publication batch. Clearing content already held by the browser remains a separate Client responsibility. Closing a participant's transport does not establish that participant's existing model/tool tasks have stopped inside a shared project runtime; participant-owned task cancellation needs independent verification.

Selected-scope document downloads subscribe to the same access monitor before authorization and remain subscribed through response consumption and runtime-lease release. Revocation stops subsequent bytes; it cannot retract bytes already delivered. Slow runtime shutdown does not delay the download's cancellation. Cleanup failure is reported and blocks acknowledgment rather than being treated as successful release. Ordinary metadata and upload registration do not acquire a download cancellation subscription.

## Layered directory enforcement

The gateway only authenticates and orchestrates; regular-user directory access is enforced by the Linux production systemd mount namespace and the [dsh-directory-guard](../plugins/dsh-directory-guard/README.md) plugin loaded inside every instance. Regular units mask the users root, project-runtime root, configured project roots, and Gateway-owned credential paths before re-binding only the runtime home, `$DSH_HOME`, and authorized project directories; `ProtectSystem=strict`, `ProtectHome=tmpfs`, and removal of `CAP_SYS_ADMIN` apply across the process tree. The home patch also replaces the host OS directory chooser with the in-app browser, which lists grant roots and refuses paths outside them. Administrators retain the same plugin composition but receive a filesystem-root grant and the Full access preset; their systemd unit removes the regular directory masks and read-only system/home settings while retaining the non-root runtime account, `NoNewPrivileges`, the capability restriction, and the Gateway-directory exclusion. Shared project units run under `HGW_PROJECT_RUNTIME_USER`, bind only the project path and their private `$DSH_HOME`, and expose credential settings read-only. The managed user-project root must inherit group access for `HGW_PROJECT_RUNTIME_USER` (for example a setgid `2770` root owned by `harness-project`, or an equivalent default ACL), otherwise a newly allocated directory cannot be opened by its project unit. On macOS there is no systemd mount namespace, so regular-user and shared-project process-wide confinement remains a development limitation.
