# harness-gateway

English | [中文](README.zh.md)

The public-facing portal gateway for DeepSeek Harness: PostgreSQL-backed login/session handling, user/project/directory grants, HTTP+WS reverse proxy (rewriting Host/Origin to the instance loopback address), personal and shared-project dsh runtime lifecycle, the `/admin` SPA plus `/admin/api` JSON, collaborative conversations, model governance, usage accounting, and auditing. Design and staged plan: [design doc](../.agents/superpowers/specs/2026-08-14-user-directory-permission-gateway-design.md), [Phase 1 plan](../.agents/superpowers/plans/2026-08-14-gateway-phase1.md), [project-centric admin](../.agents/superpowers/specs/2026-08-14-project-centric-admin-design.md).

Automatic idle release requires a fresh authenticated Host decision for the exact process generation and an explicit `runtime-execution.mode: on-demand` setting. The default is resident. Missing policy, unavailable probes, unsigned decisions and recovered processes whose challenge credential is unavailable retain their processes. The final PostgreSQL idle claim locks node resource admission before the instance, rechecks the activity cutoff and generation, and refuses queued, active or uncertain resource reservations. New work either wins admission and prevents release, or observes the stopped intent and is refused. Existing HTTP and WebSocket leases still protect foreground work. Timers run in their original Runtime; this release does not provide process-external scheduled startup.

## Toolchain

- **Node 25** (`.nvmrc`; the dsh repository's engines `^22.19 || >=24` accept it). `better-sqlite3` and `argon2` are native modules whose ABI binds to the Node major that installed them — after switching Node, run `npm rebuild better-sqlite3 argon2`, otherwise they fail with a `NODE_MODULE_VERSION` mismatch.
- Commands: `npm run dev` (tsx source entry), `npm run build` (compiled `lib/index.js` production entry), `npm test` (unit tests), `npm run typecheck`. `HGW_TEST_DATABASE_URL` selects a disposable database for `npm run test:postgres`; its PostgreSQL suites run serially and replace the `harness` schema. CI runs both test commands.
- PostgreSQL fixture URIs must explicitly select a database ending in `_test`, `_accept` or `_acceptance`; the driver-resolved name is checked, so a suffix in credentials or query fields is insufficient. The required command includes the project manager, administrator, account, invitation and deletion HTTP replays. Additive organization fixtures retain peer data; schema-resetting migration and restore suites require exclusive database ownership. Focused specs, diagnostics and child fixtures use the same selector; required bootstraps refuse missing configuration before runtime setup.
- Managed execution: from the repository root, set `HGW_TEST_DATABASE_URL` to a disposable PostgreSQL database and run `pnpm run test:gateway:execution`. It requires workspace and Gateway runtime dependencies, checks compiled Runtime pressure admission under plain Node, then runs the real Loader and HTTP authorization without a model API key, and joins the existing CI consumer job for Gateway-related changes.
- Web lifecycle: after the workspace build, run `npm run test:built-web-assembly` in this directory with `HGW_TEST_DATABASE_URL` pointing to a disposable database ending in `_test`, `_accept` or `_acceptance`. `npm run test:local-web-assembly` selects the source launcher. Both verify the shipped Web profile through login, personal/shared scope selection, Gateway crash recovery and graceful shutdown without a model API key. CI runs the compiled scenario after the consumer build.

`npm run build` emits the Gateway source graph under `lib/` with relative imports rewritten to `.js`; production supervisors must execute `node lib/index.js` from the same release directory. The source `tsx` entry is for development and tests only.

Fixtures that create users, projects, runtime files or deployment state use `tests/test-config.ts` with their own `mkdtemp` directory. It confines writable configuration paths to that directory before services start; subprocesses receive the same explicit environment. Parser tests still exercise production defaults directly. Overriding only `HGW_USERS_ROOT` does not isolate project runtimes, keys, backups or systemd unit files.

Browser validation rechecks current account authority and both expiry deadlines after waiting for its session lock. Login issuance and failure-window checks use the current database clock after admission, so waiting does not shorten a new session’s lifetime. A completed administrator demotion denies the queued admin request; idle and absolute deadlines are exclusive, including exact equality. See the [authentication wait decision](../.agents/notes/implemented/bug-fix/2026-10-24-browser-authentication-lock-waits.md).

Node enrollment, outbound connection monitoring and an explicit verification bridge to another computer's existing Gateway are available through the [node-agent API and process](docs/node-agent/README.md). Connectivity alone grants no execution authority or stopped-writer acknowledgement. The bridge reuses the same project's existing local services. The [computer permission backend](docs/node-agent/README.md#computer-permissions) separates use permission and capability qualifications per computer; see its [migration guide](../docs/upgrade-guide/v0.2.1-rc.1.coharness.1/computer-permissions/guide.md). Startup assignment repair requires an authorized host, and trusted SQLite imports preserve their selected host without reopening revoked grants. The Admin selector retains its target across existing pages and API calls. Computer changes preserve the current page, query and fragment; pending edits keep their original page and offer the exact destination in a new tab. User-interface Runtime selection and deployment acceptance remain separate from the allocation APIs.

## Configuration (environment variables, see src/config.ts)

Authenticated `GET /account/api/runtimes` lists the caller's personal and authorized project environments; `GET /admin/api/runtimes` lists organization environments after rechecking administrator membership. Both return bounded metadata pages with `items` and `nextCursor`; optional `limit` and `cursor` query fields select the next page. Reads do not start runtimes, probe nodes or scan directories. Environment IDs survive ordinary process generation changes, and retired assignment identities remain recorded. Remote entries retain `routing: 'unavailable'` for direct local execution; managed dispatch uses their owning computer through the [node service](docs/node-agent/README.md#existing-gateway-services), which is disabled by default. An optional `ids` filter accepts at most 32 comma-separated UUIDs, rechecks current access, and binds continuation cursors to that selection. It resolves saved shortcuts without enumerating or starting computers.

On the account endpoint, `projectId=<public project number>` resolves the selected project even when its Runtime is outside the loaded pages. It returns an empty page if project membership, computer use or entry scope excludes it.

API requests can select an authorized environment with `dshRuntime=<environment UUID>`. Explicit environment selection overrides the scope cookie; a conflicting `dshTarget` returns 400. Unknown, inaccessible and retired identities return 404, malformed IDs return 400, and remotely assigned environments return 503 with forwarding disabled. Existing owner selectors require one authorized match; ambiguity returns409. See [Runtime isolation and management](docs/node-agent/README.md#runtime-isolation) for allocation, quotas, exact process controls, private storage and computer-local data. User administration returns one row per account; `runtimeCount` summarizes local assignments, and `port` is null when there is no single local Runtime.

Production install, cutover, and acceptance live in [deploy/README.md](deploy/README.md).

The runtime dispatcher authenticates runtime tokens before streaming document operations to the Gateway-owned backend. Captured execution references resolve through the Gateway registry and retain every participant; interactive requests use signed principals. The backend rechecks current scope access and exact catalog-authorized document versions before mutation. Browser and runtime metadata notifications deliver the protected journal and cannot supply document identity, ownership or lifecycle state. Delivery preserves each change's original actor and acknowledges its private journal only after the catalog commits the prefix. A retry recovers a missing local acknowledgement from the validated receiver cursor, including when no undelivered changes remain.

Linux Gateways running as root resolve Runtime accounts asynchronously before opening a document engine. Each UID/GID query uses `HGW_READINESS_TIMEOUT_MS`, filters Gateway credentials from its environment and closes before failure returns. A failed lookup leaves engine initialization retryable; it grants no fallback filesystem access. After building Gateway, run the [compiled account publication check](tests/run-built-account-publication.mjs) on a disposable Linux root host to verify both Runtime accounts.

The local document broker counts initialization, identity observations, interrupted-operation recovery, catalog acknowledgement, upload finalization and retention cleanup as writes. Initialized reads remain available during maintenance when no persistent reconciliation is required. Finalization retains its own writer after an upload returns `202`; refused admission preserves retryable work. `build:production` runs the compiled document authority check under ordinary Node; `test:built-document-authority` and `test:built-document-maintenance` require built workspace packages and release-local links.

Private document storage belongs to an organization and immutable user or project id. Recreating a project at a retained directory imports its active files with new identities and unknown creators; its previous trash and unfinished uploads remain separate private archives. The broker drains the former owner before opening its replacement. Durable ownership records fence stale scopes and finish interrupted retirement before serving the new scope. A path-only private store keeps its identity when a committed catalog prefix confirms its current owner; unbound private data is retained independently.

Document upload and transfer metadata preserves validated optional incarnation fields while dropping private paths and unknown identity fields. Invalid supplied identities refuse the response; metadata alone never grants document access. See the [document reference API](../packages/attachment/userdoc/README.md).

Catalog writes triggered by reads acquire current maintenance admission independently of the read response. Mutating requests retain their admitted writer through handler completion; their deferred catalog updates retain separate writers when queued, including time spent behind earlier deliveries. Maintenance refuses new reconciliation while already admitted mutations and their accepted deliveries finish. Original request actors remain captured throughout the queue.

## Performance and Runtime admission

`GET /admin/api/performance` requires a signed-in administrator and returns an uncached, cumulative snapshot of HTTP, internal HTTP and WebSocket lifetimes, errors and in-flight counts; fixed duration buckets with approximate percentile upper bounds; Gateway event-loop delay/utilization and process memory; native database-pool counters; and Runtime admission counts. The snapshot includes its own in-flight read. It retains no request paths, account names or Session identifiers. Compare counter and bucket differences across samples; cumulative percentiles, maxima and memory snapshots are not subtractable interval statistics. WebSocket duration measures socket lifetime, not per-frame delivery latency, and Gateway memory excludes Runtime children and PostgreSQL.

Cold Runtime admission shares FIFO start and resident reservations across this Gateway's personal and project runtimes. Warm runtimes remain available while cold starts wait. Capacity stays reserved through confirmed process termination. Supervisor-owned survivors count against the limit after restart and are not terminated merely because the configured limit is lower. The defaults are conservative protection settings, not measured support for 300 users or 100 mixed tasks. These limits cover managed Runtime processes, not Agent/tool/PTY concurrency, unmanaged processes or another Gateway on the same machine. See the [Runtime admission decision](../.agents/notes/implemented/architecture/2026-10-23-gateway-runtime-admission.md).

Cold starts also spend the node's shared pressure credits immediately before local process allocation or the systemd start command. Missing or stale pressure, memory warnings, CPU pressure, and event-loop pressure cause bounded waiting; cancellation prevents allocation. Observation validity starts at host capture, so sensor and database waits consume it. Fresh warnings immediately stop new grants; recovery requires a provably newer observation. Queued reservations recheck pressure expiry and their own deadline. The emergency resident ceiling is optional and independent of this admission. Start pacing does not reserve a calibrated number of bytes per Runtime.

Node accounting locks and fair queue scheduling execute inside PostgreSQL through migration105 functions, keeping their row locks and fresh deadline checks without per-statement network round trips. Node accounting and instance activity retain their locks while waiting within the configured PostgreSQL statement timeout. A lease checks current eligibility after acquiring its assignment lock; withdrawal during that wait refuses admission. Bounded contention returns503 without replaying work or releasing uncertain reservations. See the [Runtime admission decision](../.agents/notes/implemented/architecture/2026-10-23-gateway-runtime-admission.md).

An explicit Runtime ID must identify the same environment as the owner, computer and generation selected for startup. A mismatched or missing environment is refused before allocation state or shared credits change. Legacy owner selectors retain their existing generation lookup.

The macOS pressure command has a sample deadline and joins physical closure, including when its client ignores normal termination. A failed measurement publishes no observation; existing credits still expire. Shutdown waits for the owned sensor and accepted publication.

Personal startup resolves the current eligible account after capacity admission. A changed identity, home or role during policy preparation or pressure waiting refuses allocation with `503 INSTANCE_UNAVAILABLE`; a new request prepares current privileges. Warm policy refresh also uses the current eligible role. Existing invalidation and stop procedures still govern already running processes. Admin admission errors retain readable `error` text and include a stable `code`, using503 for unavailable policy/capacity and409 for stop or resource-generation conflicts. Linux launch preflight returns409 `RUNTIME_ACCOUNT_NOT_PROVISIONED` for a missing configured Unix account and503 `RUNTIME_ACCOUNT_VERIFICATION_UNAVAILABLE` for an unavailable lookup, with account preparation guidance. It allocates no process, credential or unit on refusal. Custom adapters follow the [personal authority upgrade guide](../docs/upgrade-guide/v0.2.1-rc.1.coharness.1/personal-runtime-authority/guide.md). The Admin client retains the Gateway error code separately from translated display text, so confirmation dialogs and revision-conflict recovery use the original failure identity.

Explicit Admin start, stop and restart retain the server-authenticated initiating administrator through lifecycle and admission waits. Revocation returns403 before later effects; an already approved stop or cancellation can remain completed. Restart revoked after stop leaves the Runtime stopped. Database checkout capacity returns `503 DB_CHECKOUT_QUEUE_FULL`; reload current state before deciding whether to retry. The project-settings link retains the same initiating administrator through passive startup and warm reuse; manually stopped Runtimes still require an explicit start. Custom adapters follow the [administrator-control guide](../docs/upgrade-guide/v0.2.1-rc.1.coharness.1/administrator-runtime-control/guide.md).

Terminal and plugin management apply the same [current-administrator response rules](../.agents/notes/implemented/bug-fix/2026-10-29-administrator-runtime-control.md): withdrawal withholds ordinary replies and interrupts later streaming chunks. Inspect current state before retrying an admitted mutation.

Gateway initialization preserves active assignments and their capacity reservations. Local macOS/Linux Runtimes have independent supervisors with authenticated loopback control and private records under `HGW_STATE_ROOT/local-runtime-supervisors`. Recovery binds the node, owner, generation, credential fingerprint, kernel boot and unchanged lock inode. A confirmed different kernel boot permits remounted device numbering only under the current exclusive lock and commits terminal stop evidence; same-boot device changes and changed inodes remain refused. Stop intent fences delayed allocation; capacity is released only after the kernel lease, owned POSIX group and any native descendant slice confirm exit. Recovery never sends a signal to a PID read from disk. Missing or corrupt evidence retains occupation. Unavailable supervision returns `503 INSTANCE_UNAVAILABLE`; confirmed local exit permits a new generation. Systemd reattachment uses the captured generation and credential fingerprint, and query failures retain occupation unless systemctl reports an inactive or missing unit. See the [local supervision decision](../.agents/notes/implemented/architecture/2026-10-25-local-runtime-supervisor.md).

Interrupted attempts remain occupied until completion or matching kernel-lock recovery, then report missing usage when counts are unavailable. Project archival preserves billing. Model-usage totals do not gain a fabricated participant from a manual button click. See the [progress decision](../.agents/notes/implemented/feature/2026-10-21-project-progress-journal.md).

## Steward maintenance space

`HGW_STEWARD=on` reserves one project space per organization (`kind='steward'`, default name `维护中枢`) as a resident maintenance runtime for operating the deployment itself. Migration 051 adds the project kind, the user-scoped `steward_access_policies` qualification lane, and the `steward_query_log` audit table; startup seeds the project row, provisions `HGW_STEWARD_WORKSPACE` (a `git worktree` of `HGW_STEWARD_SOURCE` when configured), and calls `ensureRunning` once — a crash is healed by the supervisor's `Restart=always`, while an explicit administrator stop stays stopped until the next gateway boot or explicit start. The local launcher preserves a live Runtime through Gateway failure but does not automatically restart a crashed Runtime. Exact administrator stop and restart use current administrator authority and the selected generation without requiring Steward data qualification; project deletion retains its reserved-project refusal.

Git workspace preparation runs asynchronously with the Gateway tooling environment filter. `HGW_STEWARD_PREPARE_TIMEOUT_MS` bounds preparation, and Gateway shutdown cancels it before project seeding or Runtime allocation. Cancellation joins Git and ordinary checkout hooks through the local subprocess provider; `HGW_STEWARD_PREPARE_KILL_GRACE_MS` controls termination escalation. An existing provisioning branch keeps its commits; a replacement workspace uses a detached checkout of the source `HEAD`. Other Git failures are reported without a detached retry, and partial checkout files remain for inspection. See the [preparation upgrade guide](../docs/upgrade-guide/v0.2.1-rc.1.coharness.1/steward-worktree-preparation/guide.md).

Admission to the steward space layers the qualification lane on administrator membership: an enabled `steward_access_policies` row admits an active organization administrator with `rw`, while an administrator without the row and a member holding one are both denied — membership rows stay empty and member/invitation mutations are rejected. Grant writes that enable a non-administrator fail inside the policy transaction, every admission path re-checks the role at read time so a downgrade ends entry immediately, and migration 052 deletes grant rows that can never take effect. Administrators manage the lane on the `/admin/steward` page or per user on the user detail page under revision fencing. The steward runtime's directory grants cover its workspace at `rw` plus the deployment tree — the releases collection under `HGW_RELEASE_ROOT` layouts, the repository root otherwise — and `HGW_STEWARD_READ_ROOTS` entries at `ro`. The steward runtime runs a fixed composition (`dsh-steward-tools` mounted through its profile patch); plugin-state and plugin-management writes reject steward owners, so the resident runtime can never restart itself through a composition change.

A resource request attributed to a Steward principal requires the current administrator role and an enabled grant on the Runtime computer. Queue polling checks the same facts before returning a grant. Session execution checks the qualification of every captured actor. The exact owner can still report that refused work did not start.

The agent's `steward_query` tool reaches `POST /internal/runtime/steward/query`, which authenticates the runtime token, verifies the target project is an active steward row, executes exactly one statement through PostgreSQL’s extended protocol, reclassifies the SQL server-side, and audits every attempt to `steward_query_log` with the runtime generation. Read-classified statements execute inside a `READ ONLY` transaction — the keyword test selects the lane, PostgreSQL enforces it, so `EXPLAIN ANALYZE` and data-modifying CTEs fail and are audited rather than smuggled through — bounded further by statement size (64 KiB), row (≤5000), result (256 KiB), and timeout (15 s) limits; `dry_run` returns the `EXPLAIN` plan instead. Writes require an `allowed-once` interaction approval granted by a still-qualified responder inside a conversation rooted in the same steward project within 15 minutes; an advisory lock on the approval serializes concurrent writers so the verdict spends exactly once, then the write executes in the transaction that also writes the audit row. v1 deliberately has no general runtime-invoke proxy and no release-activation automation: code changes ship through the ordinary worktree → PR → release pipeline, and administration beyond audited SQL stays in `/admin`.

Query rows and dry-run plan rows are retained as an ordered prefix within the requested row limit and the complete response’s 256 KiB UTF-8 budget. Rows beyond that prefix are drained without accumulating a second result array, including write `RETURNING` output; `rowCount` reports the full command count and `truncated` identifies omitted read or plan rows. The driver still decodes each individual row before applying the retention limit.

## Model governance and usage accounting

Runtime-specific model reporting credentials bind supplied execution witnesses to the exact durable Runtime owning the Session, including when the same account has several runtimes on one computer or across computers. Billing remains account/project-wide. Revocation does not erase valid delayed charges from that Runtime; another Runtime cannot borrow those witnesses or replace its reporting identity in the event body.

The admin SPA has **Models** and **Usage** pages. Models are identified by exact `(provider, model)` routes. The governance catalog is the sole authorization source for every role — the former `defaultAllowed` bypass for administrators has been removed. A per-route role default (`admin` / `member`), per-user `allow` / `deny` / `inherit` exceptions, and a global enabled flag determine the effective policy for catalog routes. New projects start with a project-level default that authorizes every currently available organization-managed model; newly added catalog models follow that default until an administrator clears the project or records a model-specific denial. Existing projects retain their stored mode. Routes absent from the catalog are denied for all roles; in a personal runtime, a route the user declared in their own settings layer (BYOK, bring your own key) is additionally authorized with personal-cost attribution and no catalog price, while project runtimes remain catalog-only. A policy projection also writes the first authorized, enabled organization route as the composition default in the runtime home patch; a user-layer `agent-default-model` selection remains higher precedence. A policy change atomically rewrites `$DSH_HOME/model-governance.json` (mode `0600`); a running instance watches that file and applies the validated policy without a restart, while an invalid live document fails closed for new model requests. The instance plugin provides `ctx.modelAccess`; `apiproxy` filters catalogs and rejects selection/prompt RPCs, while the `llm/stream` middleware is the final adapter-dispatch enforcement point for chat, title, compaction, and direct calls.

User-detail effective model access comes from the server policy for the target account, including its role, Provider/model enablement and individual overrides. Role defaults and user overrides describe configuration sources; neither substitutes for effective authorization.

Administrative model, Provider, credential, access and quota writes retain the current administrator through commit. Account and project overrides also retain a nondeleted account or active project target. Discovery checks current administrator authority before preparing stored or draft credentials, then releases the database connection before its HTTP probe. Browser actor fields grant no authority. Withdrawal before preparation returns403 without configuration changes or discovery traffic; withdrawal during an admitted probe returns403 before model metadata is published. See the [model administration guide](../docs/upgrade-guide/v0.2.1-rc.1.coharness.1/model-administration-authority/guide.md). Shared administrator and project-manager admission also checks current required-password-change qualification after authority waits; a reset committed before admission refuses queued management. Already admitted mutations keep their completion results.

Bulk policy projections use bounded workers over active users and project rows already returned by the catalog queries. A transient file or credential failure schedules a retry; triggers arriving during that retry retain a follow-up pass that reads the latest durable policies. Personal policy reads current account and membership authority after admission. Eager and lazy refresh compare effective contents as well as the catalog revision, because account role changes do not advance that revision. Credential-store failures retain the existing policy and intake bearer. See the [model policy authority guide](../docs/upgrade-guide/v0.2.1-rc.1.coharness.1/model-policy-authority/guide.md).

Disabled-account inspection shows no effective model access while preserving configured overrides. Policy refresh skips disabled accounts; a combined role/status change stops their personal Runtime without restarting it. Re-enablement follows current startup authorization.

The home-patch projection edits a YAML sequence, preserving user rows, comments, and unevaluated `!!js` expressions. Empty documents, flow sequences, and explicit document markers remain loadable across default changes and removal. Invalid patches fail before replacement; serialization can normalize YAML formatting.

Document-catalog reconciliation validates the complete metadata request before writing and applies a removal list in one scoped transaction when the PostgreSQL batch method is available; compatibility providers retain the per-document fallback. Ordinary project catalog reads admit current members and organization administrators; writes require `rw` membership or administrator authority. Steward documents additionally require current administrator membership and enabled Steward qualification. The user overview excludes archived projects from rows, totals and metrics. A read-only member's permitted filesystem listing remains available when best-effort catalog synchronization is refused.

Browser document fan-out rechecks the active administrator role before every source read, upload request and later target. Demotion stops the remaining requests even when project write memberships remain valid; permitted member copies to one target remain available. See the [fan-out authorization guide](../docs/upgrade-guide/v0.2.1-rc.1.coharness.1/browser-document-fanout-authority/guide.md).

Catalog transitions preserve permanent purges and check current state and retention deadlines after row-lock waits. Member mutations recheck active organization, account, membership and project write authority before commit; ownership transfer also rechecks the eligible recipient. Administrator lifecycle actions recheck current administrator authority. Refusal rolls back catalog changes and history; it cannot undo a filesystem operation completed before its catalog callback. See the [document lifecycle decision](../.agents/notes/implemented/architecture/2026-08-27-document-index-pagination-and-trash-lifecycle.md).

The policy projection version cache retains at most 10,000 recent subject/path entries; eviction only causes a later safe rewrite.

## PostgreSQL control plane

Catalog replacement and batch removal lock their initial document rows before invalidating updates and preserve registrations committed while that snapshot waits. Conversation-repository text search accepts escaped literal substrings before fuzzy alternatives, including Chinese and short queries in long events; blank queries match nothing. These changes require no schema migration. See [catalog lifecycle](../.agents/notes/implemented/architecture/2026-08-27-document-index-pagination-and-trash-lifecycle.md) and [literal search](../.agents/notes/implemented/bug-fix/2026-10-25-gateway-literal-conversation-search.md).

Administrators register webhook endpoints through the Admin UI or `/admin/api/webhook-endpoints` (`POST`, `POST …/update`, `POST …/mutate` with `enable`/`disable`/`remove`). New endpoints are disabled and answer intake with 404 until an administrator enables one explicitly. Each endpoint binds a provider (`github`), a write-only signing secret encrypted under `HGW_WEBHOOK_SECRET_KEY_FILE`, an execution account, a user or project runtime target, event/action filters, a structured repository filter of `owner/repo` full names matched case-insensitively against the payload's `repository.full_name`, `{{path}}` title and prompt templates, and intake limits. Providers POST to the public `POST /webhook/<endpointId>` route; the signature is verified against the stored secret, the body is deduplicated durably, and accepted deliveries are dispatched to the bound runtime's managed `webhook-dispatch` route, which admits one Session per delivery. Administrators can query `/admin/api/webhook-deliveries?endpointId=<uuid>` with optional `cursor` and `limit` (1–100, default 50). The response contains bounded delivery receipts without event payloads or secrets. `submitted` means prompt admission, not Agent success; `ignored` means a configured event, action, or repository filter excluded the delivery, and the receipt's error code names the unmatched rule; `unknown` prevents automatic redispatch. A settled receipt can be replayed by an administrator through `POST /admin/api/webhook-deliveries/redispatch`, which records a new audited receipt under the endpoint's current configuration. The reservation service takes separate intake and body-replay windows. Equal bodies inside the replay window share a receipt across nodes, and all observed delivery ids remain bound to that receipt after expiry. Dispatching or unknown results continue to block automatic repeats outside the window.

Webhook management, endpoint and receipt diagnostics, and manual redispatch retain the current active administrator through database admission. Provider reservation retains the active organization and exact enabled endpoint revision used for verification: unavailable endpoints return404 and changed configuration returns409 without consuming intake budget. Explicit administrator replay may use a disabled endpoint's current configuration. Parsed provider payloads must survive JSON serialization without loss; otherwise intake returns400 before allocating a receipt. Custom services pass the authenticated administrator id ([decision](../.agents/notes/implemented/bug-fix/2026-10-29-webhook-admission-authority.md)).

Project Webhook roots default to project visibility; each endpoint can select private visibility for its execution account. Current project write membership is required both before dispatch and before persistence; personal targets must belong to that account.

Only idle-reaped runtimes can be awakened by a Webhook, after current account, project-write and Auto qualification checks. Manual stops survive Gateway restarts and background permission refreshes. An authorized user can explicitly start and open a stopped runtime; its form and redirect retain the selected `dshRuntime` independently of other tabs. Passive reconnects cannot start it. Disabled owners and maintenance refuse starts. An inactive/deleted owner, inactive membership or missing runtime assignment reports `INSTANCE_UNAVAILABLE`; explicit start does not bypass it. Only an eligible runtime blocked by its stop policy reports `INSTANCE_STOPPED`. Legacy stopped rows without a reliable stop reason require one explicit start.

A pinned PostgreSQL 17 deployment lives in [`deploy/postgres/`](deploy/postgres/README.md). The Gateway entry point applies its immutable migrations and refuses to listen unless the configured active organization and compute node resolve. Authentication, users, account preferences, projects, personal/project instances, shared project conversations, collaboration claims, audit, model governance, project Provider profiles and encrypted credentials, quotas, and usage are PostgreSQL-backed. Internal UUIDs preserve organization foreign keys while numeric public IDs keep the existing HTTP API stable. SQLite remains only as the accepted source of a stopped-writes final import and rollback backup; the running Gateway never opens it.

PostgreSQL Session storage is bound to the authenticated organization and Runtime through `PostgresConversationStore.forRuntime()`. Original Host identifiers remain local: bodies, append retries, lineage, migration predecessors, search, participation, claims, file references, push and progress receipts keep the same namespace. Unknown history remains legacy data and cannot be adopted by a new allocation. Empty-draft maintenance retains each reviewed Runtime/Host pair. See the [Session identity upgrade guide](../docs/upgrade-guide/v0.2.1-rc.1.coharness.1/postgres-session-runtime-namespace/guide.md).

Message text, literal search and bounded previews preserve NUL through the [lossless text migration](../docs/upgrade-guide/v0.2.1-rc.1.coharness.1/conversation-nul-text/guide.md). Shared activity and progress use versioned event query fields; original event JSON and Runtime ownership remain intact.

Every call produces one UUID-keyed usage record in a crash-safe per-runtime outbox. The loopback intake deduplicates UUIDs in PostgreSQL, applies the price version effective at the call timestamp, and attributes company cost from a non-secret credential source label (`file`/`project-env`/`request` are personal; launch environment sources are company; unknown remains company-conservative). No API key, prompt, or response content enters the ledger. Natural months use `HGW_USAGE_TIME_ZONE`; token and company-cost quotas support role defaults, per-user inherit/unlimited/custom overrides, and project inherit-or-explicit limits. Quotas warn at 80% and 100% but do not block calls. `GET /admin/api/quotas` reads back the stored row for `subjectType=role` (`admin`/`user`, `null` limits mean unlimited) or `subjectType=user` (inherit/unlimited/custom modes), and the Usage quota dialog stays disabled until that read lands. Billing ownership remains exactly one user or project; shared-project records additionally retain a verified participant id when available for non-billing activity reports. Historical project records without that fact remain unattributed. Users see durable crossings in the Web shell; admins see separate personal, project, and contributor summaries, missing-usage counts, and explicit price-coverage status.
The Admin usage API keeps the legacy subject summary and adds `/admin/api/usage/overview`, `/admin/api/usage/contributors`, and `/admin/api/usage/health`; contributor rows are activity projections and are never added to project billing totals. Archived identities remain in the overview so historical personal usage and confirmed project activity continue to reconcile with their subject totals.
Personal settings changes use the same authenticated outbox with a `model-registration` record type. The Gateway stores Provider/model creation, modification, and deletion separately from usage and exposes them through the administrator Models page; records contain route identities and timestamps only.

## Deployment maintenance and coordinated restore

Governance recovery preserves current node content and peer backup authority; incompatible ownership or protected schemas require isolated recovery. See the [maintenance decision](../.agents/notes/implemented/architecture/2026-09-25-gateway-deployment-maintenance.md).

Database maintenance uses private connection input; native clients require a separately built libpq adapter and custom Docker/SSH wrappers must implement its readiness protocol. See the [PostgreSQL maintenance client reference](deploy/postgres/README.md#private-maintenance-connections) for installation, configuration and cancellation semantics.

On macOS, `release-control.sh activate <candidate> --rollback-target <directory>` preselects a complete compiled fallback whose database compatibility the operator has verified in isolation. Candidate and fallback must resolve to distinct direct release directories with complete payloads before any switch or process action; `current` aliases, missing/incomplete payloads and paths outside the release root are refused. Failure restores only the specified target and verifies its PID, working directory and health release id; an unhealthy fallback reports failure without trying another older release. Without the option, rollback uses the previous release. Old PID and descendant cleanup always refer to the actual running release. The controller checks payloads, not database compatibility, and does not read or migrate the database. See the [managed release decision](../.agents/notes/implemented/process/2026-08-18-atomic-macos-gateway-releases.md).

Maintenance administration checks and retains the current active organization administrator through reads and committed transitions. Entry, exit and node-status changes commit with their operation row, and concurrent entrants create one window entry. Restore registration also retains the organization-owned verified complete backup through acceptance. A withdrawn account, role or membership returns403; an unexpected database failure returns503 without committing a partial transition. The trusted standalone applier remains available under its deployment ownership.

All runtime processes must confirm stopped before writer quiescence, including on nodes declared offline. The deployment page shows the remaining instance count. Administrators can stop an owner-addressed instance or an exact Runtime generation during maintenance; current authorization and generation checks still apply. A stale pre-restore process cannot stop either target. Restore appliers hold an exclusive database advisory lease through file reconciliation. Restore SQL also holds its own transaction lock and checks the coordinating backend identity before mutation and commit; losing a local Docker command proxy cannot release this database exclusion. Failed restore attempts remain in `restoring`, block maintenance exit, and can be retried with `pg:deploy restore`; only verified complete reconciliation returns the deployment to maintenance.

Upgrades and restores run as controlled operations instead of relying on startup migration or the `deploy/postgres` shell scripts alone. `harness.cluster_control` holds one organization row: the mode (`serving`/`maintenance`/`restoring`), the maintenance epoch nodes must acknowledge, the write epoch that fences stale writers, and the operator reason. `harness.deployment_operations` is the operation ledger; `harness.backup_records` registers each dump with its managed-file manifest, verification state, and the write epoch it was taken under. Each compute node reports its applied maintenance epoch on `maintenance_applied_epoch`; a node with a fresh heartbeat that has not acknowledged the current epoch counts as an active writer, while an offline node still requires stopped runtime records — and returns to `active` if it keeps heartbeating.

While maintenance is open the Gateway rejects mutating HTTP and runtime calls with 503 (`maintenance`), and after a restore the bumped write epoch rejects every process started before it (`stale-epoch`). The Admin Deployment page creates and verifies backups through the same service as `pnpm pg:deploy backup`; restore requests are executed by the independent `pnpm pg:deploy restore` applier. `HGW_PGDUMP_COMMAND` and `HGW_PGRESTORE_COMMAND` configure PostgreSQL wrappers, `HGW_PSQL_COMMAND` can select a matching SQL executor, and `HGW_BACKUP_DIR` selects private backup storage.

PostgreSQL command children use the Gateway's scrubbed tooling environment. Unrelated Gateway, Runtime and credential-named variables are excluded; standard `PGPASSWORD`, `PGPASSFILE` and `PGSSLKEY` inputs remain available when configured. Custom wrappers receive private connection input and PostgreSQL settings without unrelated Harness configuration.

Command failure details retain at most 8 KiB of stderr as a complete UTF-8 prefix; process status and command context remain separate from that byte ceiling.

A complete backup requires maintenance, stopped runtimes and the database data-operation lease. Creation and verification retain the authenticated administrator through command admission and registry writes. Configuration preview also checks current authority before publishing its POST read result. Verification and configuration preview require a canonical registry UUID; malformed selections return400 and unknown valid identities return404. Revocation refuses later admission without marking a valid backup failed; files captured before a refused registration remain for operator cleanup. Retained users remain data owners after deletion removes their operational instance row; local assignment without that row requires the verified single-organization, single-node topology. User creation registers its pre-created document directory inside the account transaction before creating it, so an account that never started a runtime is still covered. Failed database commits retain their diagnostic files without assigning them to a different account. Each runtime's storage providers record their actual resolved paths in `DSH_MANAGED_DATA_MANIFEST`; earlier paths remain recorded after configuration changes. Backups capture every regular file and empty directory beneath those approved roots, plus node-owned configuration and credentials, with copied-byte digests, permissions and ownership. Sessions retain all committed generations, including malformed originals; attachments, User Documents, historical Review, external-member bindings and pending governance outbox records retain their owner-defined storage. Project source, SSH workspaces, unknown files and links are excluded from ownership claims rather than swept into a state-directory archive. A missing inventory, unapproved custom root, symbolic escape or incomplete snapshot refuses the operation. File copies reject zero-progress writes, observe cancellation between partial writes and recheck it after synchronization before publishing a captured digest. Complete bundles currently require one organization and one compute node; a local bundle cannot establish coverage of another node's filesystem.

The recorded owners `@deepseek-ai/dsh-agent-presets` and `@deepseek-ai/dsh-agent-preset-registry` both cover only the exact canonical default directory `<runtime.dshHome>/.agent-presets`; this compatibility does not approve custom roots or unknown owners. Collection deduplicates the physical backup root without rewriting inventory bytes. Relocation retains every original ownership record and applies the same preset-configuration checks to both names.

For historical roots absent from provider records, the node administrator supplies a private `HGW_MANAGED_DATA_APPROVAL_FILE` using the [managed-data record format](../packages/util/managed-data/README.md), with owners prefixed by `user:<public-id>/` or `project:<public-id>/`. After reviewing the current and retired storage locations, stop writers and run `pnpm pg:deploy inventory adopt --runtime user:<public-id>` (or `project:<public-id>`). The command appends only explicitly approved roots, preserves existing records and logs the adoption. Approval never permits claiming an entire project workspace or Harness home. Missing records are not inferred from familiar directory names.

Schema eligibility is checked before restoration can open its write fence. Registered backups must match the current migration version; the applier compares the actual dump’s complete migration versions, names and checksums before capturing a protection copy. Unreadable or different metadata refuses both backup-id and direct-dump restoration while maintenance remains open. See the [restore schema upgrade guide](../docs/upgrade-guide/v0.2.1-rc.1.coharness.1/restore-schema-preflight/guide.md) for accepted archive metadata and existing-window recovery limits.

Restoring an eligible backup first creates and verifies a complete protection backup of the current database and managed data. Its identity and the selected dump/manifest digests are committed with the restoring fence; retries reuse that first protection copy. The database transaction retains current maintenance, operation and backup records and rejects different organization or compute-node identities. File reconciliation removes later additions only from owned roots, restores recorded bytes and metadata, and verifies full membership before returning to maintenance. Restore retains current node configuration, revisions and the database connection file. Outstanding current-node apply requests remain subject to their write-epoch check; a restored database cannot grant an old request new authority. Stored applied settings can be previewed for separate administrator review; neither old pending requests nor old addresses are applied by restore. A different data location or node identity requires explicit migration and refuses before database replacement. The ledger records both the selected manifest and the derived manifest that preserves these control files. Protection copies remain for explicit administrator cleanup. Failure keeps writes closed; `pnpm pg:deploy restore` resumes the recorded target without recapturing partial state. Legacy shallow manifests cannot qualify as complete backups. See the [maintenance note](../.agents/notes/implemented/architecture/2026-09-25-gateway-deployment-maintenance.md) for the durability and recovery rules.

Document identity inventory includes public files, private metadata, same-filesystem retained objects and directory-ownership records. Directory bindings serialize only the logical owner kind and public id; Runtime UUIDs and generations remain request authorization fields. Active identity domains retain original object witnesses, digests and setgid directory permissions. Restoration first verifies complete bytes, then rebuilds active document hard links and rebinds their new kernel identities; logical ids, creators, trash actions and delivery positions remain intact. Retired private stores retain their raw metadata, trash bytes and upload manifests in byte-verified archives; restoration keeps those archives separate from active identity rebinding. Multiple active identity domains for one physical public directory, unreconciled active-file edits or incomplete evidence refuse certification. Existing storage connections reject a replaced metadata file and require restart behind the restored write epoch.

Upstream resets after response headers destroy the incomplete downstream HTTP response. Browsers and caches receive a transport failure rather than a successfully ended partial body. See the [proxy error handling decision](../.agents/notes/implemented/bug-fix/2026-10-12-gateway-proxy-error-listeners.md).

Remote forwarding retains request error listeners through transport disposal, including repeated errors after an HTTP failure or WebSocket handshake failure. A late transport abort terminates its request without restarting the Gateway.

## Access revocation across Gateways

The account workbench checks each personal root against its exact Runtime assignment and that computer’s current use permission. A grant on another computer cannot expose its title, working directory or other catalog metadata, including when a personal Runtime is unavailable and the workbench uses the account catalog. Authorized roots on other computers and other accounts keep their existing visibility.

Human login and cookie validation require an active organization, user, and membership. Login rechecks them after password verification before creating a session. Disabled organizations receive the ordinary authentication refusal; organization status is not disclosed. See the [organization authentication decision](../.agents/notes/implemented/bug-fix/2026-10-24-disabled-organization-human-auth.md).

The browser retains its session token for the absolute lifetime, rounded up to whole seconds. Server validation enforces both idle and absolute expiry; browser retention grants no access after either deadline. Conditional idle renewal commits before a fresh authority read, so database row locks do not span remote result delivery. A failed authority read returns no principal even when renewal has committed. The [session retention decision](../.agents/notes/implemented/bug-fix/2026-10-24-browser-session-retention.md) records the transport and upgrade rules.

Committed changes to existing account, project, conversation, archive, and document access invalidate affected proxied HTTP responses and WebSockets on every Gateway in the organization. New requests catch up with the durable access records and recheck login and project authority after runtime admission. Directory-grant changes also stop affected local runtimes so their next start receives current grants. New Session/document registration, message appends, statistics, and sliding login expiry do not invalidate traffic.

A lost PostgreSQL listener closes admitted proxy traffic. Reconnection waits for cancellation and reads missed records before admitting more traffic; signed-principal expiry is an additional limit. A cold Gateway resumes its compute node's successfully applied runtime revision; an existing process keeps its own cursor across reconnects. Keep the `access.invalidate` records in `harness.outbox`, including records with `completed_at` set: they are a replay history, not a deletable work queue. Missing revisions fail readiness and proxy admission. The [decision record](../.agents/notes/implemented/architecture/2026-09-22-cross-gateway-access-invalidation.md) explains transaction ordering, retention, and cost.

Runtime event streams recheck Session visibility for each publication batch. Clearing content already held by the browser remains a separate Client responsibility. Closing a participant's transport does not establish that participant's existing model/tool tasks have stopped inside a shared project runtime; participant-owned task cancellation needs independent verification.

Selected-scope document downloads subscribe to the same access monitor before authorization and remain subscribed through response consumption and runtime-lease release. Revocation stops subsequent bytes; it cannot retract bytes already delivered. Slow runtime shutdown does not delay the download's cancellation. Cleanup failure is reported and blocks acknowledgment rather than being treated as successful release. Browser upload sessions subscribe through request and response cleanup, including raw chunk receipt; admission catches up before checking the current login, then closes any authority-check race. Ordinary document metadata does not acquire a transfer cancellation subscription. Runtime document `openRead`, `save` and `writeUploadChunk` calls subscribe through the complete captured participant set, recheck their runtime generation after monitor catch-up, and retain revocation delivery until the input, file source and response settle. A document backend requires an initialized access monitor; monitor loss refuses admission and cancels active transfers.

## Layered directory enforcement

The gateway only authenticates and orchestrates; regular-user directory access is enforced by the Linux production systemd mount namespace and the [dsh-directory-guard](../plugins/dsh-directory-guard/README.md) plugin loaded inside every instance. Regular units mask the users root, project-runtime root, configured project roots, and Gateway-owned credential paths before re-binding only the runtime home, `$DSH_HOME`, and authorized project directories; `ProtectSystem=strict`, `ProtectHome=tmpfs`, and removal of `CAP_SYS_ADMIN` apply across the process tree. The home patch also replaces the host OS directory chooser with the in-app browser, which lists grant roots and refuses paths outside them. Administrators retain the same plugin composition but receive a filesystem-root grant and the Full access preset; their systemd unit removes the regular directory masks and read-only system/home settings while retaining the non-root runtime account, `NoNewPrivileges`, the capability restriction, and the Gateway-directory exclusion. Shared project units run under `HGW_PROJECT_RUNTIME_USER`, bind only the project path and their private `$DSH_HOME`, and expose credential settings read-only. The managed user-project root must inherit group access for `HGW_PROJECT_RUNTIME_USER` (for example a setgid `2770` root owned by `harness-project`, or an equivalent default ACL), otherwise a newly allocated directory cannot be opened by its project unit. The macOS local launcher has no systemd mount namespace: terminals and opaque commands run with the host account’s filesystem permissions. A macOS deployment therefore requires trusted operators with equivalent host privileges and cannot promise process-level separation between users or projects. Gateway identity, project ACL, and administrator checks still apply.
