# Agent Note: Multi-computer runtime management

Status: proposed

English | [中文](2026-10-28-multi-computer-personal-runtimes.zh.md)

## Problem

The existing single-computer system already supports multiple users and independent runtimes. One authenticated frontend needs to extend that management to several organization-managed computers. Existing account/project selectors, loopback proxy targets and node-local paths need explicit device/runtime addressing. A slow or disconnected computer must not delay another environment or the browser's input response.

## Proposal

The initial release manages macOS/Linux computers through one Web UI. Users may access one or several computers according to their grants, and one user may own several independent personal runtimes on the same computer. Permissions and quotas govern allocation. Each collaborative project is hosted on one selected computer; different projects may use different computers. Windows nodes, one project spanning computers, directory synchronization, migration and automatic failover follow separately.

Deploy the same project release on each computer and reuse its existing multi-user, multi-runtime services. The center hosts the shared Web UI, Admin and organization Gateway; it may also host its own runtimes. Managed computers retain the existing node-local instance manager, launchers, supervisors, plugin profiles and resource providers. Their local service operations are reached through the center's authenticated node connection. Multi-computer support changes service addressing, authorization delivery and configuration projection while retaining capability implementations and space behavior. Any separation of the current Gateway assembly serves these deployment roles rather than creating a replacement runtime stack.

The center owns authentication, authorization, the environment directory, routing, policies and operation receipts. A node owns local processes, resource admission, directory resolution, terminals and configuration projection. Nodes establish authenticated outbound connections so the same deployment works inside a LAN and across networks. The transport proof must cover the existing public ingress before choosing a production tunnel provider.

Environment identity is a branded `RuntimeId`, separate from account/project ownership, compute-node placement and process generation. Account ownership does not uniquely identify a runtime. A project retains one shared execution location on its selected computer. Existing instances receive durable identities through [migration 076](../../../../gateway/deploy/postgres/migrations/076_runtime_environment_directory.sql). The directory retains retired identities after assignment removal. Historical owner/node UUIDs deliberately do not reference live rows; current reads join live account, membership, project and node records. Migration093 permits multiple personal assignments; the legacy private-directory uniqueness and one shared Runtime per project remain enforced. Ambiguous owner selectors require an explicit Runtime identity, including while user-interface selection is being extended.

Session routes, browser drafts, workspaces, previews, upload identities and environment-specific settings include `RuntimeId`. Original Session log IDs and committed JSONL generations remain unchanged. Account preferences and project authorization retain their existing owners. Personal files and documents remain on their owning computer; collaborative project files remain on their project’s selected computer.

## Directory foundation

The [PostgreSQL directory](../../../../gateway/src/postgres/runtime-catalog.ts) reads authenticated metadata without runtime startup, network probes or directory scans. Account pages expose only the caller's personal environment and currently authorized projects; administrator pages recheck organization administrator membership. Keyset cursors bind organization, account and audience. Row and complete UTF-8 response budgets are deployment settings. Remote metadata reports unavailable routing until the node transport exists.

The local [runtime supervision](../../implemented/architecture/2026-10-25-local-runtime-supervisor.md), [runtime admission](../../implemented/architecture/2026-10-23-gateway-runtime-admission.md), [workbench ownership](../../implemented/architecture/2026-09-23-principal-owned-workbench-layouts.md) and [deployment maintenance](../../implemented/architecture/2026-09-25-gateway-deployment-maintenance.md) decisions remain active. This directory adds environment identity without replacing those lifecycle, authorization or recovery mechanisms.

## Node access foundation

The [computer permission service](../../../../gateway/src/computer-access.ts) stores account use decisions per registered node through migration079. Existing personal assignments and the first personal space preserve their host permission; additional nodes require explicit administrator decisions. Center API writes retain current administrator authority and optimistic revisions and commit their audit record with the permission. Project membership, directory reads, personal startup and ordinary Runtime request assertions cannot substitute for computer use. Captured execution participants recheck the same permission. Cleanup-only runtime credentials remain valid for owned resource completion after revocation.

Migration080 adds node ownership to the existing six capability-qualification tables. Decisions and revisions remain independent per computer. A project policy belongs to its assigned node. Local process, file and execution consumers use `scopeAccessMonitor`; the center's forwarding proxy retains organization-wide delivery and cancels only streams for the changed node. Node-qualified revocation does not stop unrelated computers or other participants' shared project processes. Enabled legacy qualifications for active owners without assignments refuse migration; existing assigned policies retain their node and revision. The [permission scenario](../../../../gateway/tests/computer-access-postgres.spec.ts) covers real authenticated center APIs, offline-node configuration, project gating, queued administrator revocation and independent computer access without starting a Runtime.

Migration081 binds started Runtime generations to the enrolled node's exact connection UUID and epoch. Existing local Gateways without an agent registration retain local admission. Startup, ready-process reuse and ordinary credentials refuse an unavailable or changed connection; reconnecting cannot authorize the old generation. Execution-watch heartbeats recheck that credential with a bounded, nonoverlapping read. Missing hints, expired leases and stalled authority reads therefore close the watch, allowing the existing execution plugins to cancel and drain tools. Cleanup credentials retain only their existing generation's resource-finish authority. Connection loss never certifies a stopped process or releases physical resources.

[Node access](../../../../gateway/docs/node-agent/README.md) uses one-time administrator tickets, node-generated durable credentials and PostgreSQL connection leases. HTTP control requests originate at the node and use the center origin, without an inbound node listener or database credentials. Credential revisions invalidate tickets and live leases; connection UUIDs and epochs fence delayed heartbeats and releases. Repeated enrollment binds to the original candidate credential; issuance secrets are returned once and require explicit reissuance after a lost response. Cached node pages have row and byte limits, and control admission is bounded.

Agent connectivity has its own metadata and never publishes the existing maintenance writer acknowledgement. New nodes stay offline for execution and report `executionReady: false`. This permits enrollment and ingress verification before runtime dispatch can grant work or affect process ownership. Two independent source and compiled node processes are verified locally; public-ingress and cross-computer acceptance remain required.

## Local routing and Admin access

The [runtime router](../../../../gateway/src/runtime-router.ts) resolves an exact account-authorized environment before invoking the local adapter. Placement uses the actual node UUID, independently of the directory’s availability label. The local adapter reads current project authorization services and prepares existing account/project context; existing lifecycle owners still enforce local assignment and generation. Explicit environment identity survives HTTP and WebSocket dispatch and is included in failed HTTP audit details. Missing, mismatched and remote environments never fall back to another owner or local port. WebSocket refusals retain their declared HTTP status.

The Admin deployment page manages node access independently of other deployment reads. One bounded page is retained, no node is contacted by refresh, and polling never overlaps an unsettled read. Codes stay in component memory, are masked by default and require explicit copying. Unknown mutation outcomes require directory inspection; receipt node, revision and issuance identity are validated before success is shown. Connection status and maintenance writer state have separate labels. Pending compute-node reservations retain the existing complete-backup restriction; registration explains that effect before submission.

## Existing Gateway service transport

The [service proxy](../../../../gateway/src/node-service-proxy.ts) resolves an account-authorized RuntimeId or an explicitly administrator-authorized node before opening a [node-owned service stream](../../../../gateway/src/node-service.ts). The outbound agent connects only to an operator-configured loopback Gateway, checks its organization/node/release identity and forwards the existing HTTP or WebSocket protocol. The same project retains its local launchers, supervisors, policy projections and plugin composition; the node Gateway uses the existing shared organization control plane. Browser authentication and business operations are checked again at the destination. One-use stream identities and current connection epochs prevent another node or stale lease from supplying a connection.

Control probes and service connections have independent capacity. HTTP data uses stream backpressure and bounded binary messages; aggregate metadata/file limits remain with the existing services, preserving large attachment downloads and installation streams. Request cancellation, node revocation, channel loss and shutdown dispose the owned connections without retrying forwarded operations or certifying process termination. Node-credential failures become service unavailability rather than browser-authentication failure. Organization-wide permission notifications stop only runtimes assigned to or retained by the local manager, preserving independent Gateway authority monitoring.

The existing Admin shell binds its selected computer to `/admin/computers/<node UUID>/...`. Router links retain this prefix; existing API methods, installation streams and downloads submit its explicit target. Switching computers replaces the document rather than mutating a shared request target while old page operations remain alive. Center identity and a bounded directory page load independently, while enrollment remains central. The remote project-settings shortcut cannot launch a center Runtime and remains unavailable until user-interface selection is connected.

The [compiled scenario](../../../../gateway/tests/run-built-node-service.mjs) exercises two independent Gateways, a node-agent process, PostgreSQL and the shipped Web profile through center login, exact Admin management, two simultaneous same-account Runtimes, selected-environment metadata, a real workspace event, public Webhook forwarding, generation-checked lifecycle controls and retained retirement receipts. The service bridge remains an explicit verification opt-in, disabled by default. The scenario uses local processes; physical-computer/public-network acceptance and user-interface selection remain separate work.

## Existing Admin and space management

The existing [Admin routes](../../../../gateway/admin-ui/src/App.tsx) and [management operations](../../../../gateway/src/admin-api.ts) remain the management surface. Multi-computer support extends their target resolution and delivery. Organization, account and project policy retain their existing ownership; selecting a computer does not create another account, model catalog or quota ledger.

[Account creation](../../../../gateway/src/postgres/user-service.ts) provisions the personal space. The existing account-management flow carries computer grants and additional personal-runtime allocation; a computer-use grant does not introduce a self-service runtime-creation permission. [Project provisioning](../../../../gateway/src/postgres/project-service.ts) preserves both administrator-configured spaces and user-created, owner-managed spaces, with the current member invitations and read/write permissions. Each newly allocated space records its selected computer. Project membership does not grant computer access: a member needs the hosting computer's use permission before entering the project.

[Directory grants](../../../../gateway/src/runtime-directory-grants.ts) preserve account homes and authorized project mounts on their owning computer. Personal runtimes belonging to the same account on the same computer use the existing granted working directories, while each runtime has separate Session storage, plugin composition and runtime settings. Different computers resolve their own local roots; adding a computer neither copies absolute paths nor synchronizes files. Existing document ownership and private-store reconciliation remain authoritative.

Administrators retain the current account, space, document, archive, plugin, terminal and deployment management operations. Their existing purpose-limited assertions remain attached to the corresponding operations; device administration does not replace plugin qualifications, Session consent or physical-resource admission. Shared-desktop exclusivity applies to each actual node/desktop pair, so different computers may operate concurrently. Loss of the authorized Gateway connection preserves the current refusal of new work and drainage of affected execution. Existing data on the original computer is retained; importing another independent deployment is deferred.

| Existing Admin area | Policy and data that retain their owner | Computer/runtime extension |
|---|---|---|
| Accounts and spaces | One organization account, role, status, personal space, project owner, member and invitation model | Computer grants and runtime allocations in the existing account/space flows; lifecycle actions identify one runtime or the whole account explicitly |
| Plugins and qualifications | Existing profiles, settings layers, protected modules and resource qualifications | Inspect, configure and apply to the exact runtime on its owning computer, retaining desired/applied/running revision checks |
| Models, quotas and usage | Organization catalog and credentials, account/project overrides and quota ledger | Project policy to every affected runtime and aggregate usage across computers; additional runtimes do not reset quotas |
| Documents and archives | Existing account/project ownership, visibility, document incarnations and immutable Session generations | Carry the actual computer/runtime locator in listings, content reads, transfers and retirement operations |
| Terminals, SSH and desktops | Existing terminal ownership, SSH grants, VNC view/control consent and Computer Use admission | Resolve both the runtime host and the actual resource host; preserve capability-specific concurrency and revocation |
| Deployment and steward | Existing maintenance, configuration revisions, backup coverage and reserved steward authorization | Keep center network/database/signing settings at the center; apply machine-local paths, pressure and process settings to their owning computer |
| Webhooks and audit | Existing endpoint authority, delivery receipts, execution account and audit actors | Bind execution and receipts to the selected runtime/computer and record that identity with the operation |

The [node settings](../../../../gateway/src/node-config-fields.ts) contain both Gateway-service settings and machine-local settings. Remote configuration must preserve that distinction. The node agent receives only its authorized local configuration and credentials, rather than the center's complete configuration or database secrets. Admin filters and target selections apply only to the corresponding operation; organization-wide settings keep their existing scope.

## Exact Runtime records

The existing directory resolves owner selectors only when one authorized environment matches; an ambiguous selector requires a Runtime UUID. Placement precedes local service selection, including scope changes, root assets and WebSockets. Administrator service dispatch remains independent of the administrator's personal Runtime placement. Lifecycle queues and signed operation producers retain the selected UUID, and runtime consumers require credential/principal UUID equality. This preserves the mature authorization and lifecycle owners while preventing another same-owner assignment from receiving an operation.

[Personal storage](../../../../gateway/src/runtime-layout.ts) separates each computer's account working directory from Runtime-private settings, profiles and Session data. Existing assignments retain their released directory and supervisor name; isolated assignments use a UUID directory and supervisor name. Working-directory grants retain account/project ownership. Account preferences remain organization-account data, with their existing legacy migration source. Plugin desired-state rows and applied markers belong to the exact Runtime. Model policy files use its private home while billing and model quotas remain account/project scoped.

Model reporting credentials are Runtime/computer-owned while usage retains account/project billing ownership. Projection resolves its exact prepared local assignment before credential reuse; a sibling's startup or policy refresh cannot invalidate an existing reporter. Legacy reporting credentials remain available for coordinated cleanup. Preparing allocations receive neither policy projections nor execution admission. Generated personal supervisor keys use an underscore namespace excluded from account names, preventing a new Runtime from sharing a legacy account's supervisor name.

Migration082 retains an owner/node process-generation counter after assignment removal. This lets existing resource protocols keep their numeric generation without colliding across independent Runtimes; a second execution-coordinate namespace is unnecessary. Resource registrations also retain Runtime UUIDs, so confirmed-stop cleanup cannot reclaim a sibling's occupation. Physical desktop keys remain node plus desktop. Queued work rechecks the bound node connection at allocation; active and uncertain resources require owned completion or confirmed process termination.

Document catalogs and filesystem projection roots belong to an account/project on one computer. Personal Runtimes on that computer share their account's working documents; equal paths and incarnations on different computers remain separate records. Session execution witnesses, persisted conversation metadata and archive commands retain Runtime identity. Archive filesystem cleanup stays on the owning computer. Historical unassigned metadata does not authorize replacement Runtimes, and released Session JSONL generations remain immutable. The [node reference](../../../../gateway/docs/node-agent/README.md#runtime-isolation) owns operator-facing storage and credential requirements.

The [allocation service](../../../../gateway/src/runtime-management.ts) reserves identity and account-wide quota before local provisioning, without holding database locks during filesystem work. A durable request UUID recovers the original result or resumes a preparing assignment. Startup refuses unprepared storage. Policy overrides retain revisions through clearing and recreation, preventing an old editor from replacing a newer policy. These decisions support slow or disconnected computers without automatic mutation retries.

Retirement uses the existing manager's process-owned destructive lease and generation-checked quiescence proof. It retains data, storage history and receipts and disables automatic assignment repair for managed accounts. Account deletion checks assignments on every computer before retiring the account; it refuses unresolved remote processes instead of treating disconnection as stopped. Local configuration changes enumerate every assignment while the existing outbox distributes authority changes across Gateways. Existing lifecycle, supervision, qualification and resource policies remain their respective owners.

Webhook endpoints and receipts retain the exact Runtime and computer. Existing configuration edits preserve the binding; current revision and node checks run inside reservation admission. Public ingress forwards the original signed bytes to the owning Gateway. Retired personal Runtime inventories remain backup owners. These backend operations do not enable the default-off service bridge or complete user-interface and physical-network acceptance.

## Management model and implementation inventory

A registered computer hosts independent runtime plugin compositions, runtime-state directories and process lifecycles. Working directories retain their account/project grants as described above. A runtime can contain multiple Sessions, Agents and child processes. Node identity, stable `RuntimeId`, account/project ownership, process generation and resource ownership remain distinct. Gateway owns unified discovery, authorization, configuration intent and routing; node-local Providers own execution and resource effects. Runtime business capabilities retain their Service Definition, Provider and Consumer roles. Transport infrastructure does not absorb plugin-specific authorization or sharing rules.

Admin manages admitted computers, account grants, runtime allocation and lifecycle, plugin composition, configuration application, resource occupancy and diagnostics. The user surface exposes the computers and runtimes actually available to the caller, with a persistent device/runtime identity on each working view and an explicit target before starting work. Account/project authority, per-Session consent and current resource availability remain separate facts.

| Device and runtime access | [Resource qualifications](../../../../gateway/src/resource-access.ts) address accounts/projects; the node directory authenticates administrators | Resolve which devices, runtimes and capability actions each account can use; retain existing project/Session checks |

| Profiles and configuration | [Managed runtime profiles](../../../../gateway/src/instances.ts), [plugin management](../../../../gateway/src/plugin-management.ts) and [node configuration](../../../../gateway/src/node-config-store.ts) have existing owners | Address every operation to its device/runtime and expose desired, applied and running revisions separately |

| Data and recovery | [Archive ownership](../../../../gateway/src/postgres/conversation-archive-service.ts), documents and deployment backups retain owner-specific records | Include runtime/device ownership in indexes and operations; report actual per-device backup coverage |

Shared input resources use a resource identity such as node plus desktop; the holder includes the exact runtime, generation, workflow and authorized participant. Adding RuntimeId to the resource key would incorrectly give every runtime a separate lock on the same desktop. Different computers have independent resources. Computer Use qualification, explicit Session confirmation, and the exclusive lease retain their separate checks; unconfirmed driver shutdown cannot release the desktop to another runtime. VNC viewing and control, terminal sessions, filesystem roots, SSH realms and CPU/model admission keep their capability-owned sharing, consent, concurrency and revocation policies.

Authorization must identify which users and runtimes may use each device capability or concrete resource. Eligibility, explicit Session consent and the current lease holder are independent decisions. A runtime’s host and a resource’s host can differ, as with an SSH target or a remote desktop; resource authorization and occupancy follow the actual resource owner. User and Admin views must retain that distinction.

Account disablement and deletion must invalidate authority across every node and enumerate the account’s personal runtimes and participant-owned work. Stop requests, confirmed process exit and unavailable nodes remain distinct outcomes. Data retirement cannot report completion while required node cleanup is unconfirmed. Removing one participant does not stop shared project runtimes used by other accounts. A single-runtime destructive operation and account-wide retirement need explicit scopes that preserve the replacement-start protection in migration 078.

The backend retains existing per-capability sharing and exclusivity rules. User/Admin interaction changes consume its exact environment directory, computer permissions, lifecycle controls and operation receipts. Physical-network acceptance remains required before enabling the service bridge for a deployment.

## Implementation sequence

The [browser identity and document-location decision](../../implemented/architecture/2026-10-29-browser-runtime-and-document-location.md) records the implemented tab isolation, computer cards, direct storage authorization and verified cross-computer copy. This proposal retains the broader deployment acceptance and deferred platform requirements.

1. Use the existing Admin/space behavior and the identity, permission and capability-resource inventory as the implementation baseline.
2. Separate organization account identity from node-local process assignments, then migrate exact runtime addressing through storage, principals, runtime callbacks, client ownership and every existing management operation. Preserve existing lifecycle and authorization guarantees before relaxing owner uniqueness.
3. Extend existing account/space allocation, configuration, plugin management and node Providers through the authenticated outbound transport. Enforce computer use at actual startup and execution admission, including queued work and runtime callbacks, as well as directory reads. Verify the production ingress without granting remote execution before its complete authority path is ready.
4. After backend completion, refine the existing user and Admin flows together, including resource occupancy, queuing, revocation, reconnect, performance isolation and per-device recovery. Add Windows through the same capability interfaces afterward.

## Performance requirements

The first frontend directory comes from center metadata. Each environment has independent freshness, completeness, readiness and failure state. Remote searches publish partial results as nodes finish. Catalog failures never establish deletion, and inactive environments do not start merely to refresh a list.

Directories use bounded resumable enumeration or node-local scan snapshots; a page must not repeat a complete recursive scan and sort. Only expanded levels and visible rows require reads and DOM nodes. File contents and Session history use versioned windows. Cache keys include authenticated account, environment and version; retention is bounded and access revocation invalidates affected entries.

Node queues and global admission have separate bounds. Interactive control and content have reserved capacity independent of bulk transfers. Cancellation follows the owning request through Gateway, tunnel and node; closing one view must not cancel another view's shared read. Reconnect resumes bounded revisioned metadata rather than sending every file or transcript.

## Alternatives considered

**Browser connections to independent Gateway URLs.** Rejected for this release: organization login, project authority, credentials and native-resource routes need one verified directory and routing owner. Every browser would otherwise implement deployment federation.

**Add a computer selector to account/project IDs.** Rejected: one account can own several personal environments, while a running process can change generation. Node names, ports and display labels cannot preserve Session ownership.

**Span one collaborative project across computers initially.** Deferred: each project keeps shared execution, document ownership and durable writes on one selected computer. Different projects may be placed on different computers.

**Wait for all nodes or mirror all file trees centrally.** Rejected: the slowest node controls response latency, and indexing, memory and transfer cost grow with every remote directory. The center retains bounded summaries; nodes own file enumeration and search indexes.

## Acceptance criteria

- One account uses multiple personal runtimes on the same computer and on different computers, subject to current grants and quotas.
- Different users have different allowed computer/runtime sets; every working view identifies its actual device and runtime.
- Existing Admin operations retain their policy scope when the selected computer changes; a delayed response or action cannot inspect or mutate a different runtime. Organization/account/project quotas remain shared across their runtimes.
- Collaborative projects can be placed on different computers while each project remains hosted on one computer.
- An invitation or project membership cannot authorize entry or execution without the hosting computer's use permission. Existing personal and project directories retain their granted ownership.
- Two runtimes contending for one desktop cannot interleave control; independent desktops remain usable concurrently. Revocation and uncertain cleanup preserve existing confirmation requirements.
- Current account and project authorization is rechecked for discovery and execution. Retired, disabled and cross-organization identities cannot authorize work.
- Environment identity survives Gateway replacement and ordinary process generation changes; released Session data is not rewritten.
- A slow or unreachable node cannot delay healthy-node results, browser input or stop requests. Large-directory, constrained-network and bulk-transfer scenarios exercise built frontend assets and real Gateway/node routes.
- Enrollment, control and mutation receipts bind node identity, environment, generation and operation ID. An uncertain stop never releases process ownership or starts a replacement elsewhere.
- Complete multi-node backup/restore remains refused until every owning node's data and stopped writers are accounted for. Node and center backups identify their actual coverage.

## Risks

Directory discovery alone does not enable remote execution. Credentials, principals, plugin state, resource admission, archive identities and computer-local paths require coordinated deployment of their Runtime-aware implementations. Frontend module releases require compatibility admission; arbitrary node plugin graphs cannot be injected into one page. The performance requirements need reproducible measurements and browser input evidence before numerical release budgets are adopted.
