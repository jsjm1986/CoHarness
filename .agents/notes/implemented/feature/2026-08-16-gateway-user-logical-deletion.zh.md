# Agent Note: Gateway 用户逻辑删除

Status: implemented

[English](2026-08-16-gateway-user-logical-deletion.md) | 中文

## 问题

管理端用户页面可以创建、禁用和重置账号，但没有删除操作。物理删除不安全，因为项目、对话、内容文件、用量记录和审计事件仍通过外键引用用户。只保留一个完整配置的禁用账号，也会让会话、项目授权、运行时凭据和模型 intake 凭据继续存在，容易被误用。

## 决策

`DELETE /admin/api/users/:id` 执行逻辑删除。Gateway 为账号的本机 Runtime 持有确认停止操作，并要求所有电脑上的实例已停止或受匹配的静止回执保护，才把账号标记为禁用并写入 `users.deleted_at`。远端进程尚未确认时拒绝删除。它撤销会话、清除 Runtime 凭据，移除项目成员、用户模型授权、账号／Runtime 回传凭据及用户专属额度，并记录 `admin.users.delete`。活跃用户计数、列表、用户名查询、认证、内部公共 ID 解析、目录授权和新 intake-token 签发都会排除已删除行。工作目录、Runtime 私有数据、对话、内容元数据、模型用量、用量告警和审计行继续保留，用于历史与恢复；用户名继续保留。

当前登录管理员不能删除自己。若删除一个活跃管理员会导致没有其他活跃管理员，也会拒绝删除。禁用和降权仍使用同一条最后管理员规则。已删除账号不会再由管理端 API 返回，因此后续变更得到 `404`；重复删除按不存在处理。

SQLite schema 版本 5 为既有数据库加入 `users.deleted_at`。PostgreSQL migration 006 加入时间戳和活跃账号查询索引。SQLite 导入会把删除时间带入 PostgreSQL。PostgreSQL 登录事务在创建会话前重新检查并锁定活跃用户行，因此并发删除不会在撤销后新建会话。

### 并发项目变更与授权投影

项目创建、邀请创建/接受及成员变更会先共享锁定未删除账户行，再取得项目或关系行锁。启动恢复在插入缺失分配记录前也会持续持有用户行保护，避免账户清理后又按旧查询结果分配实例。删除要么先于该查询完成，要么等待项目变更提交后再移除其运行关系。该顺序防止成员插入在账户清理后遗留，并避免邀请行所有权与用户外键锁之间形成环。PostgreSQL 迁移 073 移除涉及已删除账户的旧项目成员与邀请；项目所有权、文件以及历史对话、用量和审计引用保持完整。

认证用户发起的创建与邀请接受，在获取项目锁或节点分配锁前保留有效账户及组织成员行。接受要求项目活跃，并在邀请锁之后检查组织可用状态；认证创建在等待分配之后检查可用状态。参与账户被拒绝时使用带类型的403响应，包括保留的已删除账户。Gateway 从认证身份推导创建参与者、所有者与创建者；服务调用省略参与者时允许受信任的内部维护。发出邀请在获取项目锁前保留发起者及收件人的账户和组织成员行，再验证当前管理权限与作用域可用状态。收件人不可用沿用 user-disabled 冲突；发起者及作用域被拒绝时使用403。SQLite 将资格读取、过期邀请更新及发布放在同一即时事务内。被拒绝的创建沿用既有[目录补偿策略](../bug-fix/2026-10-23-project-creation-transactions.zh.md)。

事务后的目录授权投影通过 `GatewayUserService.isDeleted` 确认删除。两个第一方存储都区分保留的删除标记与未知 ID。确认并发删除后返回 `deleted`，不声称完成写入或重启；未知账户和无法核实的失败仍作为错误处理。若实例解析与删除核实同时失败，会保留两个原因。文件系统失败沿用已有处理。[升级指南](../../../../docs/upgrade-guide/v0.2.1-rc.1.coharness.1/project-account-deletion/guide.zh.md) 说明部署与自定义适配器要求。

### 模型配置与历史用量

个人模型授权、额度变更和 intake-token 签发会在整个事务中共享锁定未删除账户。删除要么让新写入被拒绝，要么移除已提交的结果；旧查询结果不能重新创建这些配置。迁移 074 清理已删除账户的旧模型授权和个人额度。已有 intake 凭据仍可提交具有执行记录证明的历史用量；已删除用户的无证明用量及模型注册会被拒绝。正常删除端点会在全部实例的静止得到证明后，移除账号和 Runtime 回传凭据。保留的历史凭据不授予模型派发权限。

## 后果

管理员可以撤销访问，而不破坏审计、用量、协作历史或本地恢复所需的记录。已删除账号从正常账号流程中消失，不能重新启动运行时或获得新的模型凭据。其本地 home 与用户名仍被保留，因此恢复账号必须走未来明确的恢复流程，不会静默地用同名创建新身份。

## 验证

Gateway 聚焦测试覆盖 SQLite 逻辑删除、保留审计行、移除项目成员、停止实例、最后管理员拒绝、API 禁止自删、运行时停止、会话失效、隐藏用户和删除审计。管理台测试覆盖 DELETE 请求和确认弹窗。Gateway 类型检查与管理台生产构建通过。配置 `HGW_TEST_DATABASE_URL` 时，PostgreSQL 集成测试会执行 migration 6 的覆盖。

真实 PostgreSQL 锁测试让项目成员变更、邀请接受与实际账户删除服务交错执行。Gateway HTTP 快照覆盖管理员并发修改成员及删除账户，确保不会恢复访问。迁移检查在移除失效授权时保留项目文件、私有对话和模型用量。授权投影测试区分已删除、禁用与未知账户，并在无法确认删除时保留失败原因。

## 曾考虑的替代方案

**物理删除用户并级联所有引用。** 否决，因为这会销毁审计和用量归属、删除对话历史，并需要削弱或重写持久外键。

**只把账号标记为禁用。** 否决，因为项目成员关系、运行时凭据、模型授权和 intake token 仍会被配置，账号也仍会出现在管理流程中。

**删除后允许用户名复用。** 否决，因为旧审计、对话和文件系统记录会在两个身份之间变得含义不明；现有企业范围唯一用户名约束会被有意保留。
