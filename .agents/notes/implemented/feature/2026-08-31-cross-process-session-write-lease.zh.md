# Agent Note: 跨进程会话写租约

Status: implemented

[English](2026-08-31-cross-process-session-write-lease.md) | 中文

## Problem

JSONL 后端的写句柄认领只在单个后端实例内部排除第二个写入方，其下的跨进程层是一个"创建后探测"锁文件：`open('.locks/<id>.lock', 'wx')` 加记录 pid 的活性检查与失主删除。它携带着整个陈旧锁问题族——死亡持有者的文件必须探测后删除，探测可能误判外来或被复用的 pid，而删除本身可能与存活所有者的重建相竞。两个进程——滚动部署中的两个 Gateway 副本，或宿主与 SDK 运行时并存——需要一份仲裁者位于所有写入进程之外的持久写所有权，因为没有任何写入方能活过所有故障模式。

## Decision

`SessionWriteLease`（packages/session/session-persistence-jsonl/src/lease.ts）在 `<root>/.locks/<encoded-id>.lock` 上持有内核锁，贯穿写句柄的整个生命期：POSIX 经由预编译 `@deepseek-ai/node-addon-system/flock` 绑定以非阻塞 `flock(2)` 加锁（以已发布 npm 包消费；`native/landlock-run` 仍是本地原生源码的归属地），Windows 持有由规范锁路径派生的命名内核信号量（计数 1，`CreateSemaphoreW`，实现在 src/win32.ts 既有 koffi 绑定旁）——零文件系统足迹的内核对象，随最后一个句柄关闭而销毁。竞争映射为 `SessionAlreadyOwnedError`；持有者的描述符或句柄关闭时内核释放锁，包括任何形式的进程死亡，因此崩溃的持有者从不阻塞后继者，也不存在任何过期簿记。活着但卡死的持有者保有锁直到其进程退出：剥夺停顿写入方的所有权被否决，因为其复活后的追加会撕坏日志；POSIX 上删除锁文件仍是该场景的显式放弃手段。由于 POSIX 锁指向 inode 而非路径，获取后会校验所锁 inode 仍是锁路径上的文件，否则重试。锁在 `openHandleAsync(id, 'write')` 时于根目录 `.locks/` 下获取，而非日志旁，因此未物化的会话仍不留工件足迹；释放从不删除锁文件，保住后续加锁者用于校验的稳定 inode。

**旧版 pid 记录。** 被替换的机制留下的文件会被旧版本进程读取为 `{pid}` 记录。因此获取以独占方式创建；当文件已存在时先读其记录：存活 pid 与旧版持有者拒绝的方式完全一致地被拒绝——这也覆盖内核锁持有者，因为它发布同款记录——而死亡、缺失或自持的记录则继续进入 `flock` 仲裁。持有锁时把记录改写为自身存活 pid，使旧版竞争者看到的仍是存活所有者而非可能被其在 flock 之下删除的残迹。同一根目录上的混合版本写入方因此在两个方向上保持互斥；残余窗口是一份死亡记录的旧版文件在接管时被旧版进程删除重建，由 inode 校验吸收。

## Alternatives considered

**创建后探测的 pid 文件（本机制替换的前身）** —— 存在性加锁文件加 pid 活性探测加失主删除。它保留了陈旧锁恢复，但本质是一个微缩的分布式算法，每一步都与其所判定的所有者相竞：pid 复用、外来 pid 的 EPERM、探测到删除的窗口，且底层没有任何仲裁原语。内核仲裁删除了整族竞态，代价是一个原生绑定依赖和上述卡死持有者语义。

**TTL 记录加续约与 rename 认领** —— 上游评估后以同一理由否决的设计：续约定时器、丢失检测与接管认领仍允许有界的双写重叠（一个续约间隔）。

**`proper-lockfile`** —— npm 生态对同一 TTL 模型的"过期判定加 touch"实现。它保留"先删后建"的接管竞态，用 mtime 加 inode 检测失主（弱于 owner 令牌），且自 2021 年起再无发布。

**Windows 共享模式独占打开（`CreateFileW` 拒绝 `FILE_SHARE_WRITE`）** —— 持有期间钉住锁文件的名字与目录：仍打开的句柄会阻塞会话根目录的递归删除与临时根清理。命名信号量保住内核仲裁，且文件系统足迹为零。

**POSIX 也手写 ffi（经 koffi 调 `flock(2)`）** —— 预编译绑定把绑定选择与异步 errno 处理收敛在一个受审计的包内；Windows 侧保留 `win32.ts` 已有的 koffi 绑定。

## Consequences

跨进程排他需要对应平台的预编译系统绑定、每个被写入的会话 id 在 `.locks/` 下持有一个由释放刻意留下的锁文件，以及卡死持有者规则：卡住的进程阻塞该会话的写入方直到其退出。它换来的是即时崩溃恢复（无等待期）、零续约流量，以及删除了探测式设计只能"管理"而非"消除"的全部接管竞态。咨询式 `flock` 在部分网络文件系统（NFSv3）上不可靠；位于此类挂载上的根目录会退化为仅进程内排他。POSIX 上删除活跃会话的锁文件按设计即放弃排他——harness 自身从不这样做。
