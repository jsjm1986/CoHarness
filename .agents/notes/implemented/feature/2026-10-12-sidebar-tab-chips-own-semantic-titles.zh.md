# Agent Note: 右侧边栏标签芯片自有语义化标题呈现

Status: implemented

[English](2026-10-12-sidebar-tab-chips-own-semantic-titles.md) | 中文

## Problem

右侧边栏芯片此前渲染的是标签注册表在打开时捕获的纯字符串。对 `tool-details` 而言那是原始调用 id（`call-9`）；对 `workspace-file` 而言是资源的完整路径；`changes-review` 则完全没有图形符号——而终端、浏览器、定时任务与指南芯片早已携带带图标的实时语义标题。标签条混合了不同的标识风格，用户看到的 id 是持久化地址而不是标签名。

## Decision

每种标签类型注册一个 `sidebar.right.pane.tab.title` 渲染器，自有其芯片的图形符号与文字；注册表捕获的字符串降级为兜底值而不再是呈现层。通用侧栏外壳不持有任何类型专属知识。

- **工具详情解析的是调用而不是 id。** `toolCallPresentation` 遍历所属会话已加载的窗口——正在运行的调用加上 tool-result 表层的 `subCalls` 树（嵌套的 `run_code` 分派也能解析）——返回线上 `name` 以及详情主体渲染的卡片种类（`resultView.card`，其次 `callView.card`，`generic` 归一化为无）。芯片把该名称与卡片意图符号配对（终端提示符、被编辑的文件、搜索、阅读、网页标记；通用或未解析时为扳手），使图标表达的是主体的内容形态而非按工具名贴牌。加载窗口之外的调用——恢复的标签页、滚出窗口的调用——保留捕获的 call-id 文字与通用符号。
- **工作区文件在文件类型符号下显示基名。** `WorkspaceFileTitle` 用完整捕获路径交给 `FileTypeIcon` 分类，但只显示其基名；无末段的路径原样保留整个标题。
- **变更评审把文件笔符号与本地化的捕获标题配对**（`Turn N review`），后者本就由定义在打开时正确生成——缺口在符号而非文字。
- **面板的边框控件并入标签条的圆形图标词汇。** `.iconButton` 从 `--dsw-radius-sm` 改为 `--dsw-radius-full`，与旁边 dockkit 标签条按钮一致。

## Alternatives considered

**外壳按标签类型做一张通用图标映射表。** 放弃：这会倒置注册表的所有权——外壳需要掌握每种类型的语义，而每种类型本就声明自己的主体与标题槽位。

**打开时捕获一个更好的标题字符串。** 放弃：这会冻结运行状态——调用落定后卡片种类可能变化（通用调用意图 → 终端结果），而捕获字符串是静态的。渲染器在读取时解析，在窗口内保持实时。

**复用 ui-tool 按工具名映射的图标表。** 放弃：那张表按名称为会话行内工具贴牌；芯片的职责是命名详情主体渲染的卡片，这正是工具声明的渲染意图本身已编码的信息。

## Consequences

芯片仅在成员级变化时重绘（对 `{name, card}` 做 `shallowEqual`），调用落定不会使标签条抖动。未来的卡片种类只需扩展符号分支而不动外壳；call id 仅在窗口外标签的芯片上仍可达。`sidebar.right.pane.tab.title` 槽位现已成为新标签类型需要实现的完整契约：注册它，芯片即天然语义化。
