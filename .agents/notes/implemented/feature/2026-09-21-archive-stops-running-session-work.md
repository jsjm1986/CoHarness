# Agent Note: Archiving a Session with running work

Status: implemented

English | [中文](2026-09-21-archive-stops-running-session-work.zh.md)

## Problem

Archiving was a pure visibility write: `WorkspaceRegistry.archiveSession` added the id to the registry-global archive set and nothing else. A Session archived in the middle of a turn kept running out of sight — the agent, its tool subprocess, and its model requests continued to completion — and the archived row deliberately shows no status dot, so nothing told the user an agent was still spending tokens. A background subagent, an owned job, or a due reminder could likewise keep working or start a new turn in a hidden Session. The Web surface never disposes an Agent, so the exposure lasted until the Host process exited.

## Decision

Archive never hides running work. The registry owns the rule and declares one capability seam for it: `workspace/session-activity` (waterfall) asks providers what still runs for a Session; `workspace/session-stop` (parallel) asks them to stop it. Providers register on the root the way any plugin registers a listener, so the workspace package knows no job or subagent vocabulary. The `SessionActivityKindMap` is empty in the workspace package: the job registry seam, the Subagent runtime, and the Schedule plugin merge their own families (`job`, `subagent`, `schedule`) from a module both its faces import, and a consumer that renders them imports those modules for its cases and falls through to a generic line for any other key. The `turn` family is installed by the registry itself, answering for every Agent the `agents` service publishes — this repo's session-persistence → format-catalog chain makes workspace transitively reachable from the Agent program, so an Agent → Workspace import would close a project-reference cycle and the install cannot live on the provider side.

- **Refuse by default.** `archiveSession(sessionId)` rejects a non-empty activity answer with `WorkspaceActiveSessionError`; the api-proxy maps it to `session-active`, whose details carry the families with item ids and labels. A caller that did not ask to stop work never hides it, whichever client or SDK it is.
- **Stop on request, after the write.** `archiveSession(sessionId, { stopActivity: true })` skips the activity check, writes the archive, and then dispatches the stop event: the durable archive set is what the pre-step gate reads, so every wake a stop induces — a cancelled child's settlement, a queued follow-up — is already blocked. The stops are issued and never awaited to settlement, so the RPC returns once every provider's request is out and the user's row hides at once; a stop that fails is a logged warning, not a reason to undo the archive.
- **The stop is the user's stop.** The registry-installed `turn` family cancels the turn with `agent.cancel({ kind: 'user' })` — the stop button's path, so the aborted tool call settles as a `tool/result` and the turn ends as `aborted`, but without the button's `keepInbox`, so queued input is discarded with a logged inbox splice. The job registry seam kills the owned jobs, installed by its constructor for every implementation through the abstract `list` and `kill`. The Subagent runtime cancels running subagent descendants (durable lineage, subagent origin, any depth, never a fork) as their parent would. The Schedule plugin answers only for a live root Agent — reminders arm and deliver session-locally, so a Session with no Agent has nothing running — reporting the Session's armed reminders from its maintained `schedule` projection, and on stop deleting them the way the user's `schedule_delete` does: one durable `schedule/change` delete change per active record inside the same agent-scoped queue its tools and live owner serialize on, so the stop lands behind a management write still in flight. Each request is contained on its own, so one child or job that throws does not keep the others running. Each provider owns exactly the vocabulary it already has: the workspace registry knows turns, the job seam knows jobs, the Subagent runtime knows children, the Schedule plugin knows armed reminders. No new event type and no write inside another owner's turn, so a restored Session continues from a regularly ended log and unarchive brings nothing back that was stopped.
- **Archived means no model step.** The registry's own `agent/pre-step` listener rejects a step proposed for an archived Session or for a subagent descendant of one, which the loop ends as `blocked` without a request. This closes the window in which a late waking delivery — a subagent settlement, a queued follow-up, a turn started between the activity answer and the write — would run a hidden turn, and keeps a child whose cancel was ignored from working for a parent nobody can see; unarchiving lifts the gate for the lineage.
- **The refusal carries the confirmation data.** A quiet Session archives without further interaction. The `session-active` refusal's `activity` details list exactly what the Host would stop — families with item ids and labels — so a client confirms by resending with `stopActivity` rather than keeping its own mirror of running state; restoring the Session does not resume the stopped work.

## Alternatives considered

**Refuse only, and make the user stop each item.** Reasonix desktop does this. It keeps archive non-destructive, but a stopped Session with a background subagent still running would be refused, and the user would have to hunt down subagents and jobs by hand. The refusal's activity list states the destruction, which was the only reason to prefer refusal.

**Wait for settlement before writing.** Codex bounds the wait at ten seconds and proceeds; MiniMax refuses when a turn lock survives its budget. Both keep the user's click pending on the slowest cancel. The stops here are cheap synchronous requests, the pre-step gate guarantees no hidden model step regardless of settlement, and a failed cleanup is acceptable, so the wait moved out of the request path entirely.

**Stop from the client before archiving.** OpenCode hides in the client and never stops, and its running Sessions vanish from the list while their status events continue. A client-owned semantic reaches one client; the registry-owned seam reaches every caller.

**Grey the archive action from a client-side activity mirror.** It would need its own derivation of running turns, running children, and owned jobs from the list projections, and it could disagree with the Host (an unowned job, a child without a Host Agent). One refused round trip yields the Host's own list instead.

**Install the `turn` family and the step gate on the Agent registry.** Upstream splits them that way; here the dependency direction is the reverse: session-persistence → format-catalog → workspace reachability means `dsh-agent` cannot reference `dsh-workspace` without a project-reference cycle, while `dsh-workspace` already imports the Agent type vocabulary for the stop it issues. The waterfall and parallel events still let the job registry seam and the Subagent runtime provide their families without new edges into the entity registry — each gained an optional type-only edge to `dsh-workspace` for the event types — and the registry self-installs the only family its own dependency direction permits.

**Report the families from the api-proxy.** It sees every live Agent, the job registry, and the lineage fields on Session headers, so it could enumerate turns, children, and jobs itself — but then it would know each owner's vocabulary (descriptors and labels, the parent-cause cancel, job ownership). The job seam and the Subagent runtime already own that vocabulary, so each family lives with its owner; the api-proxy keeps only the RPC refusal mapping, which reads the registry's error and the archive set alone.

## Consequences

An archived Session is guaranteed idle: it either was quiet, or its work was stopped the way the user stops it, and no step runs for it until it is restored. The pin-and-archive decision's "archive needs no confirmation" holds for quiet Sessions only; the running case asks. Stop settlement is best effort: a job that ignores kill or a child that ignores cancel is logged, and the pre-step gate keeps the Session from spending model requests meanwhile. The activity check and the archive write are two steps, so a turn starting between them is hidden, and every step whose pre-step precedes the write still runs with its tool calls, until the first step after the write is blocked. A Session with armed work but no live Agent — the wake that comes from a scheduled or external dispatcher rather than from the jobs and children the families report — archives without refusal; the gate then ends the follow-up step as `blocked`, so nothing spends model requests in the hidden row either.

Peer products surveyed for this choice: Codex and Kimi Code stop then archive; Claude Code stops by starving the remote session of writes; Reasonix and MiniMax refuse a busy Session, MiniMax after a bounded cancel; Pi has no archive but aborts before every session switch; OpenCode neither refuses nor stops. Every product that stops does so through its ordinary cancel path so the log ends regularly.
