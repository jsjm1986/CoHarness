# Agent Note: Admin 归档对话的人类可读阅读器

Status: implemented

[English](2026-08-26-admin-archive-conversation-reader.md) | 中文

## 问题

Admin 归档阅读器把每个事件封装都渲染成卡片。序号、会话标识、内部生命周期记录和原始 JSON 淹没了用户与助手消息，而只包含配置事件的归档看起来像损坏的对话。

## 决策

Admin 归档详情把无损事件页投影为聊天式阅读器。用户和助手消息使用带角色标签的气泡，成对的工具调用与结果使用紧凑工具卡，权限、沙箱、计划、审批和失败等选定事件使用简短系统提示。空消息内容不会进入聊天投影。会话标识、序号和原始 JSON 收进默认折叠的技术详情，其中也保留会话树和每个返回事件。长消息与结果文本在卡片内部滚动，窄屏保持相同的信息层级。

投影留在 Admin 客户端，不改变归档 API。API 继续返回用于导出和未来事件类型的无损事件；未知事件可以在技术详情中查看，不会被猜测成面向用户的消息。

## 已考虑的替代方案

**继续为每个事件保留一张原始卡片。** 不采用，因为仅日志事件和封装元数据会主导阅读顺序，让普通对话难以跟随。

**从阅读器响应中移除原始事件。** 不采用，因为管理员仍需要审计未知、失败或只包含配置的记录；折叠技术详情可以保留证据，又不会让它成为默认视图。

**在服务端生成 transcript 字段。** 不采用，因为展示标签和响应式分组属于 Admin 客户端，现有事件响应则继续作为导出和其他消费方的无损来源。

## 后果

管理员首先看到对话，需要序号、会话或 JSON 时再展开一个技术详情区域。只包含配置事件的归档会明确说明没有记录用户或助手消息，不再呈现为空白。工具输出和长文本在桌面与移动端对话框内保持有界。新的事件类型仍可审计，但在客户端添加明确的人类可读映射前不会进入聊天视图。

## 验证

Admin 归档页面测试覆盖消息与工具投影、默认折叠的原始详情以及只包含配置事件的归档。完整 Admin UI 测试套件通过，Admin Vite 构建也生成了更新后的生产 bundle。
