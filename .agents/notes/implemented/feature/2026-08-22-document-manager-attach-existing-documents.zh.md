# Agent Note: 从管理器加入已有文档

Status: implemented

[English](2026-08-22-document-manager-attach-existing-documents.md) | 中文

## Problem

文档管理器与对话输入框使用同一个持久用户文档存储，但管理器没有提供复用已有文档的操作。即使当前范围内已经存在文档，用户仍必须再次选择浏览器文件并上传。

## Decision

对话服务提供 `IConversation.attachDocument(sessionId, ref)`。它创建一个就绪的输入框草稿，其 `docId` 指向传入的持久 `UserDocRef`，然后把草稿 id 加入会话输入 shell。草稿条目记录自己是否拥有浏览器上传产生的持久文件。浏览器上传仍保持移除时删除文件的行为；管理器加入的文档只释放输入框元数据，不会删除存储中的文档。

`ui-documents` 插件在 `shell.overlay` 中拥有唯一的文档选择器宿主。Workbench 不渲染侧边栏底部时，该宿主仍保持挂载。侧边栏文档按钮请求管理模式；每个输入框的文档库按钮请求选择模式，并携带明确的 Session id。宿主收到请求时捕获目标 Session 和运行时，因此之后切换焦点不能改变附件目标。打开请求的监听器随宿主退出。

宿主接收 `attachDocument` 回调，并以捕获的 Session 委托给 `ctx.conversation`。目标缺失、Session 不可用、缺少对话服务或输入 shell 锁定时，附件操作被拒绝，不会回退到其他 Session。每个文档行显示“加入对话”/“Add to conversation”；加入成功后关闭管理器，拒绝时保留管理器并显示本地化失败提示。同一个持久 `docId` 在同一 Session 中重复加入是幂等的。

提交提示词仍使用现有的 `{ type: 'document', docId }` 内容部件，因此管理器操作本身不会新增会话事件或模型可见输入。

## Alternatives considered

**把存储内容读取成浏览器 `File` 后再次上传。** 否决，因为这会复制持久存储，增加不必要的传输与失败状态，也让输入框草稿移除时的所有权变得不明确。

**让管理器通过上下文访问或浏览器事件变更 `InputBar`。** 否决，因为对话服务拥有输入框变更。浏览器事件只请求打开选择器，不会附加文档。

**持久化独立的管理器加入事件。** 否决，因为加入草稿是浏览器本地状态，用户发送消息时已有文档 id 会被记录。

## Consequences

存储中的文档可以从管理器进入捕获的输入框，无需再次上传。移除这种草稿会保留持久文档，包括历史记录中的引用。该操作要求 Session 已加载，且输入框不处于提交接纳阶段；任一条件不满足时，管理器显示本地化失败提示。选择器的可用性随根 overlay 的生命周期保持，不依赖侧边栏操作是否可见。

## Verification

对话编排测试覆盖就绪草稿投影、持久 id 保留、重复加入幂等性，以及移除时不删除持久文件。文档管理器组件测试覆盖行操作、成功关闭回调和失败提示。包级与 Web GUI 检查覆盖组装后的操作和本地化文案。
