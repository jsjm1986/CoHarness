# Agent Note: Gateway 受管项目目录

Status: implemented

[English](2026-08-16-gateway-managed-project-directories.md) | 中文

## 问题

项目创建弹窗要求管理员了解并填写宿主机绝对路径，目录不存在时 Gateway 会拒绝创建。这让日常产品流程暴露了部署细节，并把一次逻辑创建拆成浏览器操作、Gateway 主机 shell 访问、Unix 权限配置和管理 API 登记。

## 决策

管理端创建流程的默认目录模式只接收项目名称。Gateway 去除名称首尾空白，要求名称是单个文件系统目录段，创建或复用 `<HGW_PROJECTS_ROOT>/<名称>`，把新建目录权限强制设为 `0770`，解析其规范路径，并将该路径保存为项目挂载。`HGW_PROJECTS_ROOT` 默认是 `~/harness-projects`；生产单元使用 `/srv/harness/projects/admin`。独立的[管理员宿主机目录浏览器](2026-08-17-gateway-admin-host-directory-browser.zh.md)负责现有目录模式。

受管名称拒绝空值、`.`、`..`、路径分隔符、控制字符，以及规范路径不同于直接子目录路径的结果。这会阻止路径穿越和既有符号链接逃出配置根目录。既有非目录项会得到与显式项目路径相同的稳定路径诊断。

JSON 和项目服务输入保留可选绝对 `path`，用于导入既有目录以及迁移期间停止写入的 SQLite 数据。显式路径仍不会自动创建，并继续经过规范目录和用户保留目录检查。删除项目会移除控制面与运行时记录，但两种项目目录都会保留在磁盘上。

Linux 部署会用 `root:harness-project` 和 `2770` 权限预创建 `HGW_PROJECTS_ROOT`。setgid 父目录让 Gateway 创建的 `0770` 子目录继承共享运行时组，而无需开放全局写权限。本地 macOS 部署配置由 launchd 账户拥有的可写根目录。

已保存的创建来源决定 Linux Runtime 启动与文档访问时的路径复核策略。只有用户发起项目可以使用 `HGW_USER_PROJECTS_ROOT` 的子目录，根目录本身仍为保留目录。启动从已分配的数据库所有者取得来源，请求字段不能放宽目录策略。规范路径、末级符号链接和其他保留根目录仍执行相同检查。

写入 Linux 项目的 Profile 和凭据前，Gateway 解析配置的执行账号，仅准备该项目 Runtime 根下固定的私有目录链、受管清单和 Gateway 生成的策略文件。每次所有权变更都基于保留的描述符；链接、组件替换和外部所有者会拒绝准备。目录保持 0700，受管文件保持 0600，其他文件不变。原子更新默认模型补丁时保留 Runtime home 的执行所有者，包括进程运行期间的策略变更。Unix 账号仍是部署前置条件，驱动继续在挂载命名空间内切换为配置的账号。

## 验证

SQLite 服务测试覆盖自动创建目录、Unicode 名称、`0770` 组权限、路径穿越拒绝和既有显式路径诊断。管理 API 测试证明 `{ "name": "产品文档" }` 会创建并返回规范目录。管理端 UI 测试证明默认目录模式只提交去除首尾空白后的名称；现有目录覆盖由[宿主机目录浏览器 Note](2026-08-17-gateway-admin-host-directory-browser.zh.md)负责。配置 `HGW_TEST_DATABASE_URL` 时，PostgreSQL 集成测试会执行同一受管目录辅助函数。

## 曾考虑的替代方案

**继续要求绝对路径。** 否决，因为这会让正常产品操作依赖宿主机 shell 访问，并要求管理员重复部署专属前缀。

**为目录生成不透明标识或 ASCII slug。** 否决，因为单个经校验的目录段已经可以阻止路径穿越，而保留项目名称能让中文及其他 Unicode 名称的宿主机检查与恢复更清晰。

**让新建目录全局可写，或由应用修改所有权。** 否决，因为全局可写项目数据不安全，而且跨平台 Gateway 没有可移植的用户/组查询能力。生产 setgid 根目录会确定性地提供所需用户组。

## 后果

在默认目录模式中，管理员只用填写一个有意义的字段即可创建项目，同时保存的路径仍明确用于授权、挂载、审计与恢复。部署只需决定一次项目根目录权限，无需手工配置每个受管子目录。既有绝对路径仍可导入，但继续要求手工配置 Unix 权限。重命名项目只改变目录中的项目标签，不会重命名目录，因此活跃挂载和外部引用保持稳定。
