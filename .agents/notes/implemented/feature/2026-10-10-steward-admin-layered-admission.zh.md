# Agent Note: 维护中枢准入把授权叠加在管理员身份之上

Status: implemented

[English](2026-10-10-steward-admin-layered-admission.md) | 中文

## 问题

维护中枢携带的权限超出普通组织管理员：常驻运行时、通向部署数据库的受审计 SQL 通道、对部署树的只读视野。只凭资格通道准入意味着闸口只有资格而不是角色；它还默默制造了死授权——有资格的普通成员能通过空间准入，却在执行写入时因为没有项目成员行而被拒，而 steward 空间按契约永远没有成员行。维护中枢的准入需要可见地强于管理员身份，而非仅仅是另一条通道。

## 决定

单一谓词裁决所有 steward 入口：活跃组织成员资格且 `role='admin'`，**并且**存在启用的 `steward_access_policies` 行。这一决定反转了[维护中枢空间 note](2026-10-10-steward-maintenance-space.zh.md) 中资格通道独立准入的原决定。

- **同一谓词覆盖每条路径。** 空间准入、会话读写、`claimInteraction`、`readableSessionIds` 与 `steward_query` 写批准应答者校验一律评估管理员成员资格加启用授权，因此绕过 API 直写数据库或残留的旧行都无法抬升任何人。
- **授予写入在授权事务内拒绝非管理员。** `ResourceAccess.set` 新增通道钩子（`checkEnabledOwner`），在 owner 行锁定后调用；`StewardAccess` 覆盖它要求活跃管理员成员资格，否则返回 409。撤销不经过该钩子，陈旧或降级后残留的行永远可以清除。
- **降级即撤销。** 读时角色复核意味着把管理员降为普通成员会立刻终止 steward 准入，既有的准入失效广播切断在途会话；授权行可以作为无害的陈旧行留在原地，由管理面清除。
- **迁移 052 删除死行。** 面向非管理员的历史授权从来不可用；删除它们让表只保留能生效的授权，且每次删除都会触发既有的准入失效触发器。
- **通道是被管理的一等对象，不是隐藏开关。** `GET /admin/api/steward` 暴露功能开关、空间/运行时事实和每个成员的可授予/已授权/当前生效状态；`/admin/steward` 页与逐用户资格卡让叠加规则可读——授权入口只对管理员开放，陈旧行仍可撤销。

## 考虑过但未采用

**保留独立通道并向非成员放开执行。** 放弃：让有资格的普通成员写 steward 会话需要给执行层 actor 检查开 steward 例外——用更大的权限面换更低的信任，与目标相反。

**不依赖管理员角色的 maintainer 式通道。** v1 放弃：任何人都可被授权需要同样的非成员执行放宽，且部署姿态要求维护者先已经是管理员。

## 影响

维护中枢由构造上就是仅管理员的通道。授予之前必须先提升为管理员，管理 UI 在原地说明这一点；持有残留授权行的普通成员读作失效授权，直到被清除。普通项目准入不受影响，`eligibleActors` 也不需要 steward 例外——每个获准的主体本来就已经是管理员。
