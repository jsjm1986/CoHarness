# Agent Note: Gateway 按来源锁定登录

Status: implemented

[English](2026-11-13-per-source-login-lockout.md) | 中文

## 问题

SQLite 和 PostgreSQL 两套 Gateway 登录服务只按用户名统计失败次数，并且在接受正确密码之前就返回 `locked`。任何知道用户名（包括管理员用户名）的人，每十分钟输错五次密码，就能让账户所有者一直无法登录。Gateway 还只从 TCP 对端读取客户端地址；在已部署的 Nginx 或 Cloudflare Tunnel 入口之后，每个请求的对端都是回环地址，因此任何计数器都无法区分来源。

## 决定

`gateway/src/login-source.ts` 为两套服务统一负责客户端地址解析和失败计数分组。当 TCP 对端匹配 `HGW_TRUSTED_PROXIES`（默认 `127.0.0.1,::1`）时，Gateway 从右向左遍历 `X-Forwarded-For`，选取第一个不是受信代理的跳；客户端自行前置的跳永远不会被选中。IPv4 地址按 `/32` 分组，IPv6 地址按 `/64` 分组。同一分组在十分钟内对同一用户名失败五次，只会在该分组上锁定该用户名。同一分组跨用户名失败二十次会锁定该分组；缺失地址或回环地址除外，因为所有未经转发的请求都共用它。PostgreSQL 为每个可区分的分组再加一个 advisory lock，每次登录都在用户名锁之后获取它。

## 曾考虑的替代方案

**保留按用户名、阈值更高的跨来源锁定。** 拥有大量地址的客户端，或能访问回环监听器并伪造 `X-Forwarded-For` 的本机进程，仍能锁定任意账户；分布式猜测改由 argon2 校验开销和审计记录约束。

**信任任意对端的 `X-Forwarded-For`。** 直接连接的客户端就能自选来源，绕过两种锁定。

**在锁定检查前校验密码。** 超过阈值后猜中密码会暴露该密码有效，因此已锁定的分组仍在接受前拒绝。

## 影响

错误密码洪泛只会锁定攻击者自己的来源，账户所有者可以从任何其他分组登录。共用一个 NAT 地址或 IPv6 `/64` 的客户端共用两种限制。部署必须在入口追加 `X-Forwarded-For`，并把非回环代理列入 `HGW_TRUSTED_PROXIES`；缺少该请求头时，所有请求共用回环来源，只有按用户名加来源的锁定生效。本记录收窄了 [PostgreSQL 登录准入忽略用户名大小写](2026-10-23-case-insensitive-login-admission.zh.md) 中的共享锁定；其大小写变体共享锁仍在每个来源内生效。
