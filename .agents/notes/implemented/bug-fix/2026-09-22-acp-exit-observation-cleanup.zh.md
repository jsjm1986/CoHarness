# Agent Note: 退出观察失败后继续完成 ACP 清理

Status: implemented

[English](2026-09-22-acp-exit-observation-cleanup.md) | 中文

## Problem

子进程提供方可能在受管进程仍存活时丢失退出观察。若将该拒绝视为 ACP 清理的终点，就会跳过终止操作。命令结果已拒绝也不足以证明退出：命令与其受管进程范围有各自的完成信号。

## Decision

ACP 提供方保留[消费方拥有的清理阶梯](../architecture/2026-07-27-dispose-ladder-to-consumer.zh.md)。协作式退出观察失败后，仍会执行终止操作并等待提供方确认最终退出。清理会保留单次观察错误，并按观察顺序聚合两次等待产生的错误。最终等待成功可以证明进程已完全停稳，但不能抹去此前的观察失败。

清理会观察命令拒绝，但不会据此提前返回。原始 `done` promise 仍由启动或结果的责任方用于失败分类。平台的进程约束和观察保证仍由子进程提供方负责；ACP 不会根据直接命令的结果推断这些保证。

[执行通道预算决策](../testing/2026-09-07-subagent-teardown-test-budgets.zh.md) 继续规定超时的选择。EOF 与终止宽限期保持不变。

## Alternatives considered

**首次观察失败后停止清理。** 这样可以及时报告错误，但受管进程可能继续运行，而终止操作尚未发出。

**将命令结果拒绝视为 spawn 失败，认为没有进程需要回收。** 提供方可能在进程启动后才拒绝命令观察。只有提供方对受管进程范围的观察才能证明进程已完全停稳。

**终止成功后丢弃首次错误。** 这样会隐藏提供方的观察失败，并把实际发生过错误的清理路径报告为正常。

## Consequences

清理可能在成功终止子进程后仍然拒绝。调用方既保留原始失败事实，也不会因此省略剩余清理尝试。辅助函数仍归 ACP 提供方所有；它不增加子进程 API、重试策略或计时器。

真实进程回归测试覆盖首次观察失败、两次等待分别失败，以及子进程仍存活时命令结果已拒绝的情况。受控的最终等待屏障防止 dispose（资源释放）提前结算，真实退出结果则证明终止已完成。启动测试会同时保留取消或协议错误与清理错误。各提供方的进程约束保证仍须由对应原生平台运行验证。模型可见诊断与成功对话记录保持不变。
