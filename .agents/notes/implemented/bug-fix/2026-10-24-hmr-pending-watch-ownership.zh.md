# Agent Note: HMR 在就绪前持有配置监听

Status: implemented

[English](2026-10-24-hmr-pending-watch-ownership.md) | 中文

## 问题

HMR 配置辅助模块先打开 Chokidar 监听器，等到就绪后才登记清理 effect。就绪尚未完成时卸载 HMR，可能让已经分配的原生目录监听脱离已销毁提供者。之后的就绪回调会在 effect 登记失败后关闭它，但就绪仍待决时没有清理动作。

## 决策

在等待就绪前登记监听器清理。销毁会结束启动等待、关闭监听器，并等待已接受的刷新。启动期间被销毁的登记会拒绝，而不是返回可用的销毁器。启动失败仍会关闭监听器；关闭也失败时，`AggregateError` 同时保留两个原因。已有监听器继续处理排队的关闭后错误。

规范化配置路径的保留由 HMR 服务实例持有。内部监听辅助模块不持有进程级登记表；其中重复的全局表已移除。公开 `watchConfig()` 仍通过已有实例登记表拒绝重复规范路径及别名。

## 影响

提供者与根销毁在配置监听器的就绪事件到达前就已经持有它。事件延迟不会让监听器继续活跃。成功登记、串行刷新及公开销毁器保留已有语义。本变更只涉及 HMR 监听器，不证明包围所有者关闭时其他资源的通用完成顺序。

## 验证

源码测试启动真实原生 Chokidar 监听，只暂停 ready 事件的交付，销毁实际 HMR 上下文，并在释放就绪之前检查监听路径表为空。原实现会保留原生路径登记。已有用例覆盖规范路径别名、原生事件、缺失父目录、启动错误、自移除及刷新完成；受控关闭失败会保留原始启动错误。

普通 Node 的构建产物夹具在相同就绪屏障下仅销毁提供者，随后加载替代 HMR 提供者并登记同一路径。旧构建的辅助模块会留下原生监听路径，导致夹具失败。两种结果下，夹具都会恢复精确的原型属性描述符，关闭上下文与监听器，并删除临时目录。此处原生证据来自 macOS 宿主；其他平台由 CI 运行。

## 考虑过的替代方案

**等到就绪，再依靠较晚的 effect 登记失败。** 这样只会在就绪到达后清理，监听器在无界等待期间仍活跃。

**在监听辅助模块中保留第二个全局路径登记表。** 服务已经持有规范路径保留；模块生命周期没有为产品入口增加必要的去重保护。

**只报告最终的关闭错误。** 这样会隐藏原始启动失败，使调用者无法区分获取失败与清理未完成。
