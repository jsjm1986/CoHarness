# Agent Note: 维护期间已认证的节点控制

Status: implemented

[English](2026-11-17-node-maintenance-control.md) | 中文

## 问题

普通维护拒绝 Node Agent 的心跳后，控制租约会过期。租约丢失也会中断远端部署配置所需的认证连接。连通性不能证明 Runtime 进程已经停止，因此让控制租约过期不能建立安全的写者静止证明。

## 决策

普通维护为已有受管节点的 connect、heartbeat 和 disconnect 提供专用事务。该事务持有组织控制行直到提交，要求维护模式与调用 Gateway 启动时的写入代次一致，拒绝治理恢复审核状态，并重新检查主入口电脑、有效组织、当前凭据和受管接入状态。它不会把待接入或已退出的电脑转成受管状态。现有连接独占、条件续租、后继代次和精确代次释放规则继续有效。

首次接入继续经过业务写入闸门。服务状态下的 connect 可以提升待接入状态，因此保留业务写者；其事务在变更授权前读取当前服务准入，在接入失效通知完成后初始化并锁定仍处于服务模式的集群控制行，并持有锁直到提交。即使请求携带较早的服务状态判断，维护先取得锁后也会拒绝接入提升。维护专用的 connect、heartbeat 与 disconnect 不计入业务写者。停机所有者拒绝新的维护控制准入，恢复中状态或写入代次变化阻止该事务。正常 Runtime 执行、账号与项目授权仍然独立；成功的心跳或新的控制连接都不确认维护，也不修改 Runtime 状态。

## 考虑的替代方案

**让所有节点控制 URL 绕过维护。** 正常 connect 可以把待接入状态提升为受管状态。URL 豁免也无法区分普通维护、恢复中状态与旧 Gateway 进程。

**关闭租约并要求直接访问本机管理。** 这会阻止通过已有节点服务连接进行集中配置，并让健康身份在维护期间无谓过期，也不会提供额外的写者停止证明。

**把维护心跳计为业务写者。** 持续续租会让已经静止的部署表现为忙碌。控制行事务已经把租约修改与恢复串行化；独立的 Runtime 记录和维护确认继续决定静止状态。

## 后果

普通维护期间可继续访问远端管理控制，同时不准入新的业务执行。只有维护租约路径增加控制与恢复检查；服务状态下的心跳保留单语句实现。长时间断连仍可能使租约过期并需要后继代次，现有 Runtime 隔离规则保持不变。协议字段、凭据、持久身份与数据库结构均不变。

PostgreSQL HTTP 测试验证重复续租不会准入业务写者、重连重试、拒绝首次接入和待接入状态、Runtime 记录保持不变、拒绝经过认证的新执行、等待期间撤权、恢复等待租约提交，以及接入提升与维护竞争的两种完成顺序。无需密钥的组合记录在 PostgreSQL CI 任务中运行。这些隔离检查不代表已验证跨网络部署可用性。
