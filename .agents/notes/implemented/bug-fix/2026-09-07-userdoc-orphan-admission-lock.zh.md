# Agent Note: 恢复孤儿用户文档准入锁

Status: implemented

[English](2026-09-07-userdoc-orphan-admission-lock.md) | 中文

## Problem

本地可续传上传后端使用带 PID 的文件锁串行化准入和过期会话清理。运行时在持锁时停止会留下锁文件。通用文件锁工具有意不移除已有锁，因此后续每次文档列表请求都会等待后端 30 秒锁期限后失败；项目作用域列表再触发 Gateway 对应的上游超时，表现为作用域切换卡顿。

## Decision

本地后端在启动清理期间检查准入锁。如果锁内容是数字 PID 且该进程已不存在，后端会把锁原子重命名为当前进程专用的临时名称，并在获取新锁前删除临时文件。仍存活、格式错误、无法读取或已被并发移除的锁继续遵循通用竞争规则。恢复逻辑只作用于后端自己的准入锁；其他文件锁保留工具原有的操作员恢复语义。文档管理器会把 HTML 形式的 5xx 代理响应转换为本地化的“运行时不可用”提示，不再把代理标记直接渲染为错误内容。

## Alternatives considered

**让通用文件锁工具回收旧锁。** 不采用，因为锁龄和 PID 重用无法为所有调用方证明所有权；扩大恢复范围会削弱凭据、设置和清单协调的安全性。

**启动时无条件删除准入锁。** 不采用，因为替换进程启动时另一个运行时可能仍在完成准入操作；移除仍存活的锁可能导致上传冲突。

**继续只允许操作员恢复。** 不采用，因为孤儿准入锁同时阻塞读和写，最终表现为重复的 30 秒文档列表超时，而不是可操作的上传错误。

## Consequences

当记录的所有者 PID 已不再存活时，中断的运行时可以在下一次启动时自动恢复文档列表，无需操作员清理。原子重命名让恢复不会误删其他进程正在观察的锁；仍存活和无法读取的锁继续快速失败。锁文件仍是私有实现细节，代理生成的 HTML 失败内容也不再泄漏到文档面板；文档字节、会话记录和成功的 HTTP 响应均不变。

聚焦的上传、本地存储和原子写测试覆盖恢复及既有锁竞争行为；隔离项目 6 的孤儿锁后，同一列表恢复为 HTTP 200、44 毫秒。
