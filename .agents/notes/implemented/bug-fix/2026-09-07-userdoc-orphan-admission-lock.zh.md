# Agent Note: 恢复孤儿用户文档准入锁

Status: implemented

[English](2026-09-07-userdoc-orphan-admission-lock.md) | 中文

## Problem

本地可续传上传后端使用带 PID 的文件锁串行化准入和过期会话清理。运行时在持锁时停止会留下锁文件。通用文件锁工具有意不移除已有锁，因此后续每次文档列表请求都会等待后端 30 秒锁期限后失败；项目作用域列表再触发 Gateway 对应的上游超时，表现为作用域切换卡顿。

## Decision

本地后端在启动清理期间检查 `withFileLock` 实际创建的 `.admission.lock` 同级文件。只有进程探测返回 `ESRCH` 才能证明记录的所有者已经消失；格式错误的身份、权限错误和其他不确定探测结果都不能授权恢复。恢复者通过独立的 `.admission.lock.recovery.lock` 串行执行，再重新读取准入锁所有者，随后原子重命名并移除孤儿锁。因此，另一个写者获得准入锁后，第二个启动者不能依据先前的观察操作该锁。现有写者继续遵循通用锁工具的互斥规则。

恢复仅作用于准入锁。恢复操作本身被中断时可能留下协调锁；该锁需要操作员核验并清理，不进行递归自动回收。文档管理器会把 HTML 形式的 5xx 代理响应转换为本地化的“运行时不可用”提示，不把代理标记直接渲染为错误内容。

## Alternatives considered

**让通用文件锁工具回收旧锁。** 不采用，因为锁龄和 PID 重用无法为所有调用方证明所有权；扩大恢复范围会削弱凭据、设置和清单协调的安全性。

**启动时无条件删除准入锁。** 不采用，因为替换进程启动时另一个运行时可能仍在完成准入操作；移除仍存活的锁可能导致上传冲突。

**继续只允许操作员恢复。** 不采用，因为孤儿准入锁同时阻塞读和写，最终表现为重复的 30 秒文档列表超时，而不是可操作的上传错误。

## Consequences

运行时在准入操作中断后，只要能够证明所有者已消失且恢复协调可用，就能在启动时恢复文档列表。恢复不改变文档字节、Session 记录、成功的 HTTP 响应或上传预留。

回归测试在子进程退出后，用其 PID 写入真实锁文件名。两个启动者通过同步屏障观察同一孤儿锁，再验证后继写者的锁保持完整且准入仍然互斥。存活、格式错误和无法探测的身份都保持不变。真实 Web 组装中的后端重启和文档 HTTP 路由验证同一恢复路径。
