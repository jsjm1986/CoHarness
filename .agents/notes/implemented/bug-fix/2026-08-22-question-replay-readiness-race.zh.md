# Agent Note: 问题 replay 等待连接就绪

Status: implemented

[English](2026-08-22-question-replay-readiness-race.md) | 中文

## 问题

浏览器连接在 `ask_user_question` 等待期间重建时，Host 会在 mux 流打开后立即重放仍未解决的问题。随后客户端在连接握手完成后执行重连 resync，而 resync 会清空会话的待处理等待。根据调度时序，重放的问题可能短暂出现后消失，且没有第二次重放，导致模型继续阻塞而用户无法回答。

## 决策

`ConnectionController` 为每个连接代次缓存 mux 和 host 帧，直到 describe 与两条流的就绪握手完成且 `onConnected` 消费方回调返回，然后按到达顺序释放缓存帧。失败或停止的代次会丢弃缓存。这样会话消费方可以先清理旧代状态，再接收重放的待处理交互，同时保留 Host 持有的待处理问题和稳定 rpcId 语义。

## 考虑过的替代方案

**保留在 `onConnected` 之前交付 replay，并修改 `Session.resync`。** 否决：resync 还需要第二个协议级基线，才能区分重放请求和断线期间已解决的请求。连接代次已经有就绪回调，因此在该接缝处排序更小，也能同时覆盖批准和其他重放状态。

**只延迟问题和批准帧。** 否决：这样会让会话历史、队列和交互帧在不同代次可见，且顺序依赖帧类型。统一的代次缓存让所有 Host 和 mux 投影共享同一个就绪边界。

**忽略 replay，等下一次重连。** 否决：这会丢失待处理问题唯一的可回答帧，使 agent 一直阻塞。

## 后果

重放的待处理问题和批准不再因重连 resync 竞态被移除。握手失败期间收到的帧会被丢弃，不会让已失效代次修改客户端状态。就绪窗口会在内存中暂存少量流数据，但其生命周期受握手限制，并会在消费方回调结束后立即释放。

## 测试

连接生命周期测试现在断言：在 describe 响应之前到达的帧，只有在 `onConnected` 之后才会到达 mux sink。现有连接、会话和 manager 交互测试保持通过。浏览器问题编辑器 replay 测试在当前环境未能进入 workspace 初始化，因为 scaffold 的 workspace 目录对话框没有出现；该失败与本次修改无关。
