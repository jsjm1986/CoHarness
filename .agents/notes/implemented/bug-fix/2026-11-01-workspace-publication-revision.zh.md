# Agent Note: 工作区发布顺序归应用所有

Status: implemented

[English](2026-11-01-workspace-publication-revision.md) | 中文

## 问题

Gateway 只有在工作区元数据的 `(generation, revision)` 比已存发布更新时才保留它。若序号只属于单次发布器，同一应用中的注册表或 Gateway 传输替换后，它就会从一重新开始。Gateway 可能确认请求，却继续保留旧元数据；已经接收的旧请求也可能覆盖重新编号后的替换发布。

## 决策

应用内所有工作区发布共用一个根作用域拥有的序号。各发布作用域拥有取消与串行执行，而序号在注册表和传输提供方替换后继续保留。发出请求前同步分配序号，因此被放弃的请求总比替换请求更旧。达到协议规定的安全整数上限时失败，不会回绕。

序号通过根 effect 注册，活跃发布器将其作为数据保留。注销根贡献不会使已捕获的序号失效。启动身份仍归应用拥有，Gateway 继续独立执行运行时代际和当前电脑权限检查。

## 考虑过的替代方案

**把计数器放在注册表或传输提供方上。** 两者都可能在已认证代际不变时被替换。

**使用挂钟时间。** 时钟回拨与相同时间戳无法确定已接收请求的先后顺序。

**让 Gateway 接收较小序号。** 迟到的旧请求便可能替换当前元数据。

**再持久化一份本地序号。** 应用已经在提供方替换期间保留启动身份。跨进程顺序属于 Gateway 代际规则；本次修复不需要存储 schema 或新协议。

## 影响

HTTP 响应、目录字段、凭据和数据库 schema 不变。停止的发布器不再保留监听或请求准入，替换发布器则共享所属应用的发布顺序。[工作台决策](../architecture/2026-09-08-cordis-multi-session-workbench.zh.md)仍定义工作区身份与查看语义；归档序号及其归属保持独立。

## 验证

作用域注册表替换使序号从一、二继续增加到三。被放弃的旧请求迟到完成时不能替换新快照。根作用域隔离、安全整数耗尽、发布失败重试和释放期间回调继续满足其生命周期规则。真实 PostgreSQL 保留替换后的元数据，并拒绝另一账号和过期代际。两个 SDK 通过内置 profile 运行真实工作区存储与 Gateway 传输替换；完整旧版 Runtime 包会保留旧目录，无法通过相同场景。
