# Agent Note: 有界批量模型策略刷新

Status: implemented

[English](2026-08-28-bounded-model-policy-refresh.md) | 中文

## Problem

修改组织模型提供方、模型、凭据或额度时，Gateway 会串行刷新每个用户和项目的策略文件。每次用户刷新还会再次查询该用户，因此大型组织会让管理员请求或 Gateway 启动按主体逐次等待，并可能保留很长的文件和凭据工作链。

## Decision

Gateway 在每轮完整扫描中只枚举一次用户和项目，每类主体最多并发四项投影任务。刷新复用枚举返回的记录，写入器在准入后解析当前策略。权威启动检查通过后即可绑定 HTTP 监听器，因为新准备或转发的目标 Runtime 会独立执行当前策略校验。

Gateway 在绑定监听器后启动一个受生命周期管理的校准任务，维护恢复写入后也会触发。任务重试失败的 Runtime 时重新查询存储和策略，目录与所有者查询失败则按各自范围跟踪。既有的写入准入在每次投影前重新检查维护状态。关闭时取消等待中的重试，正在运行的工作结束后才释放相关服务。[触发合并机制](2026-10-23-model-policy-refresh-coalescing.zh.md)会请求下一轮完整扫描。

## Alternatives considered

**保留串行循环。** 放弃，因为延迟会随用户和项目数量线性增长，一个慢的文件系统操作会阻塞其他主体。

**使用无界的 `Promise.all`。** 放弃，因为大型组织会同时为每个主体发出策略、凭据和文件系统操作，压垮数据库连接池和主机 I/O。

**让每次管理员变更都等待完整的后台刷新。** 放弃，因为文件投影是最终一致的缓存；持久治理 revision 和运行时惰性检查已经提供权威恢复路径。

## Consequences

批量刷新每类主体最多并发四个投影操作。完整扫描仍需访问每个活动主体，耗时可能随目录规模增长。损坏的策略路径可能暂时使单个 Runtime 不可用，其他 Runtime 和 Gateway 可以继续服务。重试耗尽后，日志记录所有者或 Runtime 标识及错误码。单个用户和项目变更仍保留直接投影路径。

现有管理员性能接口读取本节点的校准快照。扫描等待期间仍可看到进度。最新完成的一轮提供问题总数及有限数量的重试中或失败目标。响应和最终失败日志使用目录标识以及允许列表中的错误码。诊断读取无需访问 Runtime 文件。

## Verification

Gateway 模型治理集成测试覆盖目录行复用、扫描未完成时的 HTTP 就绪状态、请求目标 Runtime 时的当前策略检查，以及策略文件故障后的独立恢复。测试也覆盖维护准入、关闭等待、经授权读取进度以及诊断数量上限与错误信息清理。
