# Agent Note: 有界批量模型策略刷新

Status: implemented

[English](2026-08-28-bounded-model-policy-refresh.md) | 中文

## Problem

修改组织模型提供方、模型、凭据或额度时，Gateway 会串行刷新每个用户和项目的策略文件。每次用户刷新还会再次查询该用户，因此大型组织会让管理员请求或 Gateway 启动按主体逐次等待，并可能保留很长的文件和凭据工作链。

## Decision

Gateway 只枚举一次用户和项目，然后为每种主体使用四个有界 worker 投影这些脱离的行。刷新路径直接调用投影写入器，不再执行第二次 `getById` 查询。启动和重试刷新使用同一有界批次。如果某个批次失败，会等待所有 worker 结束后报告第一个错误；既有的重试任务和运行时惰性 durable-revision 检查继续负责最终收敛。

## Alternatives considered

**保留串行循环。** 放弃，因为延迟会随用户和项目数量线性增长，一个慢的文件系统操作会阻塞其他主体。

**使用无界的 `Promise.all`。** 放弃，因为大型组织会同时为每个主体发出策略、凭据和文件系统操作，压垮数据库连接池和主机 I/O。

**让每次管理员变更都等待完整的后台刷新。** 放弃，因为文件投影是最终一致的缓存；持久治理 revision 和运行时惰性检查已经提供权威恢复路径。

## Consequences

批量刷新每类主体最多并发四个投影操作，数据库和文件系统不再接收无界突发。刷新仍需访问每个活动主体，耗时仍会随目录规模增长；临时失败可能让部分文件暂时停留在旧 revision，直到重试或运行时下一次使用修复。单个用户/项目变更仍保留直接同步投影路径。

## Verification

Gateway 模型治理集成测试验证完整刷新会使用已枚举的用户行而不进行按 id 查询，并写入预期策略。Gateway 类型检查及模型治理聚焦测试通过。
