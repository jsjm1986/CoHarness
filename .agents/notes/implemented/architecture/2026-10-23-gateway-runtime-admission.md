# Agent Note: Managed Runtime process admission

Status: implemented

English | [中文](2026-10-23-gateway-runtime-admission.zh.md)

## Problem

A single Gateway can launch a personal Runtime for every account and a shared Runtime for every project. Per-target lifecycle serialization prevents duplicate processes for one target, but concurrent targets can exhaust a Mac's memory and CPU during startup. Per-instance systemd limits do not provide a shared node budget and do not apply to the macOS local launcher.

## Decision

The [InstanceManager](../../../../gateway/src/instances.ts) acquires one resident reservation and one cold-start slot before policy materialization, maintenance admission, or process launch. Readiness releases only the cold-start slot. Confirmed process-tree termination releases the resident reservation; a failed termination retains its handle and reservation. Local child exit notifications trigger serialized cleanup, while startup failure and explicit stop use the same termination rule. Shutdown closes queue admission, cancels pending starts, and awaits their settlement before draining local processes. These rules complement the [Gateway startup ownership](../bug-fix/2026-08-18-gateway-startup-resilience.md) and [maintenance](2026-09-25-gateway-deployment-maintenance.md) decisions.

The [capacity controller](../../../../gateway/src/runtime-capacity.ts) admits distinct Runtime targets in FIFO order. A full resident budget waits for an existing process to stop or become eligible for idle reaping; it does not evict busy processes. Queue size and wait time are bounded, retries for the same target and start intent share their pending operation, and stop cancels that target's queued start. Warm Runtime calls do not acquire a cold-start slot. PostgreSQL and SQLite repositories enumerate active assignments before admission; supervisor survivors, including incomplete starts and stops, count even when they exceed a reduced limit. Uncertain survivor state is retained until termination is confirmed. Incomplete starts or stops refuse replacement immediately; recovery requires a successful administrator stop followed by an explicit start. Launcher rejection confirms that no process remains or returns a `RuntimeLaunchCleanupError` carrying the process handle for cleanup.

The node accountant spends a shared pressure credit at each launcher's allocation point, after policy and supervisor preparation. It first schedules waiting model and child-process work. Missing, stale, or exhausted credits wait under the committed node deadline and caller cancellation. Migration 064 records whether allocation is unverified, not started, waiting, or possible. A known unallocated starting generation cannot block bootstrap as an unregistered live Runtime; an admitted or unverified generation retains that protection until provider registration or confirmed termination. Changed deployment policy invalidates unused credits until a fresh sample, without releasing existing execution reservations.

Host observations carry process-monotonic capture time from before the sensor reads through publication. Sensor, checkout, maintenance and node-lock waits consume the same freshness interval. Ages immediately before and after a database clock probe enclose the actual capture time. Positive credits expire from the conservative lower bound and require that bound to follow the previous upper bound by the configured cadence. A fresh warning sets unused credits to zero immediately, preserving the latest ordering witness and warning horizon even when an older warning arrives late. This can delay relaxation until a demonstrably newer healthy capture arrives; uncertain ordering cannot clear a warning. Migration 072 adds the upper bound and invalidates unbounded unused samples without releasing active requests.

The macOS pressure sensor owns its native command through closure. Its sample deadline force-kills an uncooperative client, reports the failed measurement and publishes no positive observation. Sampler disposal joins this command and any accepted publication, so a stalled sensor cannot abandon a process or indefinitely retain shutdown ownership.

Queued selection locks the chosen request before conditionally debiting fresh pressure credits. The same debit checks the request deadline; a failed check leaves it queued or retires expired requests. Readiness observed before a database wait cannot authorize allocation afterward. Held-lock and delayed-clock regressions cover residual validity, observation order, immediate warnings and expiry between selection and reservation. Normal recovery still admits a newer healthy observation.

The transaction acquires the node row and retires expired queued requests through `harness.lock_node_resources`. `harness.schedule_node_resources` performs stale-generation cleanup, unregistered-process checks, equal-user/project selection and fresh conditional credit debit on that same PostgreSQL connection. Migration105 installs both invoker-owned functions. The caller retains the transaction through its Runtime ownership checks, result and commit; no eligibility or pressure result becomes a reusable authorization cache. Server-local scheduling removes network waits between selection and debit while retaining the current request deadline and physical occupation.

Node accounting and instance activity intentionally serialize under the configured statement timeout. Transaction-local lock waiting uses that bound; an unlimited statement retains the pool lock timeout. Other clients retain their pool settings. Contention exhaustion returns503 without replaying an operation or releasing uncertain reservations.

Activity admission acquires the assignment writer lock before checking account, membership, computer, ready state and generation in a fresh statement. A snapshot taken before the wait cannot authorize a withdrawn caller. Resource generation locks remain held through accounting.

Repository initialization repairs missing assignments without changing existing process state, credentials, or generation. A second coordinator or a Gateway restart does not prove earlier processes stopped. Active local assignments therefore also retain capacity; a coordinator lacking their process handle refuses replacement and cannot report a successful stop. The local launcher's JavaScript exit hook cannot run after `SIGKILL`, so automatic recovery of an unowned local survivor requires a separate verifiable process owner.

`startRequest.admission` resolves after bounded-queue acceptance, immediate slot reservation or warm reuse; `startRequest.completion` resolves only after authenticated readiness. The ordinary HTTP proxy awaits admission before returning its waiting response, so an already-full queue returns HTTP 503 `INSTANCE_CAPACITY` with `Retry-After`. After acceptance, HTML requests receive the existing 200 waiting page and API requests receive 503 `INSTANCE_STARTING` while startup continues. A later queue timeout or cancellation rejects completion and remains visible in admission counters, but cannot replace an HTTP response already returned.

Cold readiness spans the signed HTTP challenge, resource registration and ready publication under one process-monotonic deadline. Individual probes use its remaining time. Cancellation and expiry are checked after backend waits and before returning success; already issued publications can settle before physical rollback. Only HTTP transport, response data and challenge-proof failures retry as unavailable probes. A backend refusal retains its original error and initiates owned process cleanup; it cannot become a generic readiness timeout.

Validated node settings expose `HGW_RUNTIME_MAX_STARTING`, `HGW_RUNTIME_MAX_RESIDENT`, `HGW_RUNTIME_MAX_QUEUED`, and `HGW_RUNTIME_QUEUE_WAIT_MS`. Defaults are 2 cold starts, no emergency resident ceiling (`0`), 32 queued targets, and a 30-second capacity-queue deadline. A positive resident ceiling is optional; pressure admission still governs new starts. These settings are not a calibrated memory-per-Runtime result and do not establish that a 16 GiB Mac supports 300 personal Runtimes or 100 mixed AI tasks. Existing node-configuration records lacking additive settings read bootstrap values or the declared defaults; explicit malformed values still fail validation.

The public snapshot reports current and peak process/queue counts, rejections, queue cancellations and timeouts, target-identifier bytes, and fixed cumulative wait buckets. Identifier bytes exclude caller-owned request data and are not a measurement of total queue memory. One Gateway owner accounts for its managed processes on one node; independent Gateways sharing a host and unmanaged processes do not share this in-memory budget.

Browser form failures render localized HTML; the scope API retains JSON. A manual retry preserves the original Runtime and project and repeats authorization. Refused targets offer environment selection without falling back to another Runtime. Failure rendering retains the original server diagnostic and changes neither process admission nor supervision. Busy copy covers unavailable startup capacity without asserting that a resident-process ceiling was reached.

## Alternatives considered

**Use per-Runtime CPU and memory limits as the node budget.** These limits are platform-specific and their aggregate can exceed host capacity. Runtime process admission applies to both launchers; it does not claim to bound the CPU or memory used inside an admitted Runtime.

**Evict a resident Runtime immediately when another target waits.** Existing leases and task lifecycle rules own safe idle release. FIFO waiting with a deadline preserves those owners instead of terminating active work for capacity.

**Release after requesting termination or after a child root exits.** Descendants can retain resources and ports. Capacity is reusable only after the launcher's awaited termination completes; unknown termination keeps the reservation.

**Retry backend failures as an unreachable Runtime.** A database admission or publication refusal has different recovery and HTTP semantics from an unavailable probe. Preserve its failure while retaining the existing physical rollback and generation checks.

## Consequences

Cold bursts have bounded process starts and queue length, and retries cannot bypass the resident budget. Capacity exhaustion can delay or refuse a previously stopped space; lowering the limit does not terminate existing spaces. Runtime admission does not schedule Agent turns, LLM requests, tools, terminals, or their descendants within a resident Runtime. Those operations require their own cross-process resource ownership and admission; process-count limits alone do not protect the whole machine from mixed workloads.

Deterministic controller tests cover a 100-target burst, FIFO, both limits, cancellation, timeout, survivor accounting and idempotent release. InstanceManager tests exercise real local child startup, hot calls while another target waits, duplicate retries, queued stop cancellation, crash cleanup, retained reservations after failed termination and shutdown quiescence. [Real HTTP proxy tests](../../../../gateway/tests/proxy.spec.ts) combine the actual manager with a controlled launcher to verify queue-full refusal before readiness, accepted waiting responses and recovery after capacity release. Configuration tests reject invalid values and node-configuration tests cover persistence and additive-field reads. A [Gateway browser transcript](../../../../apps/web/tests/runtime-start-feedback.e2e.ts) covers personal/project startup refusal, manual keyboard retry, independent tab selection and metadata-only recovery. Its controlled admission failure does not establish host capacity. Timing and resident-memory calibration and a mixed-workload benchmark remain separate evidence.
