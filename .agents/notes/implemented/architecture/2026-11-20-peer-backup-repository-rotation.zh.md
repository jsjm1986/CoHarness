# Agent Note: 经核验的电脑间备份仓库退役

Status: implemented

[English](2026-11-20-peer-backup-repository-rotation.md) | 中文

## 问题

仅允许追加的仓库最终可能达到对象数、字节数或磁盘限制。附在已确认恢复点上的容量数据可能恰好在写入失败时过期。超期的恢复点也可能存在覆盖缺口。

## 决策

接收端单独记录带时间的存储压力，无需等待采集成功。治理库根据最近确认恢复点的时间计算新鲜度，覆盖缺口单独记录。

轮换为同一个范围建立新策略和独立的加密仓库，同时封存旧仓库的写入。获准的恢复继续使用原读取权限和原策略版本。退役需要管理员确认一个处于目标时限内、完整、范围相同并已由另一台电脑演练的新恢复点。该点至少保护至原仓库的最新恢复点。治理库检查未完成的演练与恢复，并在退役完成前保留拥有该点的新仓库。

只有接收端可回收获准退役的仓库。每批回收都锁定保留点对应的演练策略版本。策略停用或版本变化时暂停回收，需演练新的恢复点并重新审核。SQLite 在同一事务内写入永久标记并回收记录，最后由治理库记录完成。重试不能恢复已撤销的权限或重建同一仓库。普通 Restic 凭据没有回收权限。部署还原保留目标端的历史。组织治理重建保留封存与退役历史，未完成的回收需重新审核。

## 考虑过的方案

允许追加凭据执行 Restic 清理，会让受损的源电脑删除自己的恢复历史。直接删除最旧恢复点会在后续备份有缺口时丢失最后一个完整点。独立仓库轮换先为已核验的新恢复点保留空间，再批准删除旧仓库。

## 影响

同一接收端无法同时容纳新旧仓库时，轮换可能需要第二台接收电脑。回收让 SQLite 能再用释放的页，文件本身可能维持原来的大小。[备份参考](../../../../gateway/docs/peer-backup/README.zh.md#rotate)记录操作步骤。[覆盖和重新授权](2026-11-05-project-recovery-reauthorization.zh.md)继续负责范围验证和恢复权威。[源端空间准入](../bug-fix/2026-11-17-peer-backup-source-space.zh.md)继续负责暂存容量。

## 验证

隔离的 PostgreSQL 和 Restic Gateway 组合演练新恢复点，拒绝过早退役，并在保留点的策略停用或版本变化时暂停回收。重新演练后回收合成数据的密文仓库，并在后续采集后独立离线重开保留点。
