# Agent Note: Collapse serial governance round trips for tunnel nodes

Status: implemented

English | [中文](2026-11-06-governance-round-trip-collapse.zh.md)

## Problem

Remote node gateways reach the central PostgreSQL through an SSH tunnel at ~200ms RTT. Two hot paths multiplied that RTT by statement count. Each `NodeResourceBudget.observe` round crossed the link as ~7 serial statements (transaction, `lock_node_resources`, clock read, observation update, conditional schedule, commit), so every ~10s sample burned ~1.4s of tunnel time per node. Every `authenticateRuntimeToken` call — issued once per runtime→gateway internal API call — ran a 6-table join plus two authority functions, roughly one execution per second per node; together with background pollers it saturated the node pool and pushed user requests on `ubuntu-101` to 8–16s.

## Decision

**Server-side observation round.** Migration `121_observe_node_resources.sql` adds `harness.observe_node_resources(tenant, computer, sample, elapsed_ms, initial_limits)`: insert-or-lock the resource row, sweep expired queued requests, reject stale captures, recompute credits from the sample and stored limits, conditionally schedule, all inside one call. `NodeResourceBudget.observe` now sends `performance.now() - capturedAt` as `elapsed_ms`; the function adds its own entry-to-post-lock wait, so a capture that expires while queued for the node lock is dropped exactly as the former post-lock measurement required. `set_config('lock_timeout', statement_timeout, true)` at the top of the function reproduces the client wrapper's `lockWait: 'statement'` bound within the call's implicit transaction. The observation statement checks serving mode and the current write epoch. The sampler waits the configured interval after publication. This gives the next sample room to clear the database cadence check when transit time varies.

**Runtime-token authentication cache.** `PostgresInstanceRepository` memoizes `authenticateRuntimeToken` per `sha256(token) + cleanup` key with a short TTL (`HGW_RUNTIME_TOKEN_CACHE_MS`, default off except in the gateway, which sets it), single-flight dedup, and a bounded LRU map. `harness_access_invalidation` notifications already reach every gateway through the existing listener and clear the cache, and token grant/revocation write paths clear it on commit. `runtime_node_execution_allowed` keys node authority on `node_connection_epoch`, so a node restart rotates the epoch and makes cached entries inert regardless of TTL.

**Exact storage and request admission.** An explicit Runtime identity resolves storage through one owner query that checks organization, computer, owner and Runtime together. Owner-only selections retain ambiguity checks. HTTP and WebSocket admission synchronize access before process preparation and again after fresh account and project reads. They do not add another revision read immediately before those authority reads. The final synchronization still cancels revoked requests before forwarding, and neither change extends an authorization cache.

**Exact prepared conversation operations.** History, create, send and receipt queries hold a local reference to a tracked generation. Its supervisor and PostgreSQL reads run outside the lifecycle queue. A process replaced during those reads invalidates the result. The volatile database function checks the current browser, owner, node, scope, lease and serving write epoch, records activity, and reads a new authority snapshot after waiting for the instance row. Each SQL command takes its own snapshot within one network round trip. The exact access revision and earliest session or node deadline fence the retained response. Completion preserves the reference through a generation-bound activity write so an idle scan cannot stop the process while activity is settling. Renewal stays with the entry's login validation. The Host verifies the individual conversation and continues to own creation, input durability and receipts. The optimization applies to personal and legacy shared projects. Cold preparation retains its existing owner.

**Ready project history and directory reads.** The owning Gateway uses the retained process reference and shared instance lock. A published project read qualifies the actor and captures the exact node, Runtime, volume, writer epoch and name version. Ordinary node-service forwarding passes the authenticated entry node into this check while the browser's selectors match the signed request. The attested local volume resolves the project name. After that read, a fresh governance statement checks the same binding, access revision and Runtime generation. No governance transaction spans the volume read. A storage mismatch or lost qualification refuses dispatch, and the Host still enforces individual Session visibility. Project writes use the ordinary writer path.

**Forwarded personal Sessions.** The destination can verify a request-bound signature with previously published key bytes. Exact ready admission rereads the issuer's current key and lease together with the browser and Runtime checks, then confirms that the access revision stayed current across the instance lock. Dispatch requires the single-use nonce and carries the earliest login, node lease or assertion deadline. A missing candidate or unavailable ready admission uses the general route. The PostgreSQL Gateway fixture measures one fewer governance round trip on an issuer cache miss and checks that rotated keys and expired leases cannot qualify.

**Target connection availability.** Waiting for an idle transport to close can delay unrelated work while a reusable connection for the requested node is already available. A return or close wakes eligible waiters. The transport pool retains physical capacity accounting until closure and checks the lease before giving a reused stream to a request. Acquisition observations distinguish queuing, lease verification and opening a service connection.

**Personal execution receipt.** The personal root and original interactive input each use one database statement. The loopback carrier can recognize a previously verified personal bearer even after its cached authorization expires. This supplies only the Runtime coordinates for the statement. The carrier retains the writer count and applies the process shutdown check. The statement checks the exact Runtime credential, managed lease, serving mode and write epoch as part of the write. The Session lock serializes receipt identity and lineage. The account and membership locks make the computer grant read observe a revocation committed during the wait. A failure response checks fresh bearer authority before returning details about the requested Session. Projects, inherited lineage, edits and dispatch assertions use the shared maintenance admission check and current bearer authorization. Unknown bearers require authentication before body buffering. Host receipt confirmation flushes and reads the exact committed inbox event.

The owning Gateway records the exact personal Runtime coordinates during successful execution and control authentication. The bounded coordinate cache survives invalidation of ordinary authorization entries. After an authorization update or a reconnected control stream, an existing Host can register a new root in one query. Integration coverage compares two queries on an unknown coordinate against one on a verified coordinate and confirms that revoked or stale credentials commit no root or input.

**Prepared empty personal drafts.** Browser admission qualifies the current login, computer grant, Runtime generation and serving epoch. The local stop check and writer span cover forwarding. A signed request step lets the [execution provider](../../../../packages/context/gateway-execution/README.md#execution-authorization) leave a fresh unmaterialized draft unregistered. The first prepared prompt combines root registration with receipt publication and holds the exact Session lock through commit. Mixed versions without the signed step use ordinary registration. Stored Sessions, project Sessions and operations needing lineage keep their normal qualification.

**Execution before the first model output.** The [execution store](../../../../gateway/src/execution-identity.ts) locks the Session before observing the receipt or scope. A single statement records input entry and merges its witnesses. The scope lookup, revision increment and scope insertion share another statement, so concurrent retries preserve the same scope and revision. A single immutable receipt can supply its existing actor list. An ordinary personal execution check with an exact scope reviews bearer, lease, grant and epoch in its statement. Other capabilities and unverified-history changes keep their own permission and maintenance checks. Each actual model dispatch remains checked.

An original personal root receipt can enter through its own fenced statement using previously verified Runtime coordinates. A changed Session revision or a receipt that needs the general transaction requires fresh bearer and shared maintenance admission before that transaction starts. A personal managed credential uses a single read snapshot for Runtime eligibility, serving state and the encrypted record's model grant. One snapshot avoids mixing credential policy with a Runtime authorization read from an earlier round trip. Dispatch continues to read current authority after credential preparation.

A queued personal model can wait on the owning Gateway for a committed pressure sample or completion. The bounded wait opens no database transaction or writer span. One statement reads the exact reservation and rechecks its stored scope and current authority after the wake. Fair scheduling still belongs to the database. Older coordinators, batches and inexact reservations use ordinary status admission.

**Foreground requests during page startup.** Background requests can consume all free streams immediately after a conversation is created. The HTTP pool reserves one of its existing reusable connections for the browser bootstrap and prepared conversation operations when the configured limits permit concurrent connections. Other streams keep their own owners and time limits. The Runtime accounts for exact HTTP and WebSocket activity while governance admission or completion writes are pending, without holding the lifecycle queue across those calls.

Verified release-script requests can use the same reserved connection as structured bootstrap. The primary returns that connection after consuming the exact owning generation’s digest attestation. Browser delivery continues under the primary’s authorization and cancellation while the node transport can serve the next interactive request.

**Windows supervisor ownership.** The owner store reads ordinary DACLs through the native security descriptor. It checks exactly the owner, SYSTEM and Administrators and keeps the existing reparse-point and process generation checks. Unfamiliar descriptors use the existing PowerShell verdict and its bounds. The native read owns the descriptor through cancellation and frees the allocation before returning.

**Managed browser deadlines.** The Runtime policy emits a single `connection` configuration row. Cordis replaces the whole config of a patched row, so browser RPC and recovery deadlines must share that row with server timing. The dual Gateway fixture checks both computers' effective HTML bootstrap with different settings.

Managed model diagnostics measure [live input preparation](../../../../packages/context/gateway-execution/README.md#execution-authorization) and [resource admission](../../../../packages/context/gateway-runtime/README.md#resource-admission) at their owners. During resource polling, count queued observations and measure gaps separately from exchanges. Successful responses report coordinator hold time separately from the full status exchange. The Runtime's reservation ID pairs submissions and single-reservation status calls with the Gateway operation ring. A batched exchange has its own diagnostic ID. These measurements add no queries to admission.

A scoped personal model submission reuses a previously verified bearer's Runtime coordinates. The reservation transaction waits for the node accounting row before locking the account and checking the current bearer digest, generation, serving epoch, computer lease and captured Session authority. A rejected check rolls back the reservation and leaves its sequence available for the original operation. Polling and final execution authorization continue to check current authority. Gateway samples for submission and status polling separate bearer connection wait and setup from query duration, which includes database transport.

The [personal model reservation](../../../../gateway/src/node-resource-budget.ts) uses PostgreSQL's implicit transaction when the locked node policy equals the Gateway's validated policy. That equality establishes valid limits before accounting runs. A policy mismatch leaves accounting untouched and uses the explicit transaction, where the Gateway validates the stored policy before commit. The same functions retain account, generation and scheduling checks. An immediately active grant rechecks its scope after reservation in the same transaction. Only that confirmed result can replace a separate status lookup for the same operation. Queue checks and dispatch authority retain their current validation.

Cold Runtime model-policy projection holds the organization catalog revision before reading policy and provider rows. The same read retains disabled routes in the authorization table and carries profiles only for enabled routes. A project includes both organization and project rows, ordered within each scope, without separate round trips for route admission and presentation. Personal policy still locks the account and reads its current role before assembling the policy.

Resource completion serializes on the node accounting row. One statement checks the completed operation against its registered sequence and ID, deletes the reservation and counts the removed row. Each waiter reads a fresh snapshot after obtaining the node lock. Its final ownership statement locks the exact Runtime row immediately before commit. Ready browser admission can acquire the activity row while the coordinator waits for earlier accounting round trips. A generation replacement before the final statement rolls back accounting and queued grants. The private HTTP ingress supplies the authenticated owner to completion, and a temporary bearer lookup failure returns HTTP 503. After proven model quiescence, the [Runtime provider](../../../../packages/context/gateway-runtime/README.md#resource-admission) owns delivery retries with the original sequence and operation ID. The [model service](../../../../packages/llm/llm/README.md#understand-the-implementation) retains that permit through an adapter close deadline and releases it when the same iterator later confirms termination.

## Alternatives considered

**Merge the whole request-resolution chain first.** The /account/api/context chain is data-dependent session→user→scope→runtime→admission reads; batching it pays off per request but leaves the continuous sampler and token streams multiplying RTTs forever. The observation round and token witness run unconditionally and at higher frequency than any single endpoint, so they were collapsed first.

**Signed center-issued authorization assertions.** The forwarding gateway attaches `x-dsh-gateway-forward`, a `GatewayPrincipalSigner.issueForward` Ed25519 assertion. `GatewayNodeServiceProxy` stamps it on every forwarded HTTP and WebSocket request; any client-supplied header is deleted first. On the destination, `currentUser` honors it only when the request demonstrably arrived over the node-service channel (`x-dsh-target-node` equals the local node id): it resolves the issuer's key through `NodePrincipalDirectory` and verifies signature, exact audience, organization, and liveness with `verifyGatewayForward`; a failure falls back to ordinary session validation. A verified assertion skips the session renewal and authority snapshot entirely — every downstream query still encodes its own permission predicates, so revocation granularity is the assertion TTL plus the existing access-invalidation aborts on in-flight work. Two acceptance-time hardenings apply: claim timestamps must be safe integers (a non-integer or non-finite `expiresAt` would otherwise pass `typeof` checks into an effectively eternal window), and verified nonces are consumed into a per-destination ledger bounded by expiry — a replayed assertion verifies once and is refused thereafter.

The claims also carry the authorized placement the issuer already computed. `issueForward` optionally signs a `selection` (`runtimeId`, `target`) plus a `context` (`environment`); the proxy records the exact request selectors and the resolved catalog environment in each forward `Target`. Scope and runtime storage are node-local data (`assigned_node_id`-keyed reads), so they are deliberately not claimed — the issuer cannot produce them honestly. The destination `requestContext` adopts the claimed placement only when the assertion verified **and** the parsed request selectors (`dshRuntime`, `dshTarget` or the scope cookie) equal `selection` exactly **and** the claimed environment's node is the destination itself: it then invokes `runtimeRouter.resolve` with a checked `RuntimePlacement`, skipping the per-request catalog placement walk while still resolving scope and node-local owner storage itself. Any mismatch falls back to the ordinary resolve path, so a context claim can never widen placement beyond what the destination would have computed.

The trust registry is `harness.compute_nodes.principal_public_key` (migration `122_node_principal_keys.sql`), published per gateway at startup, honored only for nodes with a live managed agent lease or no agent row (directly provisioned gateways such as the center, whose revocation is row status). Rollout is naturally staged: a destination running new code still answers old peers through the fallback, and a peer without a published key simply fails verification and takes the session path.

**Cross-node write-path clearing.** The cache is per-process: a `markStopped`/`beginStart` on one gateway clears only that process. Remote gateways still learn the change through the 2s TTL, since runtime lifecycle writes do not bump `access_revision`; downstream generation checks inside resource operations fence any stale verdict within that window.

**Longer token TTL without invalidation.** Rejected: revocation must propagate at notification speed, not TTL speed, so the cache subscribes to the existing access-invalidation channel instead of lengthening staleness.

## Consequences

The [completion fixture](../../../../gateway/tests/node-resource-budget-postgres.spec.ts) checks the committed successor, concurrent duplicate receipts and rollback when the exact Runtime identity has changed. For one active model and one waiting user, the coordinator sends seven PostgreSQL commands including transaction setup and commit. With a 150 ms acknowledgement delay per command, three local measurements had a 1.09 s median completion time, compared with 1.54 s for ten commands.

The [resource HTTP fixture](../../../../gateway/tests/runtime-resource-api.spec.ts) observes one governance command for an eligible reservation and its replay. An explicit transaction uses three commands. The fixture also checks the fallback under a different valid policy, rollback under an invalid policy, and refusal after a lease or permission change. The [execution HTTP fixture](../../../../gateway/tests/execution-runtime-isolation-postgres.spec.ts) compares four statements with one for exact personal authorization and verifies that simultaneous input entry reuses the same scope and revision. The [dual Gateway fixture](../../../../gateway/tests/fixtures/versioned-node-service.mjs) observes one owner query on a prepared creation, no execution root before the first prompt, and one root and one inbox entry after a retry.

The focused PostgreSQL storage regression verifies one lookup, mismatched owners and computers, and no process startup. The instrumented personal HTTP proxy performs eight governance statements before forwarding and one after response completion, compared with nine and one before removing the redundant revision read. This count excludes entry routing and node transport. The [ready Session HTTP fixture](../../../../gateway/tests/runtime-asset-admission-postgres.spec.ts) checks separate counts for accepted assertions, fallback to account admission, replay refusal and maintenance. Browser fixtures measure independent targets with synthetic latency; they do not establish native Windows or cross-country production response times.

Measured on production with `log_statement='all'` windows: all three nodes emit `observe_node_resources` calls (~1.5–3.5ms server-side) and zero of the former statement chains; token witness executions on the Ubuntu pool dropped ~75%. Median `/account/api/context` on `windows-vps-47` fell to ~46ms node-side; `ubuntu-101` remains ~6s because its request-path serial reads and background pollers still multiply the 200ms RTT — merging those is the follow-up.

Semantics preserved and covered by `tests/node-resource-budget-postgres.spec.ts` (65/65): stale-while-queued captures are dropped, statement-bound lock waiting is unchanged, contention still surfaces `503 database-busy`, warnings bypass the cadence gate, and ordered witnesses keep rejecting older captures. Two test fixtures were rewritten for the single-call shape: the schema-shadowed `clock_timestamp` probe became a delayed-dispatch pool proxy, and the mocked-`performance.now` expiry test now holds the node lock past a real 50ms `staleMs`.
