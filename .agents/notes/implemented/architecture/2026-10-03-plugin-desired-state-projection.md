# Agent Note: PostgreSQL desired plugin state projects into runtime profiles, and instances publish observed composition

Status: implemented

English | [中文](2026-10-03-plugin-desired-state-projection.zh.md)

## Problem

Profile files under `dshHome/profiles/web` were the only source of truth for plugin composition. The Admin Plugins page could edit a target only while its instance held a live generation lease, so an administrator could not prepare composition for a stopped user or project, and a recreated `dshHome` silently lost every prior selection. Runtime changes never reached the database either, so the Admin view of composition drifted from what instances had actually applied. Separately, the management grant gated reads and writes alike, which left ungranted users a blank page even though inventory visibility was never the privileged part.

## Decision

- Migration [`049_plugin_states.sql`](../../../../gateway/deploy/postgres/migrations/049_plugin_states.sql) adds `harness.plugin_states` — one desired-state row per `(organization, user|project)` owner holding verbatim patch `entries`, the ordered `bundles` selection, and a CAS `revision`. An absent row means no desired state and nothing projects; the existing `instances.applied_policy_revision` column records the revision a spawn projected.
- [`gateway/src/plugin-state.ts`](../../../../gateway/src/plugin-state.ts) owns the contract: `get`/`set` serve the admin editor with revision-guarded writes, `readForSubject` returns the stored snapshot joined with the instance's `applied_policy_revision` marker, `publishForSubject` accepts runtime write-back under base-revision CAS and answers 409 on a stale base, `project` materializes a row into the profile files, `observed` reads the files for the Admin online view, and `markApplied` stamps the projected revision.
- Spawn projection runs inside `proxy.beforeStart` after `mountPolicyBundles`: a row newer than `applied_policy_revision` rewrites managed rows in `profiles/web/cordis.patch.yml` (keys limited to `{id, name, disabled}`) and `dsh.profile.bundles` in `package.json`, leaving dependencies untouched. An unresolvable bundle name warns and skips rather than blocking boot, because the database can hold a stale installation reference.
- [`PluginManagerService.change()`](../../../../packages/boot/plugin-manager/src/index.ts) publishes the committed composition through `pluginManagementAuthorization.publishDesiredState` after the profile files land. The publish base is the snapshot's `appliedRevision` — the revision the profile files were materialized from — so a runtime booted before an administrator's save still conflicts instead of overwriting it. A 409 applies the snapshot's desired state into the profile files and reloads HMR in place, so a running instance converges on an administrator's edit without restart; a reload that cannot activate every converged entry reports as a warning without masking the convergence. Publication failure leaves the committed files and reports a `warnings` entry; the next spawn re-projects the stored revision. Standalone profiles without the authorization service skip write-back and keep upstream behavior.
- Authorization splits read/manage: `authorize('read')` is unconditional, so `listPlugins`, `listBundles`, `listVersionExemptions`, `registries`, `waitForInstall`, and `access` stay open, while `inspect` and every mutation pass `authorize('manage')`. The new `access` remote answers `{manage}` so the user page, the Settings inventory tab, and the API proxy gate controls directly; `plugin_access_policies` narrows from read+write to write authority.
- The Admin Plugins page gains a fused composition matrix (`PluginMatrix`) that loads `GET /admin/api/plugins/state` for any target — running or stopped — and edits bundle selection and entry enablement in one table: the Current column mirrors the live inventory or the files' last observed state and its switches apply through the running instance, while the Startup column drafts the saved composition and saves through `POST` with the revision; a 409 reloads the newer state instead of overwriting. The user Plugins page keeps the full inventory visible for every viewer and drops to a read-only mode when `access` reports `manage: false`.
- Both projections — gateway spawn and runtime write-back/reconcile — share one managed-row rule (`{id, name?, disabled:boolean}` keys only) implemented independently on each side, with `desired-state.ts` tests and `plugin-state.spec.ts` pinning the file protocol at both ends.

## Alternatives considered

- **Files as truth, database as mirror.** A mirror would keep offline editing impossible and still lose state on `dshHome` recreation; the database had to become the desired-state authority, with files as its runtime projection.
- **Projecting at admin-write time.** Writing files when the administrator saves would make a stopped instance's live tree disagree with its future spawn materialization and could not survive `dshHome` recreation; spawn-time projection is the only point that sees the final file tree.
- **Recording the install set in desired state.** Bundle entries reference npm packages on the profile filesystem; a database row cannot reinstall them after the home is recreated. Desired state records selection and enablement only, and spawn skips unresolvable bundles with a warning.
- **Per-member desired rows for project instances.** A project runtime composes one shared tree for every member, so per-member enablement has no instance to land on; the project row is the shared desired state.

## Consequences

Administrators can prepare composition for stopped targets and have it land at next spawn, while running instances still apply edits immediately through the invoke path and reconcile onto newer desired rows through write-back CAS. Users keep inventory visibility without a grant and gain a clear read-only surface instead of dead controls. Conflicts resolve in favor of the later administrator write: the running instance's 409 path converges its files onto the stored row, and a failed publication self-heals at the next spawn. The contract is pinned by `plugin-state.spec.ts` (projection, CAS, observed reads) against real PostgreSQL, `desired-state.ts` file-protocol tests, runtime-api endpoint tests, `PluginMatrix` component tests, and the read-only store/component specs. Installation specifiers and per-user configuration values remain file-plane concerns out of scope for this layer.
