# Agent Note：显式启动传输组保留共享应用响应

Status: implemented

[English](2026-10-26-client-startup-transport-groups.md) | 中文

## 问题

启动 combo 的 URL 与 revision 标识整个有序包集合。即使共享应用包的 revision 和相对顺序完全一致，启用两个可选检查包仍会改变按 URL 长度划分的分区。检查设置不同的 profile 因而使用不同的不可变响应键下载同一批共享应用代码。

## 决策

[客户端模块](../../../../packages/client/modules/README.zh.md#use-this-package)持有可选应用传输组。组合包通过经过校验的配置选择自身包，加载器不包含功能名称策略。Inspector 组合包把两个浏览器包放入同组，使其启用状态保留共享应用序列的响应键。

启动图保留原有条目与依赖顺序。分组只改变 factory 注册的传输：先是未分组的应用序列，再按配置排列各组；每个序列保留其图内顺序与现有 URL 限制。[惰性 factory 物化](2026-07-23-client-plugin-loading-model.zh.md)让模块执行与 CSS 副作用仍等待依赖到达及 Cordis 导入。引导包保留原有 parser preload 序列。

分组选择当前已挂载的包，不请求安装或激活。缺席成员不产生资源。重复成员和引导包成员会在配置校验时失败，避免传输分配含糊或违反 parser 所有权。

[页面持有的条目控制器](2026-09-23-page-owned-client-entries.zh.md)和[带静态扩展名的 combo 路由](2026-10-20-combo-route-static-extension.zh.md)保留既有所有权与缓存规则。图更新沿用单资源到达路径；可选组内代码变化时，不相关的启动响应仍可复用。

## 考虑过的替代方案

**移除检查功能。** 这改变可用产品能力，没有消除重复传输。

**重新排列应用图。** 没有依赖边的条目仍可能有可观察的激活顺序；缓存分组不授权改变该顺序。

**每个包各发一个启动请求。** 这增加首次访问的请求开销。由组合包持有的分组隔离已测得的成员变化，同时保留共享响应。

**选择全局哈希桶数量。** 有价值的默认值需要覆盖可选包集合、压缩大小和冷网络的证据。显式分组具有当前组合消费者，避免缺少依据的全局传输策略。

## 影响

传输分组可能增加冷启动响应数或改变压缩效率，因此接受缓存复用时，同时核对完整响应字节数及普通浏览器启动、切换观测。仅凭请求复用不能证明完整 UI 就绪更快。依赖物化、立即条目、source map、不可变 revision 与 HMR 仍须验证。

分组只影响代码传输，不引入 Session 数据格式、模型输入、任务调度规则或进程预算。
