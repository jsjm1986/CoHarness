# Agent Note：按范围声明备份覆盖与恢复重新授权

Status: implemented

[English](2026-11-05-project-recovery-reauthorization.md) | 中文

## 问题

恢复点不能证明全部存储域均已采集。Runtime 文件、账号文档、插件状态和定时投递可以分别推进。策略变更使恢复审批失效后，已停止的源端也不能安全地重新开放写入。

## 决策

每个导出器声明已覆盖的数据域，并保留明确缺口。个人 PostgreSQL 记录限定到所选组织、电脑、账号和 Runtime；账号文档继续使用账号与电脑共享的身份。一致的原生文件快照只包含获准的根目录。未知插件状态、独立水位和缺少文件快照均阻止完整保护。治理清单版本 2 只保留不含业务名称的项目归属标识，版本 1 仍可作为部分清单读取。两个版本均不恢复登录、节点凭据或写入权限。

项目恢复在不可逆提交前，重新核验当前管理员、项目所有者、目标电脑使用权、节点准入和现行策略。继续接管会为同一恢复点、目标和审阅过的策略修订单独保存不可变审批，要求先完成当前修订下的独立演练。源端封存凭证保持不可变。常规配额与恢复点目标调整不能改变尚未完成的接管。

目标在安装候选数据前，先记录目录的排他归属。父目录与 inode 凭证只允许重用本次操作安装的根目录。取消会撤下候选并记录清理完成，其他操作之后才能使用该目标。撤下的非空目录保留在活动布局之外供管理员检查。由本机操作系统提供的项目锁串行执行 worker，避免借用其他连接时仍占用治理数据库连接。

目标核验文件与投递回执后，只能激活已发布的更高写入代次。同一个治理事务记录激活，并暂停原源端的策略。保护新源需要单独配置策略、接收电脑及凭据。源端不可达和租约过期均不能证明写入进程已经停止。[维护恢复](2026-09-25-gateway-deployment-maintenance.zh.md)独立保留当前审批和写入约束。

## 考虑过的替代方案

**将复制的目录称为完整备份。** 可变文件不能证明与数据库或外部插件副作用处于同一检查点。缺少证据时必须保留覆盖缺口。

**恢复旧策略修订或重新开放源端。** 这可能复活已撤销的凭据，或者产生两个写入端。新的不可变审批允许继续接管，同时保留封存结果。

**重试前删除任何占用暂存路径的数据。** 该路径可能含有其他操作或管理员的数据。清理必须依据已记录的物理归属凭证。

## 影响

个人和治理范围支持隔离恢复，不会宣称可沿用项目的正式接管流程。Mac 缺少快照服务或数据卷尚未核验时，仍是部署缺口。日常备份不会为了获取快照而停止运行任务。替换电脑后保留 Runtime 身份和项目成员关系，成员仍须具备目标电脑使用权。

## 验证

独立 PostgreSQL 实例覆盖所有者撤权、策略轮换、过期确认、当前修订演练、维护恢复保护及激活。正常 Admin HTTP 请求驱动两端 worker，每端治理连接池仅有一个连接。文件系统用例在不同准备阶段中断，保留外来文件，并核验取消后的重试。独立进程核验 worker 死亡后项目锁能够释放。Mac 到 Windows 的原生加密恢复在删除源端、断开通道后核对文件字节、Session 顺序和投递回执；它不代表生产数据已完整覆盖，也不代表完整接管耗时。
