# Agent Note: Gateway deployment maintenance control plane

Status: implemented

English | [中文](2026-09-25-gateway-deployment-maintenance.zh.md)

## Problem

A shared-PostgreSQL deployment needs upgrades and restores that every Gateway node honors together. Startup migration applies schema changes but cannot stop writers, coordinate a backup, or prevent a process started before a restore from writing over it. The `deploy/postgres` shell scripts produce dumps without coordinating the serving cluster, so a concurrent writer can leave database and managed files inconsistent at the switch point.

## Decision

[Migration 041](../../../../gateway/deploy/postgres/migrations/041_maintenance_control.sql) adds a durable control plane per organization. `harness.cluster_control` holds the mode (`serving`/`maintenance`/`restoring`), the maintenance epoch, the monotonic write epoch, and the window reason. `harness.deployment_operations` is the operation ledger; `harness.backup_records` registers each dump with its managed-file manifest, verification state, and the write epoch it was taken under. `compute_nodes.maintenance_applied_epoch` records the epoch each node's write gate has observed.

The [maintenance service](../../../../gateway/src/postgres/maintenance-service.ts) drives transitions. Entering maintenance bumps the epoch every writer must acknowledge; the HTTP write gate in [server.ts](../../../../gateway/src/server.ts) answers mutating requests with 503 while the mode is not `serving`, and `stale-epoch` once the write epoch advances past a process's startup baseline. The baseline is read before initializing cached file dependencies and rechecked before startup business writes and readiness; a restoration during initialization refuses startup rather than attaching old caches to a new epoch. Writer quiescence requires every runtime record to confirm a stopped process, plus a fresh current-epoch heartbeat and zero in-flight writes from each active or draining Gateway. Declaring a node offline cannot bypass runtime stop confirmation. A node that resumes heartbeating returns to `active` because an offline declaration was premature.

The standalone applier `pnpm pg:deploy` ([scripts/deploy-apply.ts](../../../../gateway/scripts/deploy-apply.ts)) runs the sanctioned sequence outside the serving process: status, maintenance enter/exit, migration apply under quiesce, backup (dump plus managed-file snapshot, verified and registered), restore, and rolling-restart planning. Administrators drive the same service through `/admin/api/deployment*` and the Admin Deployment page; pending admin restore requests are claimed by the applier rather than applied inline. The complete file manifest records provider-owned roots, empty directories, absent roots, permissions, ownership, sizes and SHA-256 digests. Recursive streaming copies are verified against their captured bytes and exact membership. The registry distinguishes these snapshots from legacy shallow arrays, which cannot qualify for complete restoration.

The applier renders `pg_restore --clean --if-exists` SQL into a private temporary file, then executes it with `psql --single-transaction --set=ON_ERROR_STOP=on`. Temporary relations preserve the live control row, operation ledger, and backup registry across the dump’s schema replacement. Before commit, those records replace dump-time copies, the write epoch advances, and the mode remains `restoring`. A failed SQL statement or mismatched organization or compute-node identity rolls back the entire database restoration. The selected dump is copied to private staging and checked against its recorded digest before SQL rendering. `resumeRestoring` verifies the surviving fence and refuses a lost one; it does not reopen and repair a window after exposure.

A database-wide advisory lease excludes competing backups, restore appliers and maintenance exit. Before any destructive operation, the applier captures and verifies a complete protection backup of the current database and data. Its identity and the selected artifact digests are committed atomically with the restoring fence. A failed SQL or file restore remains in `restoring`; a fresh applier can reacquire the lease and resume only that recorded target, reusing the original protection copy instead of capturing partially restored state. Only successful file reconciliation permits `completeRestore` to return to maintenance. Losing the lease connection aborts the local command proxy. Restore SQL retains an independent advisory transaction lock and checks the original backend PID, backend-start timestamp, random session marker and lock ownership before mutation and before commit. New appliers and maintenance exit refuse while that SQL transaction remains active. A failed ownership check rolls back the SQL transaction. Even when a detached Docker/container process outlives its local proxy, its transaction cannot overlap a new restoration; an uncertain commit remains behind the restoring fence until file reconciliation.

Command runners drain or close every owned pipe and await child exit. A catalog-only reader may close stdin before consuming the full dump; this is accepted only with exit status zero. Input read failures, output write failures, and nonzero exits remain failures, and error cleanup waits for process termination.

Storage providers append their actual roots to a runtime-owned inventory before writing. The anonymous identity file is registered by its actual writer. User creation records its document root after insertion of the unique account row and before commit, rejecting links and damaged inventories; commit failure retains local diagnostics without touching another account’s inventory. An instance row assigns a process and cannot determine whether retained user data still requires backup; a confirmed single-node database includes deleted users without instances. Previous roots remain recorded. Gateway selection validates each claim against its database-owned runtime and configured defaults or administrator-approved custom roots. Explicit historical adoption requires quiesced maintenance and a private node-admin-owned approval file; no directory-name heuristic establishes ownership. The protection backup retains later additions before selected-backup membership replaces them; project source, SSH workspaces and unclaimed content remain outside the operation. Profile initialization, normalization and writes register their four durable metadata files before mutation; generated dependencies are excluded. SDK launches selecting an independent Harness home clear an inherited inventory unless the caller explicitly supplies one for that child.

Node storage changes compare candidate ownership with the complete moved and retained source claims. Only default DSH_HOME data and declared Gateway key locations move; database-owned HOME, project mounts and custom provider paths keep their owners and locations. Copied absolute inventories require a complete reviewed replacement bound to the saved node revision, with the original retained as immutable evidence. Preflight verifies all copied bytes and metadata before publishing settings, and refuses unresolved configuration references or incompatible systemd HOME containment. This avoids treating a directory copy as proof that runtime consumers now read it.

## Alternatives considered

**Exclude the control-plane tables from restore.** `pg_restore` has no `--exclude-table`; selectively retaining live tables also retains foreign keys that prevent replacing the referenced organization table. Preserving live records within the restore transaction keeps dependency ordering and prevents another connection from observing dump-time control state.

**Let each writer poll maintenance and stop itself.** A sleeping or partitioned node then keeps writing past the window. The gate must reject writes at the server, and epoch acknowledgment makes a stale node's silence visible instead of assumed drained.

**Restore managed files best-effort alongside the dump.** Input digests are checked before copying, but a later I/O failure can still leave a partially restored file set. The serving gate must remain closed until the complete restored set passes verification.

## Consequences

The write gate adds one control-row read per mutating request; deployment-control routes remain available during maintenance. Restores retain the current ledger and backup identity, advance the write epoch before committing changed data, and remain closed for managed-file verification. Only verified backup records permit restore. The complete file-backup runner accepts one provisioned organization on one compute node. Multiple organizations or nodes are refused until every node can supply an independently verified data bundle; the shared maintenance fence alone does not establish filesystem coverage. Destination organization and compute-node identities must match the dump. Private SQL and dump staging require disk space and are deleted after success or failure. The current node configuration and database connection file come from the first protection snapshot; the selected backup’s configuration remains available for separate review. Applied storage locations and node identity must agree before SQL execution. Current revisions are retained; outstanding apply requests remain bound to their original write epoch, and the immutable checkpoint binds the derived file manifest so a retry cannot switch restoration policy. Protection backups are retained for explicit administrator cleanup. Real PostgreSQL tests prove data restoration, retained control records, stale-writer rejection, and rollback of incompatible dumps.
