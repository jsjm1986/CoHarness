# Agent Note：Gateway 部署维护控制面

Status: implemented

[English](2026-09-25-gateway-deployment-maintenance.md) | 中文

## 问题

共享 PostgreSQL 的部署需要所有 Gateway 节点共同遵守的升级与恢复流程。启动迁移能应用 schema 变更，但无法停止写者、协调备份，或阻止恢复前启动的进程覆写恢复结果。`deploy/postgres` 的 shell 脚本只产生转储而不协调在服集群，并发写者可能在切换点留下数据库与受管文件不一致的状态。

## 决策

[迁移 041](../../../../gateway/deploy/postgres/migrations/041_maintenance_control.sql) 为每个组织建立耐用控制面。`harness.cluster_control` 保存模式（`serving`/`maintenance`/`restoring`）、维护纪元、单调写纪元和窗口备注。`harness.deployment_operations` 是操作台账；`harness.backup_records` 登记每个转储及其受管文件清单、验证状态和取材时的写纪元。`compute_nodes.maintenance_applied_epoch` 记录各节点写门已观察到的纪元。

[维护服务](../../../../gateway/src/postgres/maintenance-service.ts) 驱动状态迁移。进入维护会推进全部写者必须确认的纪元；[server.ts](../../../../gateway/src/server.ts) 在维护期间以 503 拒绝变更请求，恢复后的旧进程以 `stale-epoch` 拒绝写入。启动基线在初始化文件缓存依赖前读取，并在启动业务写入和就绪前再次核对；初始化期间发生恢复会拒绝启动，不能让旧缓存使用新纪元。写者收敛要求全部运行时记录确认进程已停止，且每个活动或排空中的 Gateway 心跳新鲜、已确认当前维护纪元、在途写入归零。把节点登记为离线不能绕过运行时停止确认。恢复心跳的节点重新成为 `active`，因为此前的离线声明已不再成立。

独立应用器 `pnpm pg:deploy`（[scripts/deploy-apply.ts](../../../../gateway/scripts/deploy-apply.ts)）在服务进程之外执行受控序列：status、维护进入/退出、静止下应用迁移、备份（转储加受管文件快照，验证并登记）、恢复、滚动重启计划。管理员通过 `/admin/api/deployment*` 和管理端 Deployment 页驱动同一服务；管理端发起的待处理恢复请求由应用器认领而非内联执行。完整文件清单记录提供者所有的根、空目录、缺席的根、权限、所有者、大小及 SHA-256 摘要。递归流式副本按捕获的字节及精确成员集合进行验证。登记表区分完整快照与旧式浅层数组；后者不能用于完整恢复。

应用器先把 `pg_restore --clean --if-exists` 生成的 SQL 写入私有临时文件，再以 `psql --single-transaction --set=ON_ERROR_STOP=on` 执行。临时关系在转储替换 schema 期间保留当前控制行、操作台账和备份登记。提交前用这些记录替换转储中的旧副本，推进写纪元并保持 `restoring`。SQL 语句失败或组织、计算节点身份不匹配会回滚整个数据库恢复事务。选中的转储先复制到私有暂存区，按登记摘要验证后才生成 SQL。`resumeRestoring` 只核验保护状态仍在，丢失时直接拒绝，不在曾经暴露写入窗口后补救。

数据库级 advisory lease（咨询锁租约）排斥并发备份、恢复应用器，并阻止退出维护。任何破坏性操作前，应用器先捕获并验证当前数据库及数据的完整保护备份。保护备份身份与选中产物摘要随恢复保护状态原子提交。SQL 或文件恢复失败后保持 `restoring`；新应用器可以重新取得租约，只继续登记的目标，复用原始保护副本，而不捕获部分恢复状态。只有文件全部核对成功后，`completeRestore` 才能返回维护状态。持锁连接丢失会取消本机命令代理。恢复 SQL 保留独立的咨询事务锁，并在变更前和提交前核验原后端 PID、后端启动时间、随机会话标记及锁归属。该 SQL 事务仍活动时，新应用器及退出维护均拒绝执行。归属核验失败会回滚 SQL 事务。即使脱离本机代理的 Docker／容器进程仍在运行，其事务也不能与新恢复重叠；提交结果不明时仍受恢复保护状态约束，直到完成文件核对。

命令运行器会排空或关闭其拥有的全部管道，并等待子进程退出。仅读取目录的程序可能在读完整份转储之前关闭 stdin；只有退出码为零时才接受该情况。输入读取失败、输出写入失败和非零退出仍视为失败，错误清理会等待进程终止。

存储提供者在写入前把实际根追加到运行时所属的清单中，且保留之前的根。 匿名身份文件也由真实写入者登记。用户创建在唯一账号行插入后、事务提交前登记文档目录，拒绝链接和损坏清单；提交失败保留局部诊断，不修改其他账号的清单。运行实例行用于进程分配，不能决定保留用户的数据是否仍需备份；在已确认的单节点数据库中，无实例的已删除账号仍纳入数据所有权。Gateway 按数据库确认的运行时，以及已配置的默认位置或管理员批准的自定义根，验证每项认领。显式采纳历史记录要求维护写者已静止，并使用节点管理员所有的私有批准文件；不能凭目录名推断所有权。选中备份的成员集合替换当前集合前，保护备份会保留后来新增的数据；项目源码、SSH 工作区和未认领内容不参与操作。Profile 初始化、规范化及写入在变更前登记四个持久元数据文件，生成的依赖不纳入。SDK 启动选择独立 Harness home 时清除继承的清单，除非调用方明确为该子进程提供清单。

节点存储变更将候选所有权与全部需移动及需保留的源认领比较。只有默认 DSH_HOME 数据和声明的 Gateway 密钥位置发生移动；数据库所有的 HOME、项目挂载和自定义提供者路径保留其所有者及位置。复制的绝对清单必须使用绑定已保存节点代次的完整审阅清单进行替换，原件作为不可变证据保留。预检在发布设置前验证全部复制字节和元数据，并拒绝未解决的配置引用或与 systemd HOME 包含要求不兼容的位置，不能把目录副本当作运行时消费者已读取该位置的证据。

## 备选方案

**恢复时排除控制面表。** `pg_restore` 没有 `--exclude-table`；单独保留存活控制表还会保留阻止替换组织表的外键。在恢复事务内保存当前记录，既遵循依赖顺序，也让其他连接无法观察到转储时的旧控制状态。

**让每个写者轮询维护状态自行停写。** 休眠或网络分区的节点会越过窗口继续写。写门必须在服务端拒绝写入，纪元确认也让沉默节点的状态可见，而不是被当作已排空。

**受管文件随转储尽力恢复。** 复制前会校验输入摘要，但后续 I/O 失败仍可能留下部分恢复的文件集。在全部恢复文件通过核对前，服务写入必须保持关闭。

## 影响

写门给每个变更请求增加一次控制行读取；维护期间部署控制路由保持可用。恢复保留当前台账和备份身份，在提交数据变化之前推进写纪元，并在受管文件验证期间继续禁止写入。只有已验证的备份记录能进入恢复。完整文件备份运行器接受单个已配置组织和单个计算节点。在每个节点都能提供独立验证的数据包之前，多个组织或节点会被拒绝；共享维护保护状态本身不能证明文件系统已被覆盖。目标组织和计算节点身份必须与转储一致。私有 SQL 和转储暂存需要磁盘空间，成功或失败后都会删除。当前节点配置和数据库连接文件取自第一次保护快照；选中备份的配置保留供另行审阅。SQL 执行前必须确认已应用的存储位置与节点身份一致。当前修订号被保留，未执行的应用请求仍绑定原始写纪元；不可变检查点绑定派生文件清单，防止重试时切换恢复政策。保护备份保留到管理员明确清理。真实 PostgreSQL 测试验证数据恢复、控制记录保留、旧写者拒绝及不兼容转储的整体回滚。
