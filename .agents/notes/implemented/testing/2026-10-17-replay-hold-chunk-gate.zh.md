# Agent Note：回放 `hold` 把脚本流闸停在指定分片处

Status: implemented

[English](2026-10-17-replay-hold-chunk-gate.md) | 中文

## Problem

需要在模型流仍在进行时断言的浏览器滚动契约测试，要求断言执行时流确实还在进行，但回放脚本是有限长度的：`chat-scroll-contract` 的锚点用例与甩动用例各自按节奏播放固定数量的文本增量，然后在滚动驱动的锚点捕获之后统计到达的分片数。在负载较高的运行机上，滚轮、甩动与重绘步骤耗尽了脚本，计数停在总量上，断言 `received > captured + 5` 永远不可能成功——master 浏览器扫描在 run 38952571005 上以 `124 > 129` 和 `249 > 250` 失败，尽管产品行为本身正确；锚点用例此前已在更早的 master 运行上以相同的耗尽特征失败过两次。把录制脚本加长只能缩小窗口而不能消除它：任何有限长度的流在足够慢的机器上仍会落败。

## Decision

`chunks` 回放条目可以携带 `hold: { after, releaseFile }`（`dsh-llm-replay` 的 `ReplayHold`）。生成器先产出 `after` 个分片，随后轮询 `existsSync(releaseFile)` 再产出其余分片；释放文件由场景持有，在希望尾部继续流动时创建。相对路径的 `releaseFile` 相对覆写文件所在目录解析，标记因此落在场景自己的 `mkdtemp` 回放目录内并随目录一并清理；`after` 必须小于分片总数（永远不会生效的闸停在加载时即报错）；等待与 `paceDelay` 遵循相同的 abort 契约，被取消的请求不会滞留。

锚点用例在流末尾前 24 个分片处设闸，在捕获阅读锚点之后立即释放，因此"流仍在进行"这一前置条件是测试自己创造的状态，而不是需要赢下的竞争。甩动用例扣住 44 个分片：先释放工具闸，在流停住期间甩离底部再甩回，待重新钉住之后才释放尾部，底部跟随由此被证明确实接管了到达底边的实时分片。`markdown-inline-code-links` 把 popup 导航纳入已有的有界 shift+click 重试，而不是只重试 popup 创建事件：注释所引用的 chromium-1234 缺陷在任一位置都可能丢弃默认动作，停在 `about:blank` 的 popup 现在只消耗一次手势尝试，而不会让整个用例失败。这与[观察等待落在被观察的状态上](2026-09-27-observation-waits-on-observed-state.zh.md)是同一条规则：等待绑定在被断言的状态上，而不是绑定在墙钟窗口上。

## Alternatives considered

- **更长或更慢的录制流**——任何有限脚本在足够强的争用下仍会耗尽，前置条件仍是概率性的；闸停让"流还在运行"成为测试控制的事实。
- **在前缀与尾部之间放一个 `hang` 式收尾条目**——`hang` 只能作为整条等待取消的条目存在，结束流会改变 turn 的结算方式；断言需要的是一条能续上的连续流，而不是两次调用或一条被中止的流。
- **断言前先轮询 `assistantFrames` 确认存活**——在计数前重新确认流未结束只能把竞争缩小到"观察到断言"的间隙而无法消除，输掉竞争的运行仍会产生错误失败。
- **等待 DOM 就绪而非等待流**——这些用例需要的内容恰恰是进行中的分片本身；只有挡住生产者才能保证它们存在。
- **为 popup 重试或放宽 `waitForURL`**——被等待的状态已经明确；失败模式是上游手势被丢弃，只有重新发出手势才能修复，因此重试只是给已知的瞬态划界，而不是掩盖等待。

## Consequences

两个滚动用例与 popup 用例的前置条件不再依赖机器速度；它们仍上报的失败指向真实回归。任何需要在指定时刻观察到进行中流的场景都可以复用同一个条目字段，而不必自行设计节奏预算。付出的代价：没有任何用户可见的损失——该字段是可选的，既有条目行为不变，`hold` 只存在于覆写伴随文件中，released 会话格式不受影响。
