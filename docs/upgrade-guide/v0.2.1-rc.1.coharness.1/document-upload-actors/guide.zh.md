# 使用原始上传者恢复文档上传

[English](guide.md) | 中文

## 变更

已认证的上传会话属于发起用户。其他有项目写权限的成员不能查询、追加、完成或取消该会话，浏览器指纹只能恢复同一用户的会话。并发上传会预留不同目标名称。已发布文档继续使用普通访问策略。

个人 Gateway 运行时即使没有 collaboration 插件，也会把上传请求绑定到已验证的 principal。无法取得上传者的受管请求，以及缺少 collaboration 授权的项目运行时，都会拒绝创建上传，不会创建匿名会话。

`.upload-sessions/v1/` 下绑定参与者的私有清单使用第 2 版格式。旧后端拒绝该版本。第 1 版会话仍然没有所有者；已认证的组合拒绝认领，因为无法确认原始上传者。带文档实例身份元数据的完成引用使用第 3 版清单；第 1、2 版无法表示该元数据。上传状态、传输列表和复制结果都会保留经过校验的身份字段。浏览器拒绝无效的完成引用或不匹配的字节数。公开 HTTP 协议仍为 `resumable-v1`。

已接受的 `verifying` 上传在接收阶段保留期限之后仍可恢复。其名称和并发名额保持占用，直到完成、失败或经认证的取消；启动会恢复中断的校验。浏览器轮询使用独立的有界等待。清理接收中或终态会话必须有有效的过期记录。未知、损坏或超出大小上限的清单会使清理失败并保留字节；缺少清单时也保留部分文件以供恢复。恢复自动清理需要兼容的读取器或原始清单备份。

## 迁移

1. 运行第 3 版写入器前先停止旧工作进程：早期清理实现可能删除未知清单。备份每个文档根目录，包括 `.upload-sessions/`，并同时升级 Gateway、`dsh-host-userdoc-http` 和本地文档后端。
2. 使用原始账号和作用域恢复已绑定身份的会话。其他账号即使有项目写权限，也会收到 `404 DOCUMENT_UPLOAD_NOT_FOUND`。浏览器元数据不能覆盖所有者。
3. 重新选择源文件，使用已认证账号重新发起尚未完成的无身份上传，包括没有 collaboration 时创建的个人上传。浏览器会在收到 HTTP 404 后丢弃旧的恢复元数据。其私有部分文件保留到配置的保留期届满；旧的接收中预留占满作用域并发上限时，等待过期后再重试；已接受的校验应等待其完成，或由原始已授权参与者取消。不要向旧清单写入所有者或身份，也不要降低版本号。回滚时恢复完整且兼容的备份。
4. 使用两个有项目写权限的账号，以相同文件名和指纹发起上传。确认上传标识符和名称不同，完成两个文件，并核对目录中的所有者。重启服务，确认未完成的上传仍然只接受发起账号。
